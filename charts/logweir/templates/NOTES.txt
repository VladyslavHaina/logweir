THE UI, AND WHOSE AUTHORITY IT ACTS WITH:
  kubectl port-forward -n {{ .Release.Namespace }} svc/{{ .Release.Name }}-ui 8001:8001
  then open http://127.0.0.1:8001/ui/

  The page is served by kubectl proxy from a pod whose ServiceAccount is
  "{{ .Release.Name }}-ui", and the proxy attaches THAT ServiceAccount's
  credential to every request it forwards: anyone who can reach the Service
  acts with that ServiceAccount's authority. The page holds no credential of
  its own. The proxy admits only /ui/ and /apis/logweir.dev/v1alpha1/, the
  ServiceAccount holds only the verbs the page issues (get/list on the five
  namespaced kinds, create on approvals/kafkaclusters/backupschedules/restores,
  patch on backupschedules, list on trustrosters), and there is no Ingress.
  It is bound in this namespace{{ with .Values.ui.namespaces }} and in {{ join ", " . }}{{ end }};
  to let the page see another namespace's objects:
      kubectl create rolebinding {{ .Release.Name }}-ui --clusterrole={{ .Release.Name }}-ui --serviceaccount={{ .Release.Namespace }}:{{ .Release.Name }}-ui -n <namespace>

BEFORE ANY CUSTOM RESOURCE — the five Secrets, the two keypairs, the

The digests this chart pins are LOCALLY BUILT measurements (Global Constraint
37, `blocked: images not published`): a cluster with no access to
ghcr.io/logweir/… leaves the controller pod in ImagePullBackOff, exactly as
docs/install.md path (a) records. An author-only install (images you built and
loaded yourself) is examples/author-only.values.yaml, and it is not evidence
that anything was published.
