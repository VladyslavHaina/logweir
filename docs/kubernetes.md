# Running Logweir on Kubernetes

The operator guide for one team's install: back up, restore, verify, set
retention and approve. Start at [install.md](install.md) for the walk from
install to disaster restore, and for installing and upgrading the chart. Every
reason, exit code and runner output line is in [reference.md](reference.md); signed document fields are in
[formats/](formats/). Section numbers used before v1 are mapped at
[the end of this page](#section-numbers-before-v1).

## Concepts

Logweir backs up Kafka topics to object storage, restores them into new topics,
and verifies both with signed evidence. The `weirkeeper` controller turns
custom resources into runner Jobs; the runner (`logweir`) does the work and
signs the result. The controller links no signing code; the console links it
only to sign its own approval documents with its `ConsoleConfirmation` key,
never evidence (see
[the signing-oracle residual](#the-signing-oracle-residual)).

**Minimum Kubernetes: 1.29.** The CRDs seal what may not change with CEL
validation rules, which are GA in 1.29. On an older API server the rules are
dropped silently, so an approved object could be edited. The CRDs live in
[`../charts/logweir/crds/`](../charts/logweir/crds/) and are generated by
`just crds`; do not hand-edit them. Every `kubectl` command in this repository
names its context.

Fourteen kinds, on `logweir.dev/v1alpha1`:

| Kind | Scope | What it is |
|---|---|---|
| `KafkaCluster` | Namespaced | A saved connection: bootstrap servers, auth, role, marker topic. Credentials are references. [Saved connections](#saved-connections) |
| `BackupDestination` | Namespaced | Where archives live, referenced by name. Holds no credential value. [Destinations](#destinations) |
| `BackupSchedule` | Namespaced | A recurring backup of named topics or of all user topics. Every field but `sourceRef` is editable. [Schedules](#schedules) |
| `Backup` | Namespaced | One archive run, as one Job. [A `Backup` and its Job](#a-backup-and-its-job) |
| `Restore` | Namespaced | One restore run, as one Job, into new topics only. A drill is a `Restore` in `scratch` mode. [Restore](#restore) |
| `Approval` | Namespaced | A signed authorisation for one `Restore`. [Approvals](#approvals) |
| `TrustPolicy` | Cluster | The keys that may sign evidence, confirm and approve, with a lifecycle; names the namespaces it governs. [Trust](#trust-which-keys-govern-a-namespace) |
| `TrustRoster` | Cluster | Deprecated, still served: the fallback trust, `TrustRoster/default` only |
| `RecoveryCatalog` | Namespaced | A bounded, expiring view of one destination's recovery points. [The recovery catalog](#the-recovery-catalog) |
| `RetentionPolicy` | Namespaced | What may be removed from one destination. `Report` by default, which deletes nothing. [Retention](#retention) |
| `Preflight` | Namespaced | One readiness check. Authorises nothing. [Readiness checks](#readiness-checks) |
| `TopicDiscovery` | Namespaced | One observation of the topics a connection can see. [Topic discovery](#topic-discovery) |
| `ProtectionPolicy` | Namespaced | A recovery objective and the health against it. [Protection health](#protection-health) |
| `Switchover` | Namespaced | Applies a restore's reviewed consumer positions to stopped groups, under its own approval. [Consumer positions](#consumer-positions) |

`RehearsalSchedule` is withdrawn in v1 (release-notes item 73).

**What is sealed.** `KafkaCluster`, `Approval`, `TrustRoster`, `Backup` and
`Restore` carry `self == oldSelf` on `.spec` ("spec is immutable; create a new
object instead"); `Backup` and `Restore` add the destination-sentinel rules.
`BackupSchedule` seals `sourceRef` only. `BackupDestination` seals
`spec.storage` and `spec.transport.security`. `RecoveryCatalog` seals all but
`spec.syncRequest`. `RetentionPolicy` seals `destinationRef`, `catalogRef` and
`scope`. `TopicDiscovery` and `Preflight` seal `spec.request`;
`spec.cancelRequested` may move `false` → `true` only. A `TrustPolicy` key may
not be removed, and each key's fields move one way only. `ProtectionPolicy` is
not sealed. The `ValidatingAdmissionPolicy` example
(`config/samples/validatingadmissionpolicy.yaml`) is 1.30+, ships commented and
is not installed.

**Absent fields keep the old behaviour.** Every field added since v0.1 is
optional, and absent means what the controller that stored the object did; an
upgrade converts nothing. Two exceptions are required on purpose:
`Backup.spec.topics` stays required (a dynamic run carries `topics: []`), and a
destination-backed `Backup` carries `archive.url:
logweir-destination://<destinationRef.name>` and no `archive.secretRef`, so an
older controller refuses it `ArchiveUrlUnreadable` instead of stalling every
`Backup` watch. Absent status fields (`progress`, `capture`, `completion`,
`signedAt`, `trust`) mean "not observed", never a failure.

**Exit codes** are one contract for every runner: 0 pass; 1 operational, no
artifact; 2 a signed result that did not pass; 3 a guard refused; 4 signing or
lock failed, nothing uploaded. See [Troubleshooting](#troubleshooting-by-reason-and-exit-code)
and [reference.md](reference.md#exit-codes).

**Images.** `logweir` (runner, with `logweir-retention`), `weirkeeper` and
`logweir-console`, for `linux/amd64` and `linux/arm64`. The controller reads
`LOGWEIR_RUNNER_IMAGE` and `LOGWEIR_RUNNER_PULL_POLICY` (`Never`, `IfNotPresent`
or `Always`; anything else refuses startup) once at start; the chart sets them
from `runnerImage` and `runnerImagePullPolicy`, and they reach every Job the
controller creates. Both images embed `third_party/org-root.fingerprint`, the
SHA-256 of `third_party/org-root.pub.pem`'s DER SPKI (`just check-org-root`;
the private half was not kept), at
`/etc/logweir/org-root.fingerprint`; no runtime code reads it yet
([keys.md](keys.md)).

**One namespace, workspaces inside it.** An install is one Helm release in one
namespace, and everything Logweir creates lives there; [Workspaces](#workspaces)
says how its objects are grouped.

**Boundaries.** Approval is a DSSE signature checked against trusted public
keys, not a `SubjectAccessReview`. Browser verification, resumable crashed
restores and an HTTP metrics endpoint do not exist. A cluster-admin is not
stopped by anything here ([stability.md](stability.md), O0).

### Workspaces

An install is one Helm release in one namespace. Its objects, credential
Secrets, signing and console keys, runner Jobs, the controller and the console
all live there, and the controller watches that namespace only. Inside it a
**workspace** (`dev`, `tst`, `stg`, `prd`, …) is a name in the chart's
`workspaces` list and the label `logweir.dev/workspace` on every object. A
workspace has its own console role bindings, its own approval mode and its own
manual-run and check pools; trust, the signing identity, the console keys and
the images are per install.

- **The label is required.** The console writes it from the workspace in the
  address and never lets a body choose it. A `kubectl apply` must set it, to a
  name in the list: an object without it, or with a name not listed, gets
  `WorkspaceUnknown` and nothing runs. A run that had already finished keeps
  its phase and conditions (nothing more runs for it), so a workspace dropped
  from the list and put back finds its Backups and Restores as they were. List
  one workspace with `kubectl get backups -l logweir.dev/workspace=prd`, or
  all with `-L logweir.dev/workspace`.
- **References never cross workspaces.** A `Backup`, `Restore`, schedule,
  catalog or policy whose `…Ref` names an object of another workspace gets
  `WorkspaceMismatch`, terminal, with no Job; an approval signed for one
  workspace never authorises a run in another (`AuthorizationSubjectMismatch`).
  The rule follows each reference to the end: a `Preflight` or `Switchover` of
  a `dev` `Restore` whose connection, destination or credential is in `prd` is
  refused at the `Preflight` or `Switchover` itself, and so is a TTL clone
  being deleted (it keeps its finalizer and says why).
  `prd` data reaches `stg` for a drill through a `stg` destination with a
  read-only grant on `prd`'s bucket, which an administrator sets up.
- **A credential Secret carries the label too.** The controller mounts a Secret
  a Logweir object names (`auth.secretRef`, a destination's grants, a retention
  credential) only when the Secret's `logweir.dev/workspace` equals the
  referrer's. The console labels the Secrets it writes, and names an existing
  one only as an inline archive's `credentialRef`; one you create with
  `kubectl` needs the label of the workspace whose objects name it (see
  [config/samples/secrets.yaml](../config/samples/secrets.yaml)). The install's
  key Secrets (`logweir-signing-key`, the console's keys, the OIDC client
  secret) carry no workspace label, so no object can name them.
- **Names are unique per install.** Kubernetes enforces it: a name another
  workspace holds is refused ("in use in this installation").

**What Kubernetes RBAC can and cannot do here.** RBAC stops at the namespace and
cannot see workspaces.

1. Reading a Logweir kind in the namespace reads it in every workspace.
   `logweir-viewer` is the one Role to hand out for `kubectl`: it reads every
   workspace and no Secret.
2. Creating a Logweir object is creating it in any workspace: the label is free
   text, and the console's role bindings do not apply to `kubectl`.
3. **Whoever can read Secrets, create Pods or Jobs, or create a Secret in the
   namespace holds Logweir's keys** ([the signing-oracle
   residual](#the-signing-oracle-residual)): with them a person can sign
   evidence and forge any approval mode, `prd`'s two-person rule included.
4. So give people the console, and `kubectl` write access to the namespace only
   to the people you would make administrators of every workspace (Kubernetes'
   own `admin`). The chart ships no `kubectl` write role.

## Backups and schedules

A backup reads named topics (or every user topic) from a saved connection and
writes an archive and a signed receipt to a destination. A schedule creates a
`Backup` per slot; "Back up now" creates one by hand.

### Destinations

A `BackupDestination` says where archives live. It holds no credential value,
only Secret, ServiceAccount and `ConfigMap` names and key names.
`spec.storage` and `spec.transport.security` are immutable; the description, the
CA reference and the four access grants may change, so rotation needs no new
object.

**`VALID` is not a reachability claim.** The reconciler dials nothing and lists
no bucket. It checks the location rules, the addressing and the CA `ConfigMap`,
re-evaluates them every 300 s (a CA rotation edits the `ConfigMap`, not the
destination) and writes `status.reason`. The reasons are in
[reference.md](reference.md#backupdestination). To test the store itself, run a
`Preflight` with `operation: DestinationAccess`.

```bash
kubectl --context docker-desktop get backupdestination -n team-a
# NAME     BUCKET   ENDPOINT                             TRANSPORT   VALID   AGE
# primary  lw-a     https://minio-a.storage.svc:9000     TLS         True    4m
```

- `status.canonicalUrl` and `status.locationDigest` are written on every
  verdict, refusals included. `status.caBundleSha256` is written only when the
  bytes were readable, so its absence means "no digest", never "empty bundle".
- The controller reads the CA `ConfigMap` and never a Secret. It holds no verb
  on `secrets`, so it checks a grant's spelling (a DNS-1123 name in this
  namespace, legal data keys), never its existence. A `<namespace>/<name>`
  spelling is refused `DestinationRoleNotConfigured`.
- A Secret that is really missing is reported by the kubelet to the pod that
  needed it, as `CredentialSecretNotFound` naming the Secret and the key: in a
  run's `status.progress.diagnostics[]` and `RunnerReady` condition, or in a
  `DestinationAccess` preflight.
- `storage.addressing: VirtualHosted` with a `storage.endpoint` is refused
  `AddressingUnsupportedByEngine`: the engine forces path-style whenever an
  endpoint is set. `VirtualHosted` with no endpoint is AWS S3's default and is
  fine. Addressing never changes transport; only `InsecureHTTP` permits
  plaintext, and it needs an explicit `http://` endpoint.

#### The grants, and the object-storage actions each one needs

A destination names up to four grants in `spec.access`: `archiveWrite`,
`archiveRead`, `evidenceWrite` and `evidenceRead`. An absent `archiveRead` or
`evidenceWrite` falls back to `archiveWrite`. An absent `evidenceRead` means
verification is `NotAttempted`, with a detail naming the field; it never falls
back to a wider grant.

The minimal actions were measured on docker-desktop MinIO by removing one action
at a time (the `U6` phases of the D2 live harness, `e2e/k8s/d2/d2_live.py` at
commit `d648b4d7`, removed from the tree after v0.2.0). The full table, with the
action each removal broke, is in [reference.md](reference.md#object-storage-grants).

| Role | Minimal actions, each at the resource scope shown |
|---|---|
| `archiveWrite` | `s3:ListBucket` on the bucket (`s3:prefix` in `<prefix>/*`); `s3:GetObject` and `s3:PutObject` on `<bucket>/<prefix>/*`; `s3:PutObject` on `<bucket>/logweir/*` |
| `archiveRead` | `s3:ListBucket` on the bucket (`s3:prefix` in `<prefix>/*`); `s3:GetObject` on `<bucket>/<prefix>/*`. For a restore of a catalog point and its preflight, also `s3:GetObject` on `<bucket>/logweir/backups/*` and, on a versioned bucket, `s3:GetObjectVersion` on `<bucket>/<prefix>/*` |
| `evidenceWrite` | `s3:PutObject` on `<bucket>/logweir/*` |
| `evidenceRead` | `s3:GetObject` on `<bucket>/logweir/*` |
| write probe | `s3:PutObject` on `<bucket>/logweir/readiness/*` |
| `catalogSync` reader | `s3:ListBucket` on the bucket (`s3:prefix` in `logweir/*`); `s3:GetObject` on `<bucket>/<prefix>/*` and on `<bucket>/logweir/*`; on a versioned bucket, `s3:GetObjectVersion` on `<bucket>/<prefix>/*` |
| retention enforcer | `s3:ListBucket` on the bucket (`s3:prefix` in `<prefix>/*`); `s3:GetObject` and `s3:DeleteObject` on `<bucket>/<prefix>/*` |

- **Nothing in this build needs a wider grant.** `s3:DeleteObject` is not needed
  by `archiveWrite`; no role but the retention enforcer is ever granted it.
  `s3:GetObject` under `logweir/*` is not needed by `evidenceWrite`, whose puts
  are create-only. `s3:GetBucketLocation` is needed by no role: the engine and
  the store are given an explicit region.
- **Without `s3:PutObject` on `logweir/*` a backup exits `4`
  (`ExecutionClaimUnproven`) before the engine starts.** The runner's first write
  there is its create-only execution claim, so nothing is written.
- **The write probe is the `evidenceWrite` principal's.** A
  `destination.evidenceWritable` check creates `logweir/readiness/<destinationUid>.json`
  as that grant (projected as `LOGWEIR_EVIDENCE_AWS_*`, or run as its
  ServiceAccount), and the row says `grant=evidenceWrite` or `grant=destination`.
- **The `catalogSync` reader is wider than `archiveRead` in one place.** The walk
  uses the `archiveRead` grant but lists under `logweir/*` and reads under both
  roots. A grant scoped to `archiveRead`'s minimum publishes no view: the
  catalog lands `Synced=False` with `PartialScan`, or `ResultUnreadable` when the
  first listing is refused. If you separate the two, give `archiveRead` the
  catalog's actions, or accept that the catalog will not sync.
- **The read of a pinned version.** A point whose receipt pins its manifest's
  version is read by version id (`GET ?versionId=`) wherever the current version
  is not the pin: by the catalog's deep check, a point-bound restore and its
  preflight. AWS S3 authorises that read as `s3:GetObjectVersion`
  [UNVERIFIED — needs a real AWS S3 bucket and a credential source]; without it
  the point is `Unreadable`, the restore exits 1 and the preflight answers
  `archive.backupSet` `AccessDenied`. MinIO serves it under `s3:GetObject`
  (measured 2026-10-09). An unversioned bucket issues no pin.
- **The `Switchover` Job and a TTL clone's cleanup Job read the restore's
  evidence with `evidenceRead`** (the scorecard, its sidecar, the positions
  mapping, a rollback's record) and write beside it with `evidenceWrite` (the
  switchover record, the cleanup attestation). The read grant is projected in
  the archive slot (`AWS_*`) and named on the runner's `--evidence-read-grant`;
  neither Job reads the archive. An `evidenceRead` no pod can hold
  (`ControllerIdentity`, absent, or a workload identity on another
  ServiceAccount than `evidenceWrite`'s) falls back to `evidenceWrite`, which
  then needs `s3:GetObject` on `<bucket>/logweir/*`. A store that refuses a
  read is never a verdict on the evidence: the run fails `EvidenceUnreadable`,
  naming the key, the grant and the store's class, for example `could not read
  logweir/drills/<run>.json with grant evidenceRead of BackupDestination
  team-a/primary: AccessDenied`.
- **A point-bound restore reads its receipt through `archiveRead`**, at
  `logweir/backups/<backupId>/<run id>.receipt.json` with its signature
  [UNVERIFIED — the receipt read was not bisected on a restricted principal; the
  reads are `drill::binding` and `check::kinds::restore`].
- **The retention enforcer HEADs every key before it deletes it**, to refuse a
  versioned bucket where a delete would only write a delete marker. Without
  `s3:GetObject` every key is `Kept` with `code=VersionProbeRefused` and nothing
  is deleted [UNVERIFIED — re-measured by U6/retention-enforcer at the next lab
  refresh]. Its tombstones and record are written with the destination's
  `evidenceWrite` grant (or `archiveWrite`), never `archiveRead`.

The docs lint
`the_documented_grants_name_the_version_read_of_every_role_that_makes_one`
holds this table and `install.md`'s to the readers that make the read.

#### What a destination-backed run carries

A `Backup` naming `spec.destinationRef` resolves it for `archiveWrite` before
anything is created. It freezes the resolution (UID, generation, location
digest, CA digest) into the run's immutable execution inputs and renders the
runner Job from that frozen block. A schedule passes its `destinationRef` to the
`Backup`s it creates. Editing, rotating, or deleting and re-creating the
destination afterwards cannot change a run that exists; a re-created Job reads
the frozen block back from the run's plan `ConfigMap`. `status.execution`
present means the plan is the answer.

- **The controller's own environment never reaches a destination-backed Job.**
  The Job carries a complete `AWS_*` and `LOGWEIR_*` set computed from the
  destination alone; [reference.md](reference.md#destination-backed-job-environment)
  lists every variable. `AWS_ENDPOINT_URL` is absent by construction and
  `AWS_METADATA_ENDPOINT` is a dead loopback, so a missing workload identity is a
  refusal, never the node's instance role.
- **The legacy inline `archive` path still forwards the controller's**
  `AWS_ENDPOINT_URL`, `AWS_REGION`, `AWS_ALLOW_HTTP` and
  `AWS_VIRTUAL_HOSTED_STYLE_REQUEST`. A controller started with
  `AWS_ALLOW_HTTP=true` therefore overrides an inline run's approved
  `allow_http: false`. Move each object to a `BackupDestination` to close this.
- **A destination with `spec.transport.caBundle` is refused for `Backup` and
  `Restore`**, `CaBundleUnsupportedByEngine`, because the engine's handling of a
  custom CA was never measured. Checks, verification and the controller's own
  reads do use the CA. An administrator who accepts the risk sets
  `engine.allowUnverifiedCustomCa` in the installation policy.
- **A `WorkloadIdentity` grant replaces the Job's `serviceAccountName`** with the
  ServiceAccount the grant names, bypassing the chart's runner ServiceAccount.
  Two different workload-identity ServiceAccounts in one pod are refused
  `ExecutionContextConflict`.
- **`status.destination`** is `{name, uid, generation, locationDigest}`, written
  at the freeze. The bucket, endpoint, region and addressing stay in the run's
  `execution-inputs.json`.
- **`status.records`** is written only from a verified receipt, so the `RECORDS`
  column stays blank until the verdict is `Valid`.

### A `Backup` and its Job

A `Backup` is one archive run. Its name and `status.backupId` are a pure
function of its trigger, so a duplicate reconcile gets `AlreadyExists` instead of
a second partial archive.

```yaml
apiVersion: logweir.dev/v1alpha1
kind: Backup
metadata:
  name: nightly-catchup          # any DNS-1123 name of 63 characters or fewer
  namespace: <your namespace>
spec:
  sourceRef: { name: source }    # a KafkaCluster in this namespace
  topics: [orders, payments]     # a NAMED allowlist; a wildcard is refused
  destinationRef: { name: primary }
  archive: { url: logweir-destination://primary }
  triggeredBy: manual
  deadlineSeconds: 3600
```

No annotation is required and none is read. The run identity is derived from the
object alone; `spec.trigger.kind` decides it, and `spec.triggeredBy` (what the
signed receipt carries) must agree with it.

| `spec.trigger.kind` | `triggeredBy` | Must also be true | `metadata.name` | Run identity (`status.execution.id`, the archive `backup_id`) |
|---|---|---|---|---|
| `Scheduled` | `schedule` | `spec.scheduleRef.uid` (or a `BackupSchedule` controller owner of that name); `spec.slot` a UTC `yyyymmdd-hhmmss`; `attempt: 0` | `logweir-backup-<schedule>-<slot>` | `<BackupSchedule UID>-<slot>` |
| `CatchUp` | `schedule` | the same: slot S, started late | as `Scheduled` | as `Scheduled` |
| `Retry` | `schedule` | `attempt` 1–3, `trigger.retryOf.name` the previous attempt | `logweir-backup-<schedule>-<slot>-r<k>` | `<BackupSchedule UID>-<slot>-r<k>` |
| `Manual` | `manual` | no `spec.slot`, no `attempt` | any; the API mints `logweir-manual-<26 base32>` | this object's API-server UID |
| absent | `schedule` / `manual` | read as `Scheduled` attempt 0 / `Manual` | | |

- A scheduled kind needs its `BackupSchedule` (that name and UID) until the run
  freezes, else terminal `ScheduleNotFound`. A manual run never needs it.
- A copied `spec.scheduleRef.runPolicySha256` that this object's fields do not
  produce is terminal `RunPolicyDigestMismatch`.
- Fields that do not compose the claimed run are `ScheduledIdentityMismatch`;
  an unusable spec (an unknown `triggeredBy`, a non-positive `deadlineSeconds`)
  is `ExecutionSpecInvalid`. Both before anything is created.
- A name longer than 63 characters is refused `NameTooLong` on the object.
- Deleting the object and creating the name again is a new run under a new UID.
  The console's "Back up now" names the object from the idempotency scope, so
  pressing twice is one run.

**What the controller creates.** First an immutable plan `ConfigMap`
`<name>-plan` holding the frozen execution inputs (`execution-inputs.json`, the
run's `backup.yaml` and any CA bytes), with `status.execution
{id, inputsRef, inputsSha256}` recorded in the same pass. Then one Job named
after the `Backup` verbatim, so the `batch.kubernetes.io/job-name` label stays
under 63 characters:

```yaml
spec:
  backoffLimit: 0                    # exactly ONE pod
  activeDeadlineSeconds: <spec.deadlineSeconds>
  podFailurePolicy:
    rules:
      - onPodConditions: [{type: DisruptionTarget, status: "True"}]
        action: FailJob
      - onExitCodes: {containerName: runner, operator: In, values: [2, 3, 4]}
        action: FailJob
  template:
    spec:
      restartPolicy: Never
      serviceAccountName: logweir-runner
      automountServiceAccountToken: false
      securityContext: {runAsNonRoot: true, runAsUser: 65532, runAsGroup: 65532, fsGroup: 65532}
      containers:
        - name: runner                # ALWAYS this name
```

- `fsGroup: 65532` is what makes the projected signing key readable; without it
  the run exits 1 having done nothing.
- The Job has no `resources` block: a namespace `LimitRange` supplies them or
  nothing does. A `ResourceQuota` that requires limits rejects the pod
  (`RunnerReady=False`, `PodCreationForbidden`).
- A Job holding the name that this `Backup` does not control is `JobNameConflict`;
  an object holding the plan name is `PlanConfigMapConflict`. Neither is adopted.
- The controller sets the Job's `ttlSecondsAfterFinished` (7 days) only after the
  exit code is on the status.

**Reading the result.**

```bash
kubectl --context docker-desktop get backups
kubectl --context docker-desktop get backup <name> \
  -o jsonpath='{.status.exitCode} {.status.exitReason}{"\n"}'
```

The `EXIT` column is why `kubectl get backups` is worth running; `REASON`
(`status.exitReason`) says why the run ended, for example `GuardRefused`, and
`-o wide` adds `FAILED`, the controller's reason behind an `operational`. Every
kind whose status holds its reason prints it the same way (`REASON` on
`kafkaclusters`, `preflights`, `topicdiscoveries`, `backupdestinations`,
`approvals`; with `-o wide` on `backupschedules`, `trustpolicies`,
`recoverycatalogs`). The full table
of exit codes, `exitReason` values and terminal reasons is in
[reference.md](reference.md#backup-exit-code-to-status). **A green `Backup`** is `phase: Succeeded`,
`exitCode: 0`, `Complete=True` and `status.evidence.verification.result: Valid`.
`Complete=True` with reason `EmptyCapture` is a run whose every partition was
empty: it records no window and is not a recovery point.

**Topic selection.** `spec.topics` is a named allowlist; a glob metacharacter is
terminal `GuardRefused`. `spec.allUserTopics` beside a non-empty `topics` is
`InvalidTopicSelection`. `status.selection`, written at the freeze, says what the
run may claim, for example
`{"mode":"SelectedTopics","coverage":"NamedTopics","resolvedTopicCount":2,"resolvedTopicBytes":14}`.
Only `coverage: AllUserTopicsAttested` may be shown as "all topics".

### Strimzi owners of a backup's topics

A `KafkaCluster` whose topics a Strimzi cluster manages names it:
`spec.strimzi: {namespace: kafka, cluster: my-cluster}`. A `Backup` of it then
lists the `KafkaTopic`s of that namespace labelled
`strimzi.io/cluster=my-cluster` (unmanaged ones excluded), freezes those naming
the run's topics into its plan, and the receipt records each topic's owner and
`owner_detection: [kafkaTopicResources]`, so a restore exports desired state
for it instead of changing it.

- The read is opt-in and per namespace: chart values
  `strimzi.readKafkaTopics: true` and `strimzi.namespaces: [kafka]` grant `get`
  and `list` on `kafkatopics` through a Role in each listed namespace, and
  nothing else.
- A namespace the chart does not list, a refused list, or no `KafkaTopic`
  resource served fails the backup closed, `OwnerDetectionFailed`, before any
  Job: never "looked, no owner". Remove `spec.strimzi` to back up without it.
- A frozen run never lists again. A controller older than this field refuses a
  plan that carries the list (`PlanConfigMapConflict`); roll back only after
  such runs finish.
- The exported `KafkaTopic` keeps the SOURCE owner's namespace and carries no
  `strimzi.io/cluster` label: Logweir does not know which `Kafka` resource
  manages the target. Set the target's namespace and label before applying
  it; as exported, no operator reconciles it.

### Dynamic selection

`topics: []` with `spec.allUserTopics` means every user topic the run's principal
can see, minus exclusions, resolved per run in the run's own discovery Job and
frozen into its plan. A `TopicDiscovery` is never an execution input.

```yaml
spec:
  topics: []                      # required, and empty in this mode
  allUserTopics:
    exclude:
      topics: ["payments"]        # exact names
      prefixes: ["tmp-"]          # LITERAL prefixes, never patterns
    incompleteDiscovery: BackUpVisibleTopics   # or Refuse. REQUIRED, no default
```

- `incompleteDiscovery` has no default: Kafka silently omits topics the principal
  cannot describe, so no listing proves completeness. A run earns
  `AllUserTopicsAttested` only from an administrator attestation; otherwise
  `VisibleUserTopicsOnly`.
- `spec.deadlineSeconds` must be at least 120 for a dynamic run, else
  `ExecutionSpecInvalid`. The discovery Job's deadline is
  `min(300, spec.deadlineSeconds)`.
- The controller creates `lwd-<backup uid>` (a `topicInventory` check Job, same
  image as the runner, no token, no signing key, no archive credential) and its
  plan `lwd-<backup uid>-plan`, both owned by the `Backup`. The phase is
  `Resolving` with `TopicsResolved=False/DiscoveryRunning`. On success it freezes
  the list and writes `TopicsResolved=True/Resolved`. The Job is collected ten
  minutes after the terminal status.
- `selection.discovery` in the plan records the provenance; the
  `internalExcluded.names` and `excludedByRule.names` samples are bounded (50
  and 200 names, 16 KiB together); each `count` is exact.

Every failure is `Failed=True`, `exitReason: operational`, no `exitCode`, and no
runner Job. "Retryable" means a new `Backup`.

| Reason | When | A new `Backup` could succeed |
|---|---|---|
| `DiscoveryFailed` | No usable result: unreachable broker, rejected credential, pod never started, deadline. The message names the check's own code (`BrokerUnreachable`, `AuthenticationFailed`, …) | yes |
| `PodCreationForbidden` | The discovery pod was refused at creation (quota, `LimitRange`, webhook, missing ServiceAccount), decided 30 s after the Job | once the namespace admits it; `spec.retry` does not retry it |
| `DiscoveryResultUnreadable` | Output that did not verify, or a name Kafka could not hold | no, not without fixing the runner |
| `DiscoveryIncomplete` | Visibility not established and the policy is `Refuse` | with more permission, or an attestation |
| `SelectionEmpty` | Nothing left after internal topics, exclusions and undescribable topics | if the cluster changes |
| `SelectionTooLarge` | Over 1,000 resolved names or 256 KiB; the message begins `BackupSelectionTooLarge`. When the message says the names are a `PREFIX`, the listing was cut at 20,000 topics or the relay budget, and exclusions will not help | split across schedules |
| `SourceChangedDuringResolution` | The broker's `clusterId`, or the saved connection, changed during discovery | yes |
| `JobNameConflict` | Something else owns `lwd-<backup uid>` | remove it first |

### The frozen plan

`<name>-plan` is created before the Job, `immutable: true`, owned by the
`Backup`, and holds three keys: `execution-inputs.json` (the canonical snapshot
of everything the run executes; grammar `logweir.dev/backup-execution-inputs/v2`,
and `v1` is still read), `backup.yaml` (the runner's spec, rendered from the
snapshot) and `allowed-clusters.json`. The Job mounts it at `/plan`. Its
digest is annotated as `logweir.dev/execution-inputs-sha256` beside
`logweir.dev/execution-id`, on the plan, the Job and the pod template, and
recorded before the Job exists:

```bash
kubectl --context docker-desktop -n <ns> get backup <name> -o jsonpath='{.status.execution}'
# {"id":"…","inputsRef":{"name":"<name>-plan"},"inputsSha256":"sha256:…"}
kubectl --context docker-desktop -n <ns> get backup <name> -o jsonpath='{.status.destination}'
# {"name":"prod","uid":"…","generation":3,"locationDigest":"sha256:…"}
```

- The snapshot records the source `KafkaCluster`'s UID and connection, the
  exact topic list, the selection's provenance, the destination block the Job is
  rendered from, the archive, and the runner argv. It carries no credential
  value and no credential Secret name.
- A later pass admits the existing plan only if it is exactly this run's (one
  owner, immutable, three keys, the annotated digest, inputs equal to a fresh
  resolution). Anything else is terminal `PlanConfigMapConflict`, naming what
  differs; nothing is patched or adopted. A changed connection, topic list or
  archive after the freeze is a conflict. A newly observed
  `KafkaCluster.status.clusterId` is not.
- A Job that disappears from a nonterminal `Backup` is re-created from the
  same frozen inputs. **It never runs the engine twice**: every runner claims its
  execution id with a create-only `logweir/backups/<backupId>/execution.claim.json`
  before the engine starts ([the execution claim](formats/backup-receipt.md#the-execution-claim-one-engine-run-per-backup_id)).
  A re-created Job that finds the claim, or finds an older runner's set at the
  prefix, exits 1 with `exitReason: ExecutionAlreadyClaimed`. A schedule with
  `spec.retry` starts a new execution; otherwise the slot is `RunFailed`.
- An evidence store that does not honour conditional create
  (`If-None-Match: *`) makes every backup exit 4, `ExecutionClaimUnproven`,
  before the engine starts. A destination with `writeProbe` on reports it first
  as `notReady / ConditionalCreateUnsupported`.
- **Rolling the runner back re-opens this window.** A runner from before the
  claim (v0.1.5) re-runs the engine over a re-created Job's set and signs a
  second receipt; on an unversioned bucket nothing reports it. Let in-flight
  `Backup`s finish before rolling the runner back.
- The source connection is resolved from the `KafkaCluster` alone. SCRAM
  projects `auth.secretRef.passwordKey` (default `password`) as
  `LOGWEIR_SOURCE_PASSWORD`; a named `auth.tlsCa` is mounted and passed as
  `LOGWEIR_SOURCE_TLS_CA_FILE`. A SCRAM source with a blank
  `auth.secretRef.name` or `auth.username` is `CredentialNotRenderable` before
  any plan or Job. A `spec.sourceRef` naming no `KafkaCluster` is terminal
  `ReferentNotFound`.
- On the backup path `allowedClusterIds` is a consistency rail, not a boundary:
  the rendered file carries an empty list, and the guard refuses a run whose
  observed source id is listed.
- **Residual:** the backup runner does not re-check the mounted plan against a
  digest of its own. A subject with `delete` and `create` on `ConfigMaps` could
  swap the plan before the kubelet projects it; such a subject can create
  `Backup`s outright, so no boundary widens.
- A `logweir.dev/runner-argv` annotation is never executed:
  `RunnerArgvAnnotationIgnored` (`AnnotationIgnored`, `AnnotationMalformed`)
  names its size and digest. A Job that predates frozen inputs is observed to
  completion with `ExecutionInputsUnverified=True` (`LegacyExecution`, or
  `JobInputsMismatch`).

### One backup names at most 1,000 topics

A receipt carries about 3 KB per topic, and every reader has a byte cap
([reference.md](reference.md#read-caps)). So one backup may name at most
**1,000 topics**, at 5,000 bytes a topic, for a receipt of at most
5,131,072 bytes and a catalog record of at most 6,131,072 bytes. The bound is the
evidence relay: a receipt at the cap and its sidecar fill most of the 8 MiB of
pod log the controller reads. `crates/logweir/tests/topic_budget.rs` prints what
a topic costs; 1,000 topics always fit at broker defaults under names of up to
about 200 characters.

A selection over the budget is refused by name before the engine runs. Nothing
is dropped to make it fit.

| Where | What you see |
|---|---|
| `logweir backup run`, more than 1,000 `source.topics` | exit 3, before any client exists |
| `logweir backup run`, the projected receipt or record over its bound | exit 3, `BackupSelectionTooLarge`, with the projected size, the bytes a topic and the bound. The backup id is claimed: run the smaller selection under a new id |
| a `BackupSchedule` with more than 1,000 named `spec.topics` | `Ready=False`, `InvalidRunPolicy`, naming `spec.topics` |
| a `Backup` with more than 1,000 named or resolved topics | `SelectionTooLarge` before any plan or Job |
| the product API | `422`, `selection_invalid`; the API's forms accept at most 256 named topics |

A point already written by a larger backup is not lost. `logweir restore` and
`logweir verify` read a receipt of up to 64 MiB. In the cluster, a point whose
receipt or record is over its bound is listed `Unreadable` with the size and the
bound, is not offered for restore in the console, and its run's verdict stays
`NotAttempted`.

### Schedules

A `BackupSchedule` creates a `Backup` per slot. Every `spec` field is editable
except `sourceRef`:

```bash
kubectl --context docker-desktop -n <namespace> \
  patch backupschedule nightly --type merge \
  -p '{"spec":{"schedule":"0 3 * * *","timeZone":"Europe/Berlin"}}'
```

Re-pointing at another `KafkaCluster` is refused (`spec.sourceRef is immutable;
create a new BackupSchedule to protect a different cluster`). Re-pointing at
another destination is an edit. `kubectl edit` and `kubectl apply` work.

**An edit reaches the next run and never a run that exists.** Each `Backup`
copies the policy and records the revision in `spec.scheduleRef`; the schedule
reports the revision in force:

```bash
kubectl --context docker-desktop -n <namespace> \
  get backupschedule nightly -o jsonpath='{.status.policy}'
# {"effectiveSince":"…","evaluatedAt":"…","generation":7,
#  "runPolicySha256":"sha256:…","timeZone":"UTC","tzdb":"chrono-tz 0.10.4"}
```

`runPolicySha256` covers what a run does (source, topic selection, archive, run
deadline), not when it runs, so suspending moves the generation and not the
digest. `status.policy.evaluatedAt` is when the status last moved; read
`status.nextRuns[0].at` for liveness. A catch-up never runs a slot older than
`effectiveSince`.

**A schedule's name has a 32-character budget.** A slot's `Backup` is
`logweir-backup-<schedule>-<yyyymmdd-hhmmss>`, and a label value is at most 63
characters, of which the fixed parts take 31. A longer name produces no `Backup`
and `Ready=False`, reason `NameTooLong`. With `retry.maxRetries > 0` the name
must be 29 characters or fewer (CEL), for the `-r<k>` suffix.

**An edit the controller cannot run** fails closed. CEL and the OpenAPI schema
refuse at the API server (422): a `sourceRef` change, `allUserTopics` beside
non-empty `topics`, a too-long name with retries, out-of-range values. The
controller refuses the rest with `Ready=False`: `UnparseableSchedule`,
`UnknownTimeZone`, `InvalidTopicSelection` (`topics: []` without
`allUserTopics`, a glob, an illegal name) and `InvalidRunPolicy`. Then nothing new
is admitted, running work continues, and fixing the spec resumes within one
reconcile.

#### Cadence

- `spec.schedule` is a five-field cron read in `spec.timeZone`. **Absent
  `timeZone` means UTC.** A slot is always the UTC instant. A zone this build's
  database does not have is `UnknownTimeZone`, never UTC; `status.policy.tzdb`
  names the database.
- DST: a matching local time fires once per real instant; a nonexistent one
  fires once at the end of the gap; a repeated autumn hour fires at both.
  `status.nextRuns` (the next five firings) marks `RepeatedLocalTimeFirst`,
  `RepeatedLocalTimeSecond` and `NonexistentLocalTimeShifted`. Interval
  schedules keep their UTC cadence.
- **Only the latest due slot is eligible.** Older ones are counted in
  `status.missedSlots {count, countCapped, lastEvaluatedSlot, recent}`.
- `spec.startingDeadlineSeconds` absent means 3600: a slot that came due more
  than **one hour** before the controller looked is skipped, unless
  `catchUpPolicy: Latest` runs the most recent one. A skip is recorded in
  `status.missedSlots` and `status.lastMissedSlot`, with `Ready` reason
  `SlotMissed`. A controller down for a week runs nothing until the next slot
  (`None`) or exactly one `CatchUp` (`Latest`).
- A slot that came due before the schedule's `metadata.creationTimestamp` is
  never fired or counted. Use "Run first backup now" for an immediate run.
- `spec.retry {maxRetries 0..3, delaySeconds}` retries only the latest slot,
  only until the next slot, as a new `Backup` `…-<slot>-r<k>` with a new
  execution id. Retried: exit 1, an exit outside `0..=4` (137/143, OOM), and
  `DisruptedMidDrill`, `PodUnschedulable`, `NoExitCode`, `DiscoveryFailed`. Not
  retried: exits 2, 3, 4, `PodCreationForbidden`, any controller refusal, and any
  state this build does not know.
- `spec.activeDeadlineSeconds` (default 3600) is the run deadline.

#### Concurrency and manual runs

`spec.concurrencyPolicy` is `Forbid` (default: no overlapping schedule-created
run) or `Allow` (up to ten; the eleventh is `Ready=True/ActiveRunLimit`). Active
runs are listed in `status.activeRuns`. Admission is a preconditioned status
reservation (`status.pendingRun {name, slot, attempt, kind, generation}`) written
before the child exists, so two replicas cannot admit the same slot.

A **manual** run (`spec.trigger.kind: Manual`, "Back up now") copies the
schedule's current policy and records it in `spec.scheduleRef`, which is a record,
not an identity. It runs while the schedule is suspended, busy or deleted, never
counts toward `concurrencyPolicy`, and is bounded instead by a per-workspace pool:

| Run | Ceiling ([installation policy](#weirkeeper-policy)) |
|---|---|
| manual `Backup` | `runs.maxManualBackupsActivePerWorkspace`, default `4` |
| admitted manual `Restore` | `runs.maxManualRestoresActivePerWorkspace`, default `2` |
| `Scheduled`, `CatchUp`, `Retry` | none: `concurrencyPolicy` |

A run over the ceiling waits `phase: Queued`, `Admitted=False/ConcurrencyLimited`,
with `status.queue.limit` and nothing created; it starts in arrival order within
one 15 s requeue of a slot freeing. A queued `Restore` keeps its approval's clock:
it is refused `AuthorizationExpired` if the approval expires while it waits
(`status.queue.authorizationExpiresAt`). The pool counts only runs that declare
themselves manual; RBAC on `create backups` governs the rest.

A manual object occupying a slot's deterministic name is a foreign occupant: the
slot is `Ready=True/SlotNameUnavailable`, `status.lastSlot.disposition:
NameUnavailable`, and nothing is created under another name.

#### Reading a schedule

`Ready`'s reason and `status.lastSlot.disposition` say what the last pass
decided; the full truth table is in [reference.md](reference.md#backupschedule).
`status.lastSlot.decidedAt` moves only when the decision does. A settled schedule
writes its status about once an hour (the history inventory).

### Deleting a schedule keeps its history

A `Backup` carries no ownerReference to its schedule; membership is
`spec.scheduleRef {name, uid}` and the `logweir.dev/schedule-uid` label. So
`kubectl --context docker-desktop delete backupschedule nightly`, with any
cascade, stops future admissions and **leaves every run**, every plan
`ConfigMap`, every Job (until its 7-day TTL) and every archive object. Frozen runs
finish. A scheduled run not yet frozen ends `Failed`, reason
`ScheduleNotFound`. Manual runs are unaffected.

Runs created by a controller before retained history still carry an
ownerReference until the controller detaches them. `HistoryRetained` says which
state a schedule is in:

```bash
kubectl --context docker-desktop get backupschedules -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name} {.status.conditions[?(@.type=="HistoryRetained")].reason}{"\n"}{end}'
```

| `HistoryRetained` | Reason | Meaning |
|---|---|---|
| `True` | `Retained` | No run is owned. Delete the schedule however you like. |
| `True` | `HistoryLarge` | The same, and history is over 2,000 runs or 64 MiB: prune. |
| `False` | `LegacyOwnerReferencesRemain` | Terminal runs are still being detached. |
| `False` | `ActiveLegacyRunsOwned` | Only still-running runs are owned; they keep it until terminal. |
| `False` | `MigrationBlocked` | Runs in `status.history.migrationBlocked` could not be detached (`ApiForbidden` and `ApiInvalid` clear themselves; `NoScheduleReference` never does), or the inventory did not finish. |

`kubectl --context docker-desktop delete backupschedule <name> --cascade=orphan`
is always safe. Gate an upgrade script on `status.history.ownershipScanComplete`.

**Recreating a schedule under the same name** gives it a new UID, so it sees
none of the old runs as its own; list them with `-l
logweir.dev/schedule-uid=<uid>`. A slot whose name the old generation still holds
is `SlotNameUnavailable`. Recreation is only for changing `sourceRef`.

**Pruning history.** No Logweir component deletes a `Backup`, a `ConfigMap` or an
archive object. Retained history costs etcd (about 8 KiB a run for 20 named
topics; about 79 KiB for a dynamic run of 1,000 topics). To prune:

1. Delete only **terminal** `Backup`s, with your own RBAC. Deleting one removes
   its plan `ConfigMap` and Job and drops it from Kubernetes history; the archive
   and receipts stay. Record `status.backupId`, `status.evidence.receiptKey` and
   `sidecarKey` first.
2. Never delete a nonterminal `Backup`: its Job goes with it (`NoExitCode`, a
   partial archive).
3. Keep, per schedule UID, the newest `Succeeded` run with a `Valid` verdict,
   every run newer than
   `max(startingDeadlineSeconds, maxRetries × delaySeconds + activeDeadlineSeconds)`,
   and any run a nonterminal `Restore` plan names.

```bash
kubectl --context docker-desktop -n <ns> get backups \
  -l logweir.dev/schedule-uid=<uid> -o json \
  | jq -r '.items[]
           | select(.status.phase == "Succeeded" or .status.phase == "Failed")
           | select(.metadata.creationTimestamp < "2026-01-01T00:00:00Z")
           | .metadata.name' \
  | xargs -r -n1 kubectl --context docker-desktop -n <ns> delete backup
```

A pruned current-slot run is never re-run: the scheduler reports `AlreadyFired`.

### A schedule has no retention report

`spec.retention{keepLast, keepDays}` no longer reports (release-notes item 78).
A schedule that still sets it keeps backing up and carries one condition:

```bash
kubectl --context docker-desktop get backupschedule nightly \
  -o jsonpath='{.status.conditions[?(@.type=="RetentionReportWithdrawn")].message}'
# spec.retention no longer reports; use a RetentionPolicy
```

Remove the field to clear it. Retention is a [`RetentionPolicy`](#retention).
Outside a `RetentionPolicy` in `mode: Enforce`, no Logweir component in tag 1
holds any delete capability against object storage. The controller's own
archive handle (`LOGWEIR_ARCHIVE_URL`, for the legacy inline archive) is
read-only, and guard G-RET (`scripts/check-no-archive-write.sh`, in `just lint`)
fails the build if the control plane names a write or a delete. Retention never
touches a Kafka topic.

## Saved connections

A `KafkaCluster` is one saved connection (contract v1). One function resolves
it for the probe, every backup and every restore, so a probe can never report
`reachable: true` for settings a run dials differently. `spec` is CEL-immutable:
changing a connection means a new object. `status.clusterId` is read from the
broker.

| Field | Absent means | Reference or value |
|---|---|---|
| `bootstrapServers` | required, at least one entry | value |
| `auth.mode` | required: `plaintext`, `scramSha512`, `scramSha256`, `plain` or `mtls` | value |
| `auth.username` | required for `scramSha512`, `scramSha256`, `plain` | value (public identity) |
| `auth.secretRef.name` | required for the SASL modes | reference to a Secret in this namespace |
| `auth.secretRef.passwordKey` | `password` | key name |
| `auth.tls` | `false` | value: the only switch that turns TLS on; must be `true` for `plain` and `mtls` |
| `auth.tlsCa` | the image's `ca-certificates` and the engine's roots | reference: exactly one of `secretKeyRef` or `configMapKeyRef` |
| `auth.clientCertificate` | required for `mtls`, refused otherwise | reference to one Secret: `name`, `certificateKey` (`tls.crt`), `privateKeyKey` (`tls.key`) |
| `role` | required: `source` or `target` | value |
| `markerTopic` | a `mode: scratch` restore against this cluster is refused | value |
| `status.credentialBinding` | written by the controller | the value the credential Secret's `logweir-binding` key must hold |

| `auth.mode` | `auth.tls` | Credential | Logweir's client (librdkafka) | The engine |
|---|---|---|---|---|
| `plaintext` | `false` only | none | `PLAINTEXT` | no `security:` block |
| `scramSha512` | either | password | `SASL_PLAINTEXT`/`SASL_SSL`, `SCRAM-SHA-512` | `SCRAM-SHA512` |
| `scramSha256` | either | password | `SASL_PLAINTEXT`/`SASL_SSL`, `SCRAM-SHA-256` | `SCRAM-SHA256` |
| `plain` | `true` only | password | `SASL_SSL`, `PLAIN` | `SASL_SSL`, `PLAIN` |
| `mtls` | `true` only | client certificate and key | `SSL` | `SSL` |

- **References never cross a namespace** and are never read by the controller;
  the kubelet resolves them at pod start. A password is projected as
  `LOGWEIR_SOURCE_PASSWORD` / `LOGWEIR_TARGET_PASSWORD`; a CA as `ca.crt` under
  `/connection/source-ca` or `/connection/target-ca`, its path in
  `LOGWEIR_SOURCE_TLS_CA_FILE` / `LOGWEIR_TARGET_TLS_CA_FILE`; a client
  certificate as `tls.crt` and `tls.key` (mode `0440`) under
  `/connection/{source,target}-client-cert`, paths in
  `LOGWEIR_{SOURCE,TARGET}_TLS_CERT_FILE` / `..._TLS_KEY_FILE`.
- **A CA only adds trust to TLS; it never turns TLS on.** Both clients get the
  same CA path, trust exactly it, and verify broker hostnames. `tlsCa` without
  `tls: true` is refused; removing a needed CA makes the dial fail, never fall
  back to plaintext. Prefer `configMapKeyRef`: a CA is public.
- **SASL/PLAIN only over TLS**: `plain` without `tls: true` is `PlainWithoutTls`,
  at admission, at the resolver and in every runner (exit 3). Confluent Cloud API
  keys and Azure Event Hubs connection strings (`username: $ConnectionString`)
  use this mode; neither provider has been run against
  ([support-matrix.md](support-matrix.md#managed-kafka-providers)).
- **mTLS:** `kubectl create secret tls <name> --cert=client.pem --key=client.key`
  (an unencrypted key: PKCS#8, PKCS#1 or SEC1). The principal is the
  certificate's subject, reported as `mtls:secret/<name>`. Receipts and catalog
  records that name `scramSha256`, `plain` or `mtls` are format 1.4.0, scorecards
  1.5.0.
- **Rotation needs nothing re-entered.** Write the new password into the Secret
  the connection names; the next Job gets it. Rotate the broker and the Secret
  together. The username, bootstrap servers and TLS switch are identity: they are
  in the signed plan, so changing them needs a new connection and a new approval.
- **No credential value leaves the Secret**: no status, log, `ConfigMap`, Job
  manifest, download or evidence carries one, and nothing reads one back.

Every refusal below happens before any `ConfigMap` or Job exists, lands on the
object as a named state, and clears `status.reachable`:

| Configuration | State |
|---|---|
| `plaintext` with `tls: true`; `tlsCa` with `tls: false`; `tlsCa` naming both or neither source; an empty bootstrap entry or one with a comma or whitespace; `mtls` with `tls: false`; `clientCertificate` on a non-`mtls` mode | `ConnectionConfigInvalid` |
| A SASL mode with no `auth.username` or `auth.secretRef.name`; `mtls` with no `clientCertificate` | `CredentialNotRenderable` |
| `plain` with `tls: false` | `PlainWithoutTls` |
| A Secret or `ConfigMap` name that is not DNS-1123, or an illegal key; a Job in another namespace | `ConnectionReferenceInvalid` |
| A field the running controller does not implement | `ConnectionFieldUnsupported` |
| A credential Secret without this connection's `logweir-binding` | `CredentialBindingMismatch` (refused by the runner) |
| An approved restore plan whose `target` is not this connection | `ConnectionPlanMismatch` |

On the `KafkaCluster`, `ConnectionConfigInvalid`, `ConnectionReferenceInvalid`
and `ConnectionFieldUnsupported` are re-evaluated every reconcile, so a
controller that understands the object clears them with no edit; for a `Backup`
or `Restore` that references it, every refusal is terminal.

**Reachability.** The probe Job's verdict sets `Reachable` and
`status.reachable`. Reachable means the bootstrap address named the cluster
AND every broker the cluster advertises answered the probe on its advertised
address (FX-46). When the bootstrap answers and an advertised broker does not
(an `advertised.listeners` entry this namespace cannot reach), the reason is
`AdvertisedBrokersUnreachable` (`Reachable=False`), the message gives how many
of how many answered, and the probe Job's log names each silent broker. A
probe that crashed, could not be read
(`ProbeOutputUnreadable`), was refused at creation (`PodCreationForbidden`) or is
older than 630 s (`ProbeStale`) clears `reachable`, keeps `clusterId` and
`observedAt`, and is probed again on the 315 s cadence. A `Restore` admits a
target only on `reachable: true`.

### Schema Registry (PROD-03.1, 03.2)

`spec.schemaRegistry: {url, username?, secretRef?: {name, passwordKey}}` names the
cluster's Confluent-compatible registry (immutable with the rest of `spec`; the
password key defaults to `registry-password`; `username` and `secretRef` go
together, for HTTP basic auth). The console writes the password into the
connection's own Secret. TLS trusts the public roots plus `auth.tlsCa` when set.

- **Backup (source):** after the engine, the runner snapshots every subject and
  version through the REST API into `<run_id>.schema-registry.json` beside the
  receipt; the receipt's `schema_registry` block names it. A registry that does
  not answer, refuses the credential, or is over 100 000 versions or 32 MiB never
  fails the backup: the block says why it was not captured
  ([backup-receipt.md](formats/backup-receipt.md#schema_registry--the-source-registrys-snapshot-format-190)).
- **Restore (target):** before any topic is created, the runner reads the
  framed schema IDs of every record it restores, takes the subjects holding them
  and the subjects they reference, and registers what the target lacks in
  `IMPORT` mode with the source's IDs and versions; each subject's mode is put
  back exactly as it was. No record byte changes. Refused (exit 3, no topic
  created): `SchemaConflict` (an ID or version held with other content),
  `SchemaRegistryCannotKeepIds` (no `IMPORT` mode: Karapace, Apicurio's
  compatibility API), `SchemaRegistryReadOnly`, `SchemaRegistryModeNotRestored`,
  `SchemaSnapshotInvalid`, `SchemaRegistryUnreachable`. A target connection
  without a registry is not refused; the scorecard says the schemas were not
  imported. Imported schemas are never removed. The registry user must be
  allowed to set a subject's mode (on Redpanda, a superuser). Any registry
  answer other than the one that means "not there" refuses the run. The plan's
  `target.schema_registry` must equal the target connection's
  (`ConnectionPlanMismatch`). The snapshot comes only from a verified receipt:
  the bound point's (`source.point`). A plan bound to no point (a restore
  planned from a Backup with no catalog row) whose set captured a registry is
  refused `SchemaSnapshotInvalid` before any topic is created, because its
  receipt cannot be verified there: plan it from the set's catalog point, or
  restore into a connection without a registry. The runner and `target.schemas`
  find that out from the receipt its set's `execution.claim.json` names (the
  archive-read grant reads `logweir/backups/` for it); a set with no claim
  imports nothing (`noSnapshot`).
- **Checks:** `registry.reachable` (connection test and backup readiness,
  advisory) and `target.schemas` (restore readiness, blocking) are listed only for
  a connection that names a registry.
- The registry Secret carries the connection's `logweir-binding` (it covers the
  registry URL and username) and is projected as
  `LOGWEIR_{SOURCE,TARGET}_REGISTRY_PASSWORD`, beside
  `LOGWEIR_{SOURCE,TARGET}_REGISTRY_CREDENTIAL_BINDING`.

### Credential binding

A credential Secret is used only when its data key `logweir-binding` equals the
binding of the object that projected it. Without that, anyone who may write a
`KafkaCluster` or `BackupDestination` could name another team's Secret beside an
endpoint they control and have Logweir present it there.

| Object | Credential | Bound to |
|---|---|---|
| `KafkaCluster` | password or client certificate | `v1:<UID>:sha256:<digest of bootstrap set, mode, username, tls and CA reference>` |
| `BackupDestination` `SecretKeys` grant | S3 key pair and session token | the destination's UID and its whole archive route |
| `RetentionPolicy` `enforcement.credentialSecretRef` | the delete key pair | the policy's UID, its destination's route and `spec.scope.prefix` |
| Inline archive `secretRef` | S3 key pair | the location: `v1:location:sha256:<hex>` over scheme, bucket, endpoint, region, addressing and `allowHttp`, never the prefix |

- Every Job carries the expectation as a literal
  (`LOGWEIR_{SOURCE,TARGET}_CREDENTIAL_BINDING_EXPECTED`,
  `LOGWEIR_ARCHIVE_CREDENTIAL_BINDING_EXPECTED`,
  `LOGWEIR_EVIDENCE_CREDENTIAL_BINDING_EXPECTED`,
  `LOGWEIR_EVIDENCE_READ_CREDENTIAL_BINDING_EXPECTED`) beside the Secret's key as
  an optional `secretKeyRef`. Every runner compares them before any client or
  store exists and refuses `CredentialBindingMismatch`: exit 3 for a run,
  `retention-refusal=CredentialBindingMismatch` for retention, a check code for a
  `Preflight`, the `Reachable` reason on a `KafkaCluster`.
- **The console**, for a connection or a destination, never names an existing
  Secret: it takes the credential once, creates a Secret owned by and bound to
  the object, and never reads it back. Only an inline archive's `credentialRef`
  (a schedule's, an ad-hoc backup's, a restore's without a destination, a
  catalog's or a preflight's `legacyArchive`) names an existing Secret; the
  workspace label rule and the location binding hold it.
- **With `kubectl`**, create the object, read its binding and write it into the
  Secret:

  ```
  kubectl --context <ctx> -n <ns> get kafkacluster <name> -o jsonpath='{.status.credentialBinding}'
  kubectl --context <ctx> -n <ns> create secret generic <name>-credential \
    --from-literal=password='<password>' --from-literal=logweir-binding='<that value>'
  ```

  `BackupDestination.status.credentialBinding` and
  `RetentionPolicy.status.credentialBinding` work the same way.
  `scripts/bind-credential.py --location` computes an inline archive's value.
- `logweir-binding` may hold several bindings separated by whitespace or commas.
  Add one only for a credential you mean to share, never for a Secret another
  object also names.
- A `Preflight` compares every Secret-backed grant a run would present, used or
  not, on the blocking row `destination.credentialBound`; it is `notReady`,
  `CredentialBindingMismatch`, naming each refused grant's field and Secret and
  `no binding` or `foreign binding`. The remedy never says to bind the refused
  Secret here: give this object its own Secret, and treat a Secret two objects
  name as an incident.
- A region not matching `^[a-z0-9-]{1,32}$` is refused `StorageRegionInvalid`
  everywhere, because without an endpoint the region shapes the host.

**Binding Secrets made before v1.** A credential Secret from an earlier release
has no binding, and every use of it is refused. Binding in a loop is the theft
the binding prevents, so bind one Secret to one object at a time:

1. **Suspend** every `BackupSchedule` whose destination, connection or inline
   archive uses a Secret.
2. Apply the CRDs, roll the controller, runner and console together, and wait for
   each object to publish its binding.
3. **Inventory, and stop on any Secret named twice:**

   ```
   kubectl --context <ctx> -n <ns> get kafkaclusters \
     -o custom-columns=CONNECTION:.metadata.name,SECRET:.spec.auth.secretRef.name,SERVERS:.spec.bootstrapServers
   ```

   A Secret two objects name is an incident, not a split: ask its owner which
   object is theirs, delete the other, and treat the credential as exposed if the
   other ever ran.
4. For each object, run the tool dry, have the credential's owner confirm the
   endpoint it prints, then apply:

   ```
   python3 scripts/bind-credential.py --context <ctx> --namespace <ns> \
     --kind BackupDestination --name primary --secret lwd-primary-archive-write
   python3 scripts/bind-credential.py --context <ctx> --namespace <ns> \
     --kind BackupDestination --name primary --secret lwd-primary-archive-write \
     --apply --confirm-endpoint '<the endpoint it printed>'
   ```

   `--kind` is `BackupDestination`, `RetentionPolicy` or `KafkaCluster`
   (`ProtectionPolicy` is refused). An inline archive is `--location s3://<bucket>
   --endpoint <url|aws> --region <region|none> --path-style true|false
   --allow-http true|false`. The tool refuses (exit 3, nothing written) a Secret
   another object names, one owned by or bound to another object, an object that
   does not name the Secret or has not published its binding, and a bad region.
5. **Resume the schedules.**

A destination created through the console before v1 also carries an
`api.logweir.dev/request-sha256` over its secret key: remove it (`kubectl
annotate backupdestination <name> api.logweir.dev/request-sha256-`) and rotate
the key if it could be guessed.

**What the binding does not close.** Secret `patch` is equivalent to Secret
`get` for every credential here: grant it only to principals you would let read
the credentials. The kubelet projects a foreign Secret's value into the refused
pod before the runner refuses; the pod has no token, sends nothing and exits. A
`WorkloadIdentity` grant names a ServiceAccount and is not bound. A
destination's CA reference is mutable and not bound.

## Restore

A `Restore` is one restore run, executed as one Job. **A drill is a `Restore`
with `spec.target.mode: scratch`**; there is no separate kind. A `Restore` only
ever writes a topic that does not exist, which it creates itself. Scratch mode
adds a marker topic, a cluster allowlist, a source-may-equal-target rule and
phase-9 teardown; `newTopic` mode writes prefixed names, or the original names
(below). The console's restore wizard writes the `Restore`, its plan and its
approval request; this section is what happens next.

### Admission: what is checked before any pod

The controller checks, in this order, before any `ConfigMap` or Job exists. An
unapproved plan creates nothing.

| # | Check | On failure |
|---|---|---|
| 0 | The object's name is at most 63 characters | `NameTooLong`, terminal |
| 0b | `spec.runnerResources`, when set, is one the controller applies | `ExecutionSpecInvalid`, terminal, naming every refused field; the `Approval` is not read |
| 0c | `spec.planBytes` parses as a restore plan | `PlanUnparseable`, terminal (`ExecutionSpecInvalid` when `spec` declares a coverage or the original names); the `Approval` is not read |
| — | `spec.authorization` (a standing authorization) | `StandingAuthorizationRefused`, terminal (withdrawn in v1, release-notes item 73) |
| 1 | `spec.approvalRef` names something | `ApprovalNotReceived`, terminal |
| 2 | That `Approval` exists and is `Verified=True` | `ApprovalNotVerified`: **held**, `phase: Pending`, `Admitted=False`, retried every 30 s |
| 3 | `sha256(spec.planBytes)` equals the `plan_hash` inside the approval's own bytes | `PlanHashMismatch`, terminal, naming both hashes |
| 4 | `spec.target.clusterRef` resolves to a `KafkaCluster` with `status.reachable: true` | `ClusterNotReachable`, terminal |
| 5 | Destination-backed: both destinations resolve and are `Valid=True` for their current generation | **held** (`Admitted=False`), retried every 30 s |
| 6 | The plan's `source.storage` is the source destination's archive location, exact on all six fields | `PlanDestinationMismatch`, terminal |
| 7 | The plan's `evidence` is the evidence destination's evidence location | `PlanEvidenceDestinationMismatch`, terminal |
| 8 | Both grants resolve and fit one pod | `DestinationRoleNotConfigured` / `ExecutionContextConflict`, terminal |
| — | The approved plan's `target` names the connection `clusterRef` resolves to | `ConnectionPlanMismatch`, terminal |

A mode-v2 namespace adds the approval-policy checks at admission
(`ApprovalPolicyMismatch`, `AuthorizationExpired`); see [Approvals](#approvals).
A manual restore then takes a slot in the namespace's manual-restore pool, or
waits `Queued`.

```bash
kubectl --context docker-desktop get restore r1 \
  -o jsonpath='{.status.phase}{"  "}{.status.conditions[?(@.type=="Admitted")].reason}'
# Pending  ApprovalNotVerified
```

The wizard mints both names before creating either object, and an approver may
take an afternoon, so a `Restore` naming an `Approval` that does not exist yet
holds, and is released the moment the `Approval` verifies. An `Approval`
reconciled before its `Restore` exists reports `ReferentNotFound`, and is retried.

- A `Restore` names two destinations or neither: `sourceDestinationRef` (read
  with `archiveRead`) and `evidenceDestinationRef` (written with
  `evidenceWrite`). Half a pair is refused by CEL and again by the controller.
- The runner reads its location from the **plan**, which the approver signed, so
  checks 6 and 7 are what stop a destination's credential being presented at a
  location nobody approved. A destination edit never invalidates an approval:
  its location fields are immutable.
- **The hash is recomputed at Job creation and never read from a status.**
  `spec.approvalBytes` is the UTF-8 document text, verbatim, never base64.

### What the Job carries

`spec.planBytes` goes into `ConfigMap` `<restore>-plan` as the single key
`restore.yaml`, verbatim: no parse, no re-serialise, no trim, because
`plan_hash` binds those exact bytes. Its grammar is the runner's own
(`examples/restore.yaml`).

```bash
kubectl --context docker-desktop get cm r1-plan -o jsonpath='{.data.restore\.yaml}' \
  | sha256sum
kubectl --context docker-desktop get restore r1 -o jsonpath='{.spec.planBytes}' \
  | sha256sum
# the two digests are equal, and both equal the plan_hash the approval names
```

The Job has the `Backup` Job's shape (one `runner` container, `backoffLimit: 0`,
no token, TTL only after the status) and these volumes:

| Volume | From | At | Holds |
|---|---|---|---|
| `approval` | immutable `ConfigMap` `<restore>-approval-bundle` | `/approval` | `approval.json`, `approval.sig`, `approver.pub.pem`, `allowed-clusters.json`; under v2 also `approval-policy.json` and `confirmation.pub.pem`; for a point-bound plan `evidence-keys.json` |
| `signing` | Secret `logweir-signing-key`, `0440` | `/signing` | The runner's signing key, readable because `fsGroup: 65532` is set |
| `plan` | `ConfigMap` `<restore>-plan` | `/plan` | `spec.planBytes`, verbatim |
| `work` | `emptyDir` | `/work` | The scorecard and offset report, on a read-only root filesystem |

- The Job template pins the SHA-256 of the plan and every bundle member, and the
  Restore and Approval identities, and passes `--execution-contract-version 2`
  with `LOGWEIR_EXECUTION_CONTRACT_VERSION=2`. The runner captures the projected
  bytes once and checks every digest, the approval signature and the plan hash
  before it builds any client.
- Archive credentials come as `secretKeyRef` env from the source destination's
  `archiveRead` grant, or from `spec.sourceArchive.secretRef` for an inline
  archive. A SCRAM target gets `LOGWEIR_TARGET_PASSWORD` from its `KafkaCluster`'s
  `auth.secretRef` (`passwordKey`, default `password`); a `auth.tlsCa` target gets
  the CA file and `LOGWEIR_TARGET_TLS_CA_FILE`. Both destinations' CA bundles are
  copied into the plan `ConfigMap` (`LOGWEIR_ARCHIVE_CA_FILE`,
  `LOGWEIR_EVIDENCE_CA_FILE`).
- **The runner validates credentials; the controller cannot.** It holds no `get`
  on Secrets. A password that cannot be rendered is exit 3,
  `refusal-reason=CredentialNotRenderable`.

### The runner's requests and limits: `spec.runnerResources`

`spec.runnerResources` reaches the `runner` container's `resources` exactly as
written. Absent, the container states none and the namespace's `LimitRange`
applies. The console never sets it and does not show it; set and read it with
`kubectl`. It is not part of the signed plan. A value the controller will not
apply is refused, never clamped (`ExecutionSpecInvalid`, check 0b):

| Rule | Refused, for example |
|---|---|
| A Kubernetes quantity | `abc`; `1K` (the decimal kilo is `k`) |
| Memory in whole bytes, CPU in whole millicores | `memory: 100m`; `cpu: 100u` |
| At most **4** CPUs and **8Gi** memory, requests included | `limits.memory: 16Gi`; `requests.cpu: "8"` |
| A limit is never zero; a memory limit is at least **32Mi** | `limits.cpu: "0"`; `limits.memory: "512"` |
| A request is at most its limit | `requests.memory: 4Gi` beside `limits.memory: 2Gi` |

```bash
kubectl --context "$LOGWEIR_CONTEXT" -n <namespace> get job <restore-name> \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="runner")].resources}'
```

`{}` means no requests and no limits. A namespace `ResourceQuota` that requires
limits, with no `LimitRange` default, refuses every pod without them;
`spec.runnerResources` is how a `Restore` runs there. A pod refused at creation
is reported, in the admission's own words, on every kind
([reference.md](reference.md#a-pod-refused-at-creation)).

### Coverage: sampled or complete

`spec.coverage` is `sampled` (absent) or `complete`, and
`spec.completeMaxRecords` bounds a complete check. They declare what the plan's
`sample.coverage` and `sample.complete_max_records` say; a declaration the plan
does not match is `ExecutionSpecInvalid` before any Job. A plan written with the
CLI needs `spec.coverage: complete` on the `Restore` too.

- Complete reads every archived segment, decodes every record, reads every
  restored record back and compares each by source offset: about a minute per
  GiB of one-KiB records, against about five seconds sampled. Size
  `deadlineSeconds` for it.
- **`covered: false` is never a pass.** A complete check stopped by the bound, or
  over an archive it could not compare, signs
  `integrity.verification.complete.covered: false`, outcome `fail-integrity`,
  exit 2. The `Verified` reason is `CompleteNotCovered`, and the runner's metrics
  carry `logweir_drill_integrity_complete_covered 0`. Alert on either.
- The status copies `integrity.coverage` (absent means not recorded, read as
  sampled), `integrity.complete` (`covered`, `incompleteReason`, `maxRecords`,
  archive counts, `replay` totals, up to 256 partition rows),
  `integrity.unsampledTopics`, and `integrity.positionsMapping` (`bound`,
  `groups`, `omitted`): whether the signed scorecard binds a consumer positions
  mapping, which a switchover requires.
- **A narrowed restore says so.** A partition subset or a window from a stated
  start is copied to `integrity.selection` with `scope: partial` (the
  `SELECTION` column), `windowStartMs`, `windowEndMs`, `narrowedTopics`,
  `partitions` and `engineRuns`. Absent means an unnarrowed restore.

```bash
kubectl --context docker-desktop get restore r1 \
  -o jsonpath='{.spec.coverage}{"  "}{.status.integrity.coverage}{"  "}{.status.integrity.complete.covered}'
# complete  complete  false
```

### Restoring under the original topic names

<a id="restoring-under-the-original-topic-names-prod-151"></a>

An ordinary restore writes a new, prefixed topic. An original-name restore
writes `orders` itself: the recovery of a deleted topic, or of a lost cluster
onto a replacement. It writes only a name that does not exist, which it creates
exclusively; Kafka gives it a new topic id. Logweir never writes into a live
topic (Never #1 in [stability.md](stability.md)).

```yaml
target:
  mode: newTopic                 # required
  topic_naming:
    prefix: ""                   # the identity mapping; an older runner refuses it
    original_name:               # the explicit opt-in
      owners: []                 # the approver's statement: no declarative owner of any restored name
      # owner_path: true         # restore although an owner is found
  topic_mapping_prefix: drill-   # still required: the LogAppendTime probe is created under it
sample:
  coverage: complete             # required
```

- The `Restore` declares `spec.target.topicNaming: {prefix: "", originalName:
  true}` in `newTopic` mode with `spec.coverage: complete` (CEL refuses it
  elsewhere). Whole topics only: a plan with `restore.partitions` is refused
  `OriginalNameNeedsWholeTopics`.
- **Its own approval subject**, `originalName` (v1 `approval_subject`, from
  `logweir drill approve --approval-subject original-name`; v2
  `approvalSubject`, authorization document format 2.1.0). An ordinary approval
  never authorises it and it authorises nothing else: `ApprovalSubjectMismatch`
  at admission, exit 3 at the runner.
- **Under `confirm`**, the console makes the requester re-type every original
  topic name, signs them as `originalNameConfirmation.typedTopics`, and the API
  refuses missing or wrong names (`typed_topics_required`,
  `typed_topics_mismatch`). Under strict the second person is still needed.
- **What the runner proves before writing** (exit 3, `GuardRefused`, the message
  opening with the condition's name): `newTopic` with an empty prefix
  (`OriginalNameNotNewTopic`, `OriginalNamePrefixNotEmpty`); complete coverage
  (`OriginalNameNeedsCompleteCoverage`); whole topics; every name absent on the
  target; the target is not the source cluster (by the bound point's verified
  receipt) or every broker reports `auto.create.topics.enable=false`
  (`OriginalNameAutoCreateEnabled`, `OriginalNameAutoCreateUnknown`); owners
  were looked for (`OriginalNameOwnerNotChecked`, `OriginalNameOwnerPresent`,
  `OriginalNameOwnersInvalid`, `OriginalNameOwnerUnreadable`); the
  `LogAppendTime` probe name is usable (`OriginalNameProbeUnusable`).
- **Declarative owners** (a Strimzi `KafkaTopic`, GitOps, Terraform) recreate a
  deleted name and revert the restored topic's settings. The runner looks in the
  plan's `original_name.owners` (an empty list is the approver's signed
  statement), in `--kafka-topic-resources <file>` (`kubectl get kafkatopics -A -o
  yaml`; CLI only), and in the owners the bound point's receipt recorded; it
  refuses when it looked in neither of the first two. The controller lists
  `KafkaTopic`s for a `Backup` only
  ([Strimzi owners](#strimzi-owners-of-a-backups-topics)), never for a
  restore. `owner_path: true` restores anyway: pause the owner first
  (`strimzi.io/pause-reconciliation: "true"`, suspend GitOps sync) and make its
  desired state keep the restored `retention.ms`.
- **Stop every producer of a restored name first.** A producer still writing is
  detected, not prevented: complete verification counts its records
  `unexpected`, and the run signs `fail-integrity` (exit 2).
- **Creation is exclusive, and nothing is ever deleted under an original name.**
  A name that appears before the create is exit 1, `failure-reason=TargetTopicAppeared`.
  A creation step that stops leaves every topic it created, empty, and names
  three lists on `status.targetTopicsAppeared`: `appeared` (someone else
  created it), `left` (this run created it; remove it yourself once nothing
  writes to it) and `unconfirmed` (asked for, no definite answer; check what it
  holds before removing it). Each has a count; a list carries at most 100 names.
  `status.exitReason` is `TargetTopicAppeared` or `CreatedTopicsLeft`;
  `status.newTopics` is exactly `left`. After any such failure, list the plan's
  target names on the cluster yourself, delete what you checked
  (`kafka-topics.sh --delete --topic <name>`), and create a new `Restore`.
- The scorecard (format 1.8.0) carries `target.original_name`, which both
  verifiers check and print as two `original name:` lines.
- A `Preflight` accepts the identity mapping it asked for but does not evaluate
  the cluster and owner conditions; phase 0 does.

### The target topics' configuration

A plan with `target.topic_configuration`
([the plan field](formats/drill-spec.md#targettopic_configuration-prod-052))
creates each target topic from the bound point's configuration model and,
with `transition: afterVerification`, applies the source's compaction,
retention and timestamp settings in phase 9 after a passing verdict. The
`Restore` itself declares nothing new: the block is in `planBytes`, and the
approval scope shows the choice and every owner it states.

- **Preview first.** A `Preflight` `operation: Restore` writes one details line
  per topic (`GET …/preflights/{id}/details`, `check: target.topicConfiguration`):
  the replication factor and why, the during-restore, at-creation,
  after-verification and never-applied sets, each inherited value against the
  target's own default, the owner route, the target's `validate_only` verdicts,
  and what the transition's retention deletes. Or the refusal phase 0 would
  make.
- **`status.topicConfiguration`** carries each topic's replication factor with
  its reason, its overrides before (Logweir's, with the at-creation set) and
  after (the whole desired set), and the transition's outcome: `applied`,
  `partial` or `notRun: <reason>`; `applied`, `failed` (each with its whole
  desired set: the remaining step, which you apply; Logweir never retries),
  `exported` and `desiredStateKey`. It is read off the runner's log; the signed
  scorecard's `target.topic_configuration` and the phase-9 attestation
  (`logweir/drills/<run_id>.teardown.json`) are the evidence.
- **The restore principal** needs `DescribeConfigs` and `AlterConfigs` on the
  restored topics, and `CreateTopics` with `validate_only`. A denied
  `AlterConfigs` is a `failed` topic, found by reading the overrides back.
- **Owned topics** (a Strimzi `KafkaTopic` recorded at backup, or `owners` in
  the plan) are created with Logweir's settings only and never altered; apply
  the exported `KafkaTopic` YAML (`desiredStateKey`) with your owner.

### Exit 3 and the evidence keys

`TargetTopicConfigRefused`, `CredentialNotRenderable`,
`PointInTimeByProducerTime` (a point in time over a `LogAppendTime` topic without
`restore.time_basis: producerTime`, [the plan field](formats/drill-spec.md#restoretime_basis-fx-8))
`TransactionMarkersInArchive` (without `restore.allow_transaction_markers:
true`) and `PointInTimeSelectionIncomplete` (a window that selects records held
out of timestamp order in a segment the engine skips,
[the limitation](stability.md#out-of-order-timestamps-inside-a-segment))
are exit 3 told apart only by the `refusal-reason=` line. The point-binding
refusals (`PointBindingMismatch`, `PointUntrusted`, `PointBindingSetMismatch`)
read `refusal-reason=GuardRefused`; their name opens the message. A log with no
such line is `GuardRefusedUnknownReason`. See
[Troubleshooting](#why-a-guard-refused-the-message).

At exit 0, and at exit 2 (the signed failure), the runner prints, read by key
name:

```
scorecard-key=logweir/drills/<run_id>.json
sidecar-key=logweir/drills/<run_id>.sig
offset-report-key=logweir/drills/<run_id>.offsets.json
```

The third only when the engine wrote an offset report.
`EvidenceRecorded=False/EvidenceKeysUnreadable` only when a mandatory key is
missing at exit 0. An exit-2 run's scorecard is fetched and verified like a pass,
so `status.outcome` (`fail-objective`, `fail-integrity`, `preflight-failed`) is
written; `Verified` is never `True` over a non-zero `exitCode`.

### What the status carries

`exitCode` and the condition come from the pod. `outcome`, `lastPhaseCompleted`,
`objectives` (`rtoSeconds`, `rpoSeconds`, `passRate`, `met`), `integrity` and
`measured` are copied verbatim by JSON pointer out of the signed scorecard; if
the scorecard was not read, each is omitted (absent means nobody looked).
`newTopics` and `oldTopics` come from the plan's prefix rule. `topicPreflight`
(`timestampType`, `retentionMs`, `timestampBound`) is copied from the runner's
`topic-preflight=` line, printed at exit 0 only; absent on every other run. A
field the target did not report is omitted.
`status.completion` (`newTopics`, `recordsExpected`,
`recordsRestored`, `recordsSampled`, `recordsSampledMatching`, `integrityLevel`,
`sampleWindow`) is written only for a run whose verdict is `Valid` (basis
`Current` or `Historical`), `outcome: pass` and `exitCode: 0`.
`recordsRestored` counts records read back in the sampled window, not the whole
restore.

`status.reason` is the reason of the current condition, verbatim, and the
`REASON` column reads it; `status.exitReason` is what the run exited with:

```bash
kubectl --context docker-desktop get restores
# NAME  MODE     PHASE    EXIT  REASON                OUTCOME ...
# r1    scratch  Pending        ApprovalNotVerified
# r2    scratch  Failed   3     GuardRefused
```

**A green `Restore`** reads both:

```bash
kubectl --context docker-desktop get restore r1 \
  -o jsonpath='{.status.evidence.verification.result}{"  "}{.status.outcome}'
# Valid  pass
```

`Valid` alone says the document is authentic; `pass` alone says the drill passed
by a document nobody verified. The `SIGNED` and `OUTCOME` columns show both.

### Cancel, and an interrupted restore

Nothing is ever resumed. A restore that stops part-way says so, lists what it
left, and holds its recovery point until you retry or clean up (PROD-07.2).

**Cancel** (`POST /api/v1/workspaces/<ws>/restores/<name>/cancel`, or the
annotation `logweir.dev/cancel-requested-by: <you>`) is allowed to whoever may
create restores in the workspace:

| When | What happens |
|---|---|
| Before its Job exists (`Pending`, `Queued`) | `Failed`, reason `Cancelled`; nothing ran |
| While it runs | The controller sets `spec.suspend: true` on the run Job. The runner gets SIGTERM, forwards it to the engine, SIGKILLs the engine after 10 s, signs nothing and exits 1 (`failure-reason=Cancelled`). The `Restore` stays `Running`, reason `Stopping`, until no pod of the Job is left; a pod on a lost node keeps it there (force-delete it) |
| After the run signed | Nothing changes: the scorecard decides |

The run Job's pod has a 30 s grace. On Linux the engine also gets
`PR_SET_PDEATHSIG(SIGKILL)`, so it never outlives a killed runner.

**`Interrupted`.** A run that ended without a signed scorecard *after* it
created its target topics is `phase: Interrupted`, with `status.interruption.cause`
`Cancelled`, `RunnerStopped` (a deleted or evicted pod, a deadline, a runner OOMKilled or crashed) or
`RunFailed`. Before its engine starts, every run writes a create-only targets
record, `logweir/drills/<run_id>.targets.json` (run id, plan hash, cluster ID,
and each created topic's name, topic ID and partitions), signed by the run's
signing key (`<run_id>.targets.sig`). A record that is missing its signature, or
whose signature does not verify, is refused: nothing is verified and nothing is
deleted. A run that ended before its creation step is `Failed`, as before.

The controller then starts `logweir-reconcile-<uid>-<n>`, a copy of the run's pod
running `logweir restore reconcile --run-id <the run>`. It keeps the recorded
topics that the plan maps and that are still on the recorded cluster with their
recorded topic IDs (a name deleted and created again is left out and named), waits until their end
offsets hold still for 10 s (at most 5 minutes, else `TargetStillGrowing`), and
verifies them against the archive with the complete lane, restoring nothing. It
signs an ordinary scorecard for its own run id: `fail-integrity` with
per-partition `expected`, `restored`, `matching`, `missing`, `duplicates`; the
kept topics in `target.creation`; and a coverage note naming the interrupted run.

| The reconcile found | The `Restore` |
|---|---|
| Every recorded topic kept and every partition exact | `Succeeded`, reason `ReconciledComplete`, without a second restore |
| Anything else, including a recorded topic left out (`integrity.result: partial` names it) | Stays `Interrupted`, `interruption.verification: Done`; the counts are on `status.integrity` and the evidence is the reconcile's scorecard |
| The run's own scorecard after all (it signed just before it stopped) | What that scorecard says |
| No targets record, or none of its topics is still the run's | `Failed`, with the reason |
| A failure (exit 1, no exit code) | Tried again, at most three times, five minutes apart; then `verification: Failed`. The point stays held and Clean up is not offered |

The reconcile reads the targets record from the evidence location with the run's
`archiveRead` grant, which must therefore read `logweir/drills/*` there
([install.md §3.11](install.md#311-object-store-permissions-per-destination-role)).

**Clean up** (`POST …/restores/<name>/cleanup`, or
`logweir.dev/cleanup-requested-by`), only on an `Interrupted` restore whose
reconcile signed, and with no second approval: the controller runs
`logweir-cleanup-<uid>-<n>`, wired as a clone's cleanup (the evidence
destination's `evidenceRead` grant reads the scorecard), running `logweir restore
cleanup --run-id <the reconcile's run>`. It deletes only the topics that scorecard
lists, each only while its topic ID is the recorded one, through a deleter scoped
to the plan's mapped target names, and signs what it did. What it removed and
left is on `status.teardown`; `interruption.cleanup.phase: Removed` releases the
recovery point. A topic someone recreated, or one under its original name
(an original-name restore), is left and named: delete it yourself once checked.

**Retry** is a new `Restore` into fresh names, with its own approval; phase 0
refuses any execution into the old partial targets.

```bash
kubectl --context docker-desktop get restore r1 \
  -o jsonpath='{.status.phase}{"  "}{.status.interruption.cause}{"  "}{.status.interruption.verification}'
# Interrupted  Cancelled  Done
```

### Safe clones: a scratch restore kept for a declared time

A clone (PROD-11.1a) is a `scratch` restore whose plan says how long to keep
what it restored:

```yaml
target:
  mode: scratch
  topic_mapping_prefix: "clone-"
  teardown: {ttl_seconds: 86400}   # 300 (five minutes) to 2592000 (thirty days)
```

Scratch mode's checks hold unchanged: the target cluster is in the
`TrustPolicy`'s `allowedTargetClusterIds`, it is not the source, and the marker
topic exists. The map form outside scratch mode is refused
`CloneTtlNeedsScratch`, out of bounds `CloneTtlOutOfRange`, both before any Job.
A runner from before this feature cannot parse the map form and restores
nothing. Restored records always keep `x-original-offset` and
`x-original-timestamp`; the approval scope shows `teardownAfterSeconds` and
`lineageHeaders: kept`.

The `Restore` carries the finalizer `logweir.dev/clone-cleanup` from admission,
before its run Job exists. `status.clone` says where the clone is:

| `phase` | Meaning |
|---|---|
| `Active` | The run passed; its topics are kept until `expiresAt` (the success the controller recorded plus `ttlSeconds`). The cleanup Job exists, suspended. |
| `Removing` | At `expiresAt`, or at once when the `Restore` is deleted: the cleanup Job (`logweir-clone-cleanup-<uid>-<attempt>`) runs `logweir restore cleanup`. |
| `Removed` | It deleted what the run's signed scorecard records (`target.creation`), on the cluster the scorecard records, each topic only while its ID is the recorded one. `status.teardown` lists `deleted`, the topics it left (`failed`, with why) and the signed attestation (`logweir/drills/<run_id>.cleanup.json`). The finalizer is released. |
| `NotKept` | The run did not pass and the runner exited with one of its own codes (1 to 4): its phase 9, or the teardown of a run that failed after creating, removed what it created at once and named anything it left in `status.teardown.failed`; a stopped creation step deletes nothing and names what it left in `status.targetTopicsAppeared`. A run refused before any Job created nothing. The finalizer is released. |
| `RemovalFailed` | The cleanup refused (exit 3, for example `CloneTargetClusterChanged`: the target answers with another cluster ID), failed three times five minutes apart, or the controller cannot settle the clone (a plan it cannot read, a recorded run Job gone before its outcome, a run that ended with no exit code or was killed by a signal, 137 or 143, so its teardown never ran). `status.clone.reason` says which. The finalizer stays. |

A topic recreated by someone else since the run is never deleted: it is left
`CloneTargetReplaced` in `status.teardown.failed`, and the clone still reaches
`Removed`. One window remains: the cleanup reads each topic's ID and then
deletes by name, because librdkafka has no delete by topic ID, so a topic
deleted and created again under a recorded name between that read and the
delete request would be deleted. The cleanup verifies the run's scorecard with
the installation's current signing key (and, for a plan bound to a recovery
point, the evidence keyring); a signing key rotated during a clone's lifetime
makes it refuse, `RemovalFailed`, and nothing is deleted.

The cleanup Job reads the run's scorecard with the evidence destination's
`evidenceRead` grant and writes its attestation with `evidenceWrite`
([the grants](#the-grants-and-the-object-storage-actions-each-one-needs)); a
scorecard the store will not hand over is `EvidenceUnreadable`, retried like
any failed attempt, and `status.clone.reason` names the key, the grant and the
store's answer. The reason points at `status.teardown.failed` only when the
last attempt left topics there; one that deleted nothing says so.

**After an upgrade.** A cleanup Job a controller from before this release
built reads with the run's write grant and runs the older runner: it is never
started. A suspended one is replaced by the next attempt, built with this
release's grants and runner image, at the clone's expiry. A clone already in
`RemovalFailed` whose last cleanup Job is such a Job is re-armed,
automatically, the first time this controller reconciles it: `status.clone`
goes to `Removing` on the next attempt number and its old reason is cleared.
The re-armed attempt counts against the same budget of three: if it fails, it
is retried as any attempt is while fewer than three have run. So a clone the
older build held at attempt 1 gets up to two more attempts, and one held at
attempt 3 gets exactly one. Each such Job names its grant
(`--evidence-read-grant`), so when the last one fails too, or one is refused,
the clone holds as any `RemovalFailed` does.

**On `RemovalFailed`**, check the target for topics with the clone's
prefix, delete any the run created (`status.teardown.failed` and the scorecard's
`target.creation` name them), then remove the finalizer:

```bash
kubectl --context docker-desktop -n <ns> patch restore <name> --type=json \
  -p '[{"op":"remove","path":"/metadata/finalizers"}]'
```

The controller needs `patch` on `restores` for the finalizer (the chart grants
it). **Rollback:** a controller from before this feature ignores the finalizer,
so deleting a clone's `Restore` waits until the finalizer is removed by hand as
above; delete the clone's topics first.

### The recovery catalog

A `RecoveryCatalog` indexes one destination's durable catalog,
`logweir/catalog/v1/` in object storage, which the backup runner writes beside
every receipt ([formats/catalog-point.md](formats/catalog-point.md)). **The
archive is the truth.** The Kubernetes view is a bounded, expiring window onto
it, and a restore re-verifies its point at execution.

```bash
kubectl --context docker-desktop get recoverycatalog -n team-a
# NAME     DESTINATION  POINTS  AVAILABLE  SYNCED  TRUNCATED  AGE
# primary  archive      5312    5287       2m      true       6h
```

**A sync** is a `check run` Job of kind `catalogSync`, with the destination's
`archiveRead` credential (see [the grants](#the-grants-and-the-object-storage-actions-each-one-needs)).
It runs every `spec.sync.intervalSeconds` (`0` for manual only, else at least
300), or at once when `spec.syncRequest`, the only mutable field, changes; the
token acted on is `status.observedSyncRequest`. A sync that finished inside the
current interval slot serves it. An `Index` sync walks the day shards of
`logweir/catalog/v1/log/` newest first, down to the archive's oldest day (at most
3,660 shards). A `Full` rescan pages `logweir/catalog/v1/points/` and resumes
after `status.cursor.rescanStartAfter`.

| Bound | Value |
|---|---|
| `spec.sync.viewLimit` | 100–5000, default 2000: how many newest points are materialised. The rest are counted, and `status.truncated` says the view is a window. `truncated` is also set for entries that did not fit the view's pages or one page, which a larger `viewLimit` does not cure; the `Synced` message names each cause. The product API publishes an absent `truncated` as `true`. |
| `spec.sync.maxObjectsPerRun` | 1000–1000000, default 100000: the object budget of one sync Job; a walk that does not finish persists its cursor (`ScanIncomplete`, `catalogStoppedFor: objectBudget`) |
| `status.pages[]` | at most 8 immutable `ConfigMap`s, entries one JSON per line under `entries.jsonl`, each with its `sha256` |
| `status.indexConfigMap` | one fence-pointer `ConfigMap`: per page, the point-id and recovery-point ranges |
| `status.histogram` | at most 400 days, over the whole walk |
| `status.signers[]` | at most 16, untrusted keys first |

The pages, fence pointer and plan are owned by the sync Job, whose
`ttlSecondsAfterFinished` is `max(3 × intervalSeconds, 3600)`. At most 120
`ConfigMap`s and 12 Jobs live per catalog (30 and 3 at the hourly default). If
syncing stops for longer than the TTL the object reports `Stale`, then
`Ready=False/ViewExpired`. A failed sync keeps the previous view. Nothing here
deletes from object storage, and `logweir catalog list` still reads the durable
catalog.

**Conditions.** `Ready` (a usable view exists), `Synced` (the last walk:
`Succeeded`, `PartialScan` when some points could not be read, `ScanIncomplete`
when a budget stopped the walk, or a check code), `Stale` (older than two
intervals) and `TrustAvailable`. `Synced=Unknown/SyncInProgress` means a walk is
running while the previous view stays usable.

**Two axes per point.** `selectable` is their conjunction: a point is offered for
an ordinary restore only when it is `Available` and `Verified` or
`VerifiedHistorical`.

| `availability` | Meaning |
|---|---|
| `Available` | Receipt, sidecar and manifest readable; the manifest digest equals the receipt's; for a pinned version, the current version is the pin, or this bucket does not hold the pin and the digest decided (the `remedy` says so) |
| `Missing` | A definite `NotFound` |
| `Unreadable` | Any other storage error (403, timeout, a failed read of a pinned version), a document over its read bound, or bytes that are not the document its key names. "Could not tell", never "is not there". |
| `Deleted` | A completed retention tombstone exists (this build's sync does not produce it; a point retention removed reads `Missing`) |
| `Conflict` | Two records disagree, a record contradicts its receipt, or the set was written again in this bucket after the point was signed |
| `UnsupportedFormat` | The record's major version is above this build's |
| `Partial` | A sampled segment is missing (not produced: segment sampling does not exist) |

| `verification` | Meaning |
|---|---|
| `Verified` | The receipt's DSSE verifies under a key this installation accepts |
| `VerifiedHistorical` | The same, under a retired or expired key, for evidence signed while it was valid |
| `UntrustedSigner` | Verifies under a key this installation does not list |
| `Revoked` | The key was revoked for compromise |
| `Invalid` | The signature does not verify, a digest does not match, or the claimed signing time is outside the key's window |
| `NoEvidence` | A manifest with no receipt |
| `NotAttempted` | Nothing could be fetched, or there is no trust material (`TrustAvailable=False`) |

- Across a point's locations, availability merges best-of and the signature
  worst-of; every degraded copy is named in `remedy`. When the signing bucket
  says `Conflict` and a copy says `Available`, believe the `Conflict`.
- Trust is the namespace's: the `TrustPolicy` naming it, else the `default:
  true` policy, else `legacy-roster-v1` from `TrustRoster/default`. Only
  `EvidenceSigning` keys count. Two policies claiming the namespace give
  `TrustAvailable=False/TrustPolicyConflict` and every point `NotAttempted`. A
  published view keeps its verdicts until the next sync, so set
  `spec.syncRequest` after a trust change.
- `status.counts` does not sum to `total`: `unverified` folds `NotAttempted` and
  `NoEvidence`; `Partial`, `Revoked` and `VerifiedHistorical` are counted in the
  `Synced` message. `catalog-counts` carries `unreadableOverReadCap` and
  `unreadableMalformed` when non-zero.
- A point whose record gave no facts is listed by its point id alone and is
  never selectable. A walk that never started relays nothing; the controller
  reads that as `ResultUnreadable` and keeps the previous view.
- A record is read for keys only where a receipt can be: its receipt key must
  be `logweir/backups/<set>/<run>.receipt.json` (each id one plain path
  segment) and its sidecar key the `.receipt.sig` beside it. Any other record
  is `Unreadable` (`unreadableMalformed`) and neither key is read (FX-36).
- `deepCheck: ManifestDigest` is the default. `deepCheck: None` makes a point
  `Available` once its record and receipt read. `deepCheck: SegmentSample` is
  honoured as `ManifestDigest` (`catalogSegmentSample: notImplemented`).
- **One catalog per destination.** A later catalog over the same
  destination reports `Ready=False/DuplicateCatalog` and runs no sync; a
  `RetentionPolicy` or `ProtectionPolicy` pointed at it fails closed. Point them at
  the elder (a `RetentionPolicy.catalogRef` is immutable, so re-create it), or
  delete the elder with `kubectl`; the next one takes over within a minute.
- `spec.legacyArchive` is admitted and not synced:
  `Ready=False/LegacyArchiveUnsupported`. Use a `BackupDestination` with an
  `archiveRead` grant.

**Points written before the catalog existed** (v0.1.5 and earlier) have a
receipt and no record, so a catalog neither counts nor offers them. Their
`Backup` objects, where they exist, restore as before. To add them, run the
backfill once with a credential that may write under `logweir/catalog/v1/`, then
set `spec.syncRequest`:

```bash
logweir catalog sync --url s3://<bucket> [--endpoint <url> --region <r> --path-style --allow-http] \
  --signing-key <record-signing-key.pem> --public-key <receipt-key.pub.pem> [--public-key …]
```

It writes a signed record, create-only, for every receipt that verifies under a
`--public-key`. It is idempotent, resumable with `--since <catalog-next>`,
bounded by `--max`, and deletes nothing.

### Disaster restore: an archive and no `Backup` object

A cluster that lost every `Backup` object still has every point in object
storage. This path reads no `Backup`, `BackupSchedule` or source `KafkaCluster`.

1. **A read-only credential.** In the console's *Destinations* page, enter the
   archive's key pair once for `archiveRead`; the console creates a Secret bound
   to the destination. With `kubectl`, create the `BackupDestination` naming a
   Secret (`access.archiveRead: {mode: SecretKeys, secret: {name}}`), then the
   Secret with the key pair and the destination's `status.credentialBinding`
   under `logweir-binding` ([credential binding](#credential-binding)).
2. **Connect the archive.** Create a `RecoveryCatalog` with
   `spec.destinationRef` and `sync.mode: Full` (console *Catalog* page, *Connect
   an existing archive*, or `POST .../catalogs`).
3. **Trust the signer explicitly.** A point signed by a key the namespace's
   trust does not list is `UntrustedSigner` and never offered. Compare the key id
   out of band ([keys.md](keys.md)), add the key to the `TrustPolicy` with
   `kubectl apply`, then set `spec.syncRequest`.
4. **Choose a point.** The wizard (`#/<ns>/restores/new?catalog=<name>&point=<pointId>`)
   re-reads the row from the API and offers it only when it is `selectable`, the
   verdict join is complete and the row names its set id, receipt key and both
   digests. A catalog synced by a runner up to v0.2.0-rc.1 redacted scheduled
   runs' set ids; upgrade the runner and sync again. The view lists each topic's
   partitions and replication factor, and its schema dependency: the catalog
   page names schema-dependent topics under "Registry not captured: applications
   may not read these records after restore."
5. **The plan is bound to the point**: `source.backup: <backupId>` and
   `source.point {point_id, receipt_key, receipt_sha256, manifest_sha256}`. The
   point in time defaults to `coveredTo − 1 ms` and must be in
   `[coveredFrom + 1 ms, coveredTo − 1 ms]`.
6. **Readiness.** A `Preflight` with `spec.request.restore.catalogPointRef
   {catalogRef, pointId}` re-reads the row and the archive, as the runner will.
7. **Approve and run.** Before any client exists the runner re-reads the
   receipt, re-derives the point id, compares both digests, verifies the
   signature against the evidence keyring in the approval bundle
   (`evidence-keys.json`) and reads the manifest back.
   - A receipt key that is not `logweir/backups/<source.backup>/<run id>.receipt.json`
     is exit 3 `PointBindingMismatch` with nothing read. An absent receipt,
     other bytes or one over the 64 MiB cap are one answer, exit 3
     `PointBindingMismatch` (FX-36).
   - A digest mismatch, or a pinned version this bucket holds that is no longer
     current, is exit 3 `PointBindingMismatch`. A pinned version this bucket
     does not hold is logged `PointPinUnchecked` and the digest decides.
   - A pinned version that cannot be read (a 403, an outage) is exit 1.
   - An unsigned receipt or a signer the trust refuses is exit 3
     `PointUntrusted`.
   - A plan whose `source.backup` is not the receipt's set, or whose described
     set differs from the bound one, is exit 3 `PointBindingSetMismatch`; the
     preflight calls the same plan `CatalogPointBindingMismatch`.

In every refusal no data moves and no target topic is created.

- **A run the controller could not verify** (verdict `NotAttempted`) has no
  `status.windowCovered`. The console offers it from its catalog row only when
  exactly one row answers its receipt digest, that row is offerable, and the
  catalog reads the destination the run froze. Never for `Invalid`, `Untrusted`
  or `Pending`.
- **A restore started from a `Backup`** is bound the same way when a catalog over
  its destination lists its point. Otherwise the plan carries `source.backup`
  only, the wizard says it is not bound, and the scorecard reports each topic's
  timestamp type NOT RECORDED.
- **Upgrade the controller and runner images together.** A runner at this
  version refuses a point-bound plan from an older controller (`PointUntrusted`,
  no keyring); an older runner does not know `--evidence-keys` and exits 1. A
  standalone `logweir restore run` of a point-bound plan needs `--evidence-keys`.
  A point-bound `Restore` caught mid-upgrade ends `ApprovalBundleConflict`:
  delete it and create it again.

## Readiness checks

A `Preflight` answers one question, *would this operation fail, and why?*, by
running one short-lived check Job in the execution pod's own shape: the same
image, ServiceAccount, Secret projections and mounts, and no token.

```bash
kubectl --context docker-desktop get preflight -n team-a
# NAME    OPERATION   PHASE       RESULT     EXPIRES   AGE
# pf-9a1b Restore     Completed   notReady   14m       28s
```

| `spec.request.operation` | Needs | Runs |
|---|---|---|
| `Backup` | A source `KafkaCluster`, a destination, 1–1000 named topics | The backup catalogue and the source's capability rows |
| `Restore` | A draft plan or an existing `Restore`, a target, the source and evidence destinations (or `legacySourceArchive`), the recovery point (`recoveryPointRef` or `catalogPointRef`, at most one) | The target, plan, archive and approval rows, and the target's capability row |
| `DestinationAccess` | A `BackupDestination` and 1–4 roles | The `destination.*` rows for those roles, and `destination.credentialBound` over every declared `SecretKeys` grant |
| `SourceConnection` | One `connectionRef` and nothing else | `connection.resolved`, `connection.credentialProjected`, `connection.authenticated`, `connection.clusterIdentity`, `runner.*`, `configuration.policy`, `configuration.egress`. No destination credential, CA or signing key is mounted |
| `Switchover` | `switchover.restoreRef` (name, optional UID) and at most 100 `groups` (`source`, optional `target`; none: every mapped group) | The review before a `Switchover` (*Switching consumer groups over*): `switchover.restore`, `target.resolved`, `destination.resolved`, then the Job's `switchover.evidence`, `switchover.target`, `switchover.groups`. The pod gets the restore's target credential and its evidence destination's `evidenceRead` grant; no signing key |

**A `ready` verdict authorises nothing.** Every execution-time guard still runs,
and none reads a `Preflight` (a source-scan test,
`no_execution_path_reads_preflight_or_discovery`, holds that). A client may
require a fresh `ready` as friction; it may never bypass a guard.

| `phase` | Meaning |
|---|---|
| `Pending` | The plan is rendered and the Job is being created |
| `Queued` | Held by a concurrency ceiling (`ConcurrencyLimited`) |
| `Running` | The Job has not finished |
| `Completed` | A result exists: read `status.result.state` |
| `Failed` | No result could be produced: `ResultUnreadable`, `RunnerContractUnsupported`, `CheckContractMismatch`, `DeadlineExceeded`, `Stalled`. Terminal; create a new `Preflight` |
| `Cancelled` | `spec.cancelRequested` was set |

`status.result.state` is `notReady` if any blocking row is `notReady`; else
`unknown` if any blocking row is `unknown` or `skipped`; else `ready`. An empty
check set is `unknown`. A pod that never started is a real answer: a missing
Secret is `connection.credentialProjected notReady CredentialSecretNotFound`
with a remedy, and the rest read `unknown`, `BlockedByPrerequisite`.

Each row in `status.result.checks[]` carries a code, a message, a remedy, an
`authority` (`controller`, `checkJob` or `podStatus`), a `scope {kind, name,
uid}`, `gating` (`blocking`, `advisory` or `executionOnly`) and its own
`expiresAt`. An `executionOnly` row (`connection.topicsReadable`,
`destination.archivePrefixWritable`, `target.logAppendTime`,
`configuration.egress`) is `unknown` forever, with one exception:
`connection.topicsReadable` turns blocking `notReady`
(`TopicAuthorizationFailed`) when the broker's authorized operations (KIP-430)
say the principal may not READ a named topic, naming the topic and the grant
(FX-45), and (`TopicNotFound`) when the broker does not hold a named topic and
the principal may Describe the cluster: "topic `x` does not exist on the
source" (DUI-5). Non-secret facts are rendered into
the message as `[key=value; …]`; long lists go to the immutable `ConfigMap`
`status.result.detailsRef`. Messages pass the redaction chokepoint: a credential
value is removed under a key name at any length, and unkeyed at 40 characters
and up, except a run of 64 or 128 hex characters, which reads like a digest.
Print secrets under a key name. A Kafka name in a typed field is not free text:
the secret-shape rules apply to it and the 40-character rule does not, so a long
name arrives whole. That covers a legal topic name (`[a-zA-Z0-9._-]`, at most
249) under a details line's `topic` or `mappedTopicExists`, a row's topic
sample and a catalog entry's topic `name`, and a group id (printable ASCII, at
most 255 bytes) under `group`, `target` or a catalog entry's `groupId`. In a
message, a legal topic name in backticks right after the word `topic` or
`topics` (and each further name of that list) is kept the same way, so "topic
`x` does not exist on the source" names a long `x`.
Anything else under those keys, and every other string, is redacted as before.
Every row code is in
[reference.md](reference.md#preflight-rows).

**Staleness.** `status.binding` records the plan hash, every referent's UID and
generation, CA digests, trust, the approval's `resourceVersion` and the policy
digest as one `inputsDigest`. A result applies only while `phase: Completed`,
`now < status.result.expiresAt`, and the plan hash and `inputsDigest` still
match. A terminal `ready` that stops applying is downgraded to `unknown`, with
`status.message` naming `expired`, `planHashChanged`,
`referentChanged:<Kind>/<name>`, `caBundleChanged`, `policyChanged` or
`inputsDigestChanged`. **The binding does not cover credential Secrets or a
recovery point's topic set:** re-run the check after rotating a credential.
`target.mappedTopics` and `target.topicCreate` expire in five minutes.

**Skipping is not answering.** `spec.request.skipChecks` leaves a row `skipped`,
which keeps the verdict `unknown`. A `Preflight` over a draft plan has no
`Restore` to approve yet, so `approval.state` is `skipped`,
`SubjectNotCreated`; the wizard treats exactly that shape as submittable.

### What the rows check

- **Destinations.** `destination.evidenceWritable` writes only with the
  destination's opt-in `spec.readiness.writeProbe: CreateOnlyMarker`; otherwise
  it is `executionOnly`, `WriteNotProbed`. The probe creates
  `logweir/readiness/<destinationUid>.json` as the `evidenceWrite` principal,
  then creates it again and requires the second create to be refused: a store
  that does not enforce `If-None-Match: *` is `notReady`,
  `ConditionalCreateUnsupported`, because every backup there would exit 4. MinIO
  `RELEASE.2025-09-07T16-13-09Z` (and the project's rebuild) is measured
  supported; older MinIO, AWS S3, GCS and Azure are
  `[UNVERIFIED — not run against those stores]`. `destination.evidenceReadable`
  reads as the `evidenceRead` principal (`LOGWEIR_EVIDENCE_READ_AWS_*`) and is
  requested only when that grant exists; a `ControllerIdentity` grant is
  `unknown`, `EvidenceReadNotConfigured`. `destination.archivePrefixWritable` is
  never probed (`ArchivePrefixWriteVerifiedOnlyAtExecution`), but its binding is
  compared on `destination.credentialBound`.
- **Restore writes nothing.** Collisions come from metadata and a validate-only
  `CreateTopics`. The archive rows read `<prefix>/<backupId>/manifest.json` and
  its segments exactly where the runner writes them.
- **Approval rows read the `Approval`.** `approval.state`: `Verified=True` is
  `ready`, `ApprovalVerified`; `KeyIdExpired` is `notReady`, `ApprovalExpired`;
  any other refusal is `notReady`, `ApprovalNotVerified` with the controller's
  message; no condition yet is `unknown`, `ApprovalPending`. The plan hash is
  checked first. `approval.keyValidity` (advisory) compares the restore's
  deadline with `status.approverKeyWindow.notAfter`:
  `ApproverKeyExpiresBeforeDeadline`, `ApproverKeyValid` or
  `ApproverKeyWindowUnknown`. Both re-check at `min(10 m, notAfter)`.
- **Broker configuration.** `target.timestampBound` needs DescribeConfigs on the
  Cluster resource; a refused read is `unknown`, `BrokerConfigsNotReadable`,
  never `ready`, and the restore's phase 0 needs the same grant. A target that
  reports no bound key is `TimestampBoundNotReported`.
- **Capability rows** ask what the endpoint can do. `connection.engineProtocol`
  (`Backup`) and `target.engineProtocol` (`Restore`) are blocking:
  `EngineProtocolUnsupported` names each request and the versions served (for
  example, Redpanda v26.2.4 serves Produce v0–v7 and the engine sends v8). The
  engine never negotiates, so without this row a run fails only with
  `kafka-backup backup exited 1`. `connection.topicConfigsReadable`
  (`TopicConfigsNotReadable`) and `connection.groupTypes` (`GroupTypesNotListed`)
  are advisory. The ApiVersions rows answer only when every listed broker and
  every bootstrap address answered within 10 s (`brokersAnswered: 3 of 3`), else
  `unknown`, `ApiVersionsNotObserved`. A bootstrap that answers while advertised
  listeners do not is `notReady`, `BrokerUnreachable`: check
  `advertised.listeners`. A `SourceConnection` Preflight (Test connection)
  answers `connection.engineProtocol`, `target.engineProtocol` and
  `connection.groupTypes` ADVISORY (FX-46): the test passes when the connection
  answers, and the rows say whether the endpoint is usable as a backup source,
  as a restore target, and whether its groups can be typed. The standalone
  commands run the same rows (FX-45): `backup run` refuses a source
  `connection.engineProtocol` is `notReady` for, and a topic the principal may
  not READ, before the engine (exit 3); `drill run` refuses a target
  `target.engineProtocol` is `notReady` for at phase 0, before anything is
  created; `doctor` reports it as check 8, `target engine`.
- **`recoveryPoint.state`** compares the point's frozen `locationDigest`
  (`Backup.status.destination`) with the source destination's: equal is `ready`,
  `RecoveryPointSucceeded`; different is `notReady`,
  `RecoveryPointLocationMismatch`; a point archived before the field existed is
  `unknown`, `RecoveryPointLocationUnknown`, until someone confirms its
  destination by hand. For a catalog point it is read from the catalog row:
  `RecoveryPointNotFound`, `CatalogPointViewUnavailable`,
  `CatalogPointRefusedByController`, `CatalogPointNotSelectable`,
  `CatalogPointSignerUntrusted`, `CatalogPointSignerUnknown`,
  `CatalogPointBindingMismatch` or `CatalogPointSelectable`. A view that does
  not list the point and holds a line the check cannot read is
  `CatalogPointViewUnavailable`, never `RecoveryPointNotFound`: the line may be
  the point.
- **A point-bound plan's archive** is judged as the runner will judge it.
  Nothing is read unless the binding is well formed, `source.backup` is the set
  the check reads (never `latestCompleted`), and the receipt key is exactly
  `logweir/backups/<backupId>/<run id>.receipt.json` with each id one plain path
  segment; otherwise `archive.backupSet` is `notReady`, `PointBindingMismatch`,
  with nothing read. An absent receipt, other bytes, or one over the 64 MiB cap
  are one answer, `PointBindingMismatch`, where the store answers 404 (on AWS S3
  with the minimal grant an absent receipt reads `AccessDenied`
  [UNVERIFIED — needs a real AWS S3 bucket and a credential source]). A pinned
  version that is no longer current is `ManifestSuperseded`. The signature is not
  checked here; the runner checks it.
- **A legacy point** (`legacySourceArchive`, no saved destination) is read as
  the restore Job will read it: the Secret's `access-key-id` and
  `secret-access-key`, the plan's `source.storage`, and region or endpoint from
  the installation policy's `legacyArchiveAddressing` when the plan leaves them
  out. A backup check over an inline archive is not run: `Failed`,
  `ArchiveUrlUnreadable`.
- **`signer.rostered`** is execution-only for a restore
  (`SignerKeyIdNotObserved`). For a backup it reads the namespace's resolved
  trust: `SignerRostered`, `SignerNotRostered`, `SignerKeyExpired`,
  `TrustRosterNotLoaded` or `TrustUnknown`.

**Collection.** A terminal `Preflight` is deleted an hour after
`result.expiresAt` (or `observedAt`), at most twenty per pass, under
`preflight.retentionSeconds`. Copy a verdict out to keep it.

## Verify

The controller verifies every run's signed evidence (a `Backup`'s receipt, a
`Restore`'s scorecard) and writes `status.evidence.verification`. It links the
verifying half of the evidence code and never the signing half. To verify a
document yourself, offline, see [verify-a-scorecard.md](verify-a-scorecard.md).

### The verdict

| `result` | A claim about |
|---|---|
| `Valid` | The document and the signer: the bytes verify and this installation accepts the key |
| `Invalid` | The document: the digest did not match, or no key verified the sidecar |
| `NotAttempted` | The controller: no evidence credential, an unreadable object, no trust material, or a namespace two policies contest |
| `Untrusted` | The signer: the bytes are authentic and the key is one this installation will not accept. `detail` names `UntrustedSigner`, `KeyUsageMismatch`, `SignedOutsideValidity`, `Revoked` or `RecordedBeforeRevocation` |
| `Pending` | Nothing yet: an evidence-fetch Job is reading the document. Never green |

Beside it: `matchedKeyId` (the id the policy declares), `verifiedAt`,
`signedAt` (the document's own claimed signing time; recorded, not trusted) and
`trust {basis, keyState, policy {name, uid, generation}}`, where `basis` is
`Current`, `Historical`, `RecordedBeforeRevocation`, `Unverified` or `None`, and
`keyState` is `Active`, `Retired`, `Expired`, `Revoked` or `Unknown`.

**The badge is green** only when:

| Kind | Green when |
|---|---|
| `Backup` | `result == Valid` and `exitCode == 0` |
| `Restore` | `result == Valid` and `outcome == pass` and no recorded `exitCode` other than `0` and no `integrity.complete.covered: false` |

and, for both, `trust.basis` is `Current`, `Historical` or absent (an object
from before the trust block). It reads "verified by weirkeeper at `<verifiedAt>`
against key `<matchedKeyId>`", with "(signed before that key was retired)" for
`Historical`, which is a pass. Anything else renders `unverified`. The
`Verified` condition carries the same rule, reason `Verified`,
`VerificationInvalid`, `VerificationNotAttempted`, `VerificationUntrusted`,
`ExitCodeNotZero`, `OutcomeNotPass` or `CompleteNotCovered`.

**What the controller checks, in order:** an evidence credential exists (else
`NotAttempted`); it reads the payload and its sidecar (any storage error is
`NotAttempted`, never `Invalid`); it recomputes the digest and compares it with
the one the runner reported (`receiptSha256` or `scorecardSha256`; a mismatch is
`Invalid`); it verifies the DSSE sidecar under the namespace's
`EvidenceSigning` keys only; and it asks whether that key is still trusted (a
retired, expired, revoked or out-of-window key is `Untrusted`). An empty key list
is `NotAttempted` with the object to edit:

> the TrustRoster lists no signing key material; add the runner's public key to spec.signingKeys

> the TrustPolicy bound to this namespace lists no key with usage EvidenceSigning; add the runner's public key to spec.keys

The verdict is written in a second status patch after the terminal one, so a
verification failure never hides the exit code.

### Where the evidence is read from

- **A destination-backed run** is read with the evidence destination's
  `evidenceRead` grant. `SecretKeys`, `WorkloadIdentity` and `ArchiveReadGrant`
  are read by an evidence-fetch Job (below); `ControllerIdentity` by the
  controller, at an allowlisted location only. Absent `evidenceRead` is
  `NotAttempted`, naming the field.
- **An inline-archive run** (and every run an older release wrote) is read only
  through the controller's own read-only archive handle, built from
  `LOGWEIR_ARCHIVE_URL` with the credential `logweir-evidence-ro` (a read-only
  principal, `s3:GetObject` on the evidence prefix). It is verified exactly when
  its evidence is in that handle's bucket: an inline `Backup` writes under its
  archive's bucket, an inline `Restore` wherever its plan's `evidence:` block
  says. Elsewhere it is `NotAttempted`, naming the run's location and the
  `logweir drill verify` route. The console writes a plan's evidence to the
  archive's own bucket.
- `logweir-evidence-ro` is projected into the controller as environment,
  `optional: true`. Without it every inline verdict reads
  `NotAttempted`, "no evidence credential is configured; run the printed
  logweir drill verify command instead". After creating or rotating it,
  **restart the controller Deployment**; the new process reads every unverified
  run once more.

### Evidence fetch: how a pod-only grant is read

A `SecretKeys`, `WorkloadIdentity` or `ArchiveReadGrant` `evidenceRead` is read
by an evidence-fetch check Job, never by the controller, which holds no verb on
`secrets`.

- After the terminal patch and the runner's TTL, the controller creates
  `lwc-ev-<first 20 hex of sha256(<uid>:<attempt>)>` in the object's namespace,
  owned by the `Backup` (or the `Restore`, with the evidence destination's
  grant). Its plan is the immutable `<job>-plan` `ConfigMap`; its argv is
  `check run` for kind `evidenceFetch`.
- The kubelet projects exactly the `evidenceRead` grant: `SecretKeys` gives
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and optionally
  `AWS_SESSION_TOKEN`; `ArchiveReadGrant` gives the same from the `archiveRead`
  Secret; `WorkloadIdentity` runs as that ServiceAccount. No signing key, no
  write grant, no Kafka credential and no token.
- The pod relays the document (up to its cap) and a sidecar of up to 64 KiB.
  The controller reads the relay only from a pod whose controller owner is that
  Job, then checks, in order: the relayed receipt's sha256 against the runner's
  `receiptSha256` (a mismatch is `Invalid`); the binding (`backup_id` against
  `status.backupId`, or the scorecard's `run_id`); the DSSE signature against
  the namespace's trust.
- While it runs, `status.evidence.verification.result` is `Pending` and
  `status.evidence.observation` is `{mode, jobRef{name, uid}, attempt}`, plus
  `presence` once a relay is read.
- A Job that ends without a verified relay is `NotAttempted`, naming the cause,
  never `Valid`. A failed attempt (a denial, a store error other than
  `NotFound`, a broken relay) is retried with a new Job at +1 m, +5 m and
  +15 m (`observation.retryAfter`); the run itself is never re-run. A missing
  document and one over the cap are final.
- At most `checks.maxEvidenceFetchActivePerWorkspace` fetches run per workspace;
  a run over the limit waits `Pending`. The Job's TTL (10 minutes) is set after
  the verdict commits. A run whose runner reported no receipt digest
  (legacy-unbound) gets no Job.
- `evidenceRead: ControllerIdentity` is read by the controller itself, and only
  at a location listed in `evidence.controllerIdentityLocations`
  (`[{endpoint, region, bucket}]`, empty by default). Anywhere else it is
  refused `ControllerIdentityNotAllowlisted`. A transient failure of the
  controller's own read takes the same retry schedule, with
  `observation.mode` `ControllerIdentity` or `ArchiveHandle` and no `jobRef`.

### When a read fails

A failed controller read's `NotAttempted` has one of three classes, from its
`detail`:

| Class | `detail` | Next |
|---|---|---|
| transient | `the evidence object could not be read: …` (denial, no credential, timeout), trust unreadable, a verification that did not complete | Read again at +1 m, +5 m and +15 m (`status.evidence.observation {mode, attempt, retryAfter}`); the `detail` names the next attempt |
| absent | `the evidence object <key> is not in the archive` | Never read again. The store maps every 404 here, including a missing bucket or a wrong endpoint; verify such a run with `logweir drill verify` |
| configuration | No archive handle, no signing key, two policies, no `evidenceRead`, evidence outside the handle's bucket | Read once more by each new controller process |

At most four controller reads run at once. A reached verdict is never read
again.

### When trust changes

A run finishing now gets the current policy's answer. A terminal object's
verdict is re-derived on a `TrustPolicy` event from what is already on its
status (`matchedKeyId`, `signedAt`, `verifiedAt`), with no storage read and no
Job; only `evidence.verification.{result,trust,detail}` and the `Verified`
condition change. `verifiedAt` is never refreshed by a trust change. A revoked
key turns a green verdict to `Untrusted`; `status.records` and `status.capture`
stay as observed. `kubectl --context <ctx> get trustpolicy <name> -o yaml` shows
what the cluster thinks of each key now.

**Objects verified before `signedAt` existed** carry no signing time. On their
next reconcile the controller reads the document once more (bytes checked
against the recorded digest; signature not re-checked) to take its signing
time. Until that succeeds the verdict is `NotAttempted`, `trust.basis:
Unverified`, with `trust.retryAfter` fifteen minutes ahead; `matchedKeyId` and
`verifiedAt` are kept. A document that has no signing time records
`trust.signingTimeRead: absent`; one over the read cap, `overCap`. A `detail`
beginning "digest mismatch at" is worth escalating. Revocations, unlisted
signers and usage mismatches are decided at once, without the read.

### The signing-oracle residual

`weirkeeper` is a **signing oracle**: Job CRUD in the namespace that holds
`logweir-signing-key` is equivalent to holding that key, because a Job the
controller creates can mount it. That is residual **O1**, accepted. The
controller links no signing code (`weirkeeper` depends on `logweir-verify`,
never on `logweir-evidence`; `scripts/check-one-signer.sh`), and the console
links it only for its `ConsoleConfirmation` documents, but the capability to
sign evidence stands while the controller can create Jobs there.

Since OD-23 the install is one namespace, so the console's session, cursor and
confirmation keys and the OIDC client secret share it with the signing key.
**Whoever can read Secrets, create Pods or Jobs, or create a Secret in that
namespace holds every key**, and can sign evidence and forge any approval mode.
The console path is closed: a Secret a Logweir object names is mounted only
when it carries the referrer's `logweir.dev/workspace` label, the key Secrets
carry none, and the console can neither read a Secret nor create one without
its workspace's label, so a compromised console cannot make a runner mount a
key. `kubectl` users with Secret, Pod or Job rights in the namespace remain
administrators of the install ([Workspaces](#workspaces)). None of this stops a
cluster-admin (`docs/stability.md`, **O0**).

## Retention

Everything else Logweir does is additive. Deleting an archived point costs the
point. So retention has its own kind, its own credential, its own binary and
its own gate, and **`mode: Report` is the default and deletes nothing.**

A `RetentionPolicy` covers one destination. `spec.destinationRef`,
`spec.catalogRef` and `spec.scope` are immutable, because an approved plan names
point ids.

| Field | Meaning |
|---|---|
| `spec.mode` | `Report` (default), `Enforce` or `ExternalLifecycle` |
| `spec.rules` | `keepLast` (1–100000), `keepDays` (1–36500), `minUsablePoints` (default 3) |
| `spec.holds[]` | `{pointId, reason, until}`: points kept whatever the rules say |
| `spec.scope.prefix` | The archive prefix the policy may delete under |
| `spec.enforcement` | `approvedPlanSha256`, `credentialSecretRef`, `schedule` (five-field UTC cron), `deadlineSeconds` (default 1800), `maxDeletionsPerRun` (1–500, default 50), `maxObjectsPerRun` (default 20000), `planMaxAgeSeconds` (300–86400, default 3600), `requireApprovedPlan` (default `true`) |
| `spec.externalLifecycle` | `{provider: s3\|gcs\|azure, ruleId, prefix, expirationDays}` for `ExternalLifecycle` |

### What the evaluation does

The evaluation reads the `RecoveryCatalog`'s view of this destination,
digest-checked against `status.pages[].sha256`. Points the view does not name
at this destination are not counted.

- A point is a candidate only if the catalog says `Available` and `Verified` or
  `VerifiedHistorical`. Anything else lands in `status.lastEvaluation.skipped`
  and never becomes a candidate. A pass that cannot read the archive proposes
  nothing.
- **The controller's own verdict outranks the row.** The evaluation joins the
  namespace's `Backup` verdicts by `receiptSha256` (or `backupId`). A point whose
  `Backup` was refused (`Invalid`, `Untrusted`, an unknown result, or `Valid`
  on a basis the badge refuses) is skipped as `Unreadable`. When the join cannot
  be completed, the evaluation is `Evaluated=False/BackupVerdictsIncomplete`,
  nothing is planned, and `Ready=False` names the cause:
  `BackupHistoryTooLarge` (more than 10,000 `Backup`s: prune the history) or
  `BackupVerdictsUnreadable`.
- The newest `minUsablePoints` usable points are kept whatever the rules say,
  reported as `MinUsablePoints` in `status.lastEvaluation.protected`. A
  `spec.holds[]` entry still in force reports `Hold`, and a provider refusal
  (`Locked`) reports `LegalHold`.
- **Points that share a backup set are planned whole or not at all.** Points
  sharing a `backupId`, a manifest key or a segment key form a group; a group
  holding any retained point plans none of its candidates (protected
  `SharedSegment`). When every receipt of a set is due, one plan line removes
  the set and names the others in `co_point_ids`. A point whose set id is empty,
  carries `/` or reads `[redacted]` is protected `Unknown`.
- Two `RetentionPolicy` objects over one destination put both in
  `Ready=False/Conflict`; neither evaluates.

`status.lastEvaluation` counts every point once:

| Field | Counts |
|---|---|
| `pointsEvaluated` | Every point of this destination in the view |
| `keptCount` | Points that stay (rules or protection; protected ones are also in `protected`) |
| `candidateCount` | Points this plan removes, at most the ceiling |
| `truncatedByCap` | Points the rules would remove that the per-run ceiling held back. They are due, not kept |
| `skippedCount` | Points that could not be judged |

`pointsEvaluated` = `keptCount` + `candidateCount` + `truncatedByCap` +
`skippedCount`. Each list (`kept`, `candidates`, `protected`, `skipped`) holds
at most 500 entries; the counts are whole. `maxDeletionsPerRun` is the ceiling
applied (50 for a policy with no `spec.enforcement`). `kubectl get
retentionpolicy` prints a `HELD-BACK` column between `CANDIDATES` and
`EVALUATED`. An absent `truncatedByCap` or `keptCount` means an older controller
wrote the block; the API then answers `lastEvaluation.accounting: NotRecorded`.

- `status.lastEvaluation.at` is when these findings were first reached, not
  when the controller last looked.
- `status.lastEvaluation.planRef` names the plan this evaluation rendered. The
  `ConfigMap` is created only by the pass that starts a run.
- `candidates[].objects` is omitted: the view carries no segment keys, and a
  plan line names the manifest and the set prefix `<scope.prefix>/<backupId>/`
  with `enumerate_set: true`. For the real count, run
  `logweir-retention run … --dry-run`, which prints
  `retention-point=<id> state=Kept objects=<n> code=DryRun` per point and
  deletes nothing.
- `status.lastEvaluation.viewIncomplete: true` means the view is not the whole
  archive: the catalog is `truncated` (a window of `viewLimit` points) or its
  walk did not finish. Points outside the view are never candidates. `spec.sync`
  is immutable, so re-create the `RecoveryCatalog` with a larger `viewLimit`
  (at most 5000).

### Enforcing

Four gates stand between a rule and a removed object:

1. `spec.mode` is `Enforce`.
2. `spec.enforcement.approvedPlanSha256` equals
   `status.lastEvaluation.planSha256`, and the plan is younger than
   `planMaxAgeSeconds`. The digest covers the policy's identity, the destination,
   the scope, the rules as applied and the exact lines. A `rules` or `holds`
   edit, or a new backup, changes it; an edit to `deadlineSeconds`, `schedule`,
   `credentialSecretRef` or `mode` does not.
3. The controller writes `status.lease` with a preconditioned patch, then lists
   every `Restore` in the cluster, uncached. **Any nonterminal `Restore` reading
   this destination refuses the run.** `Restore` admission does not consult the
   lease, so a `Restore` created after that list and before the first delete is
   not seen: set the policy to `mode: Report` before a large restore in a
   retention window.
4. The worker re-validates every key against `<scope.prefix>/<backupId>/` and
   refuses the whole plan on the first key outside it.

```bash
kubectl --context docker-desktop -n <namespace> \
  get retentionpolicy primary -o jsonpath='{.status.lastEvaluation.planSha256}'
# sha256:…  — copy this into spec.enforcement.approvedPlanSha256 to authorise a run
```

`spec.enforcement.requireApprovedPlan: false` skips gate 2: the policy deletes
without a reviewed plan, and says so as `Enforced=True/UnattendedDeletionEnabled`.
An object that appears under an approved set prefix between preview and run is
removed too; `planMaxAgeSeconds` bounds that.

**Two credentials, and neither alone is enough.**

| Credential | From | May do |
|---|---|---|
| The delete grant | `spec.enforcement.credentialSecretRef`, projected into retention Jobs only | `s3:ListBucket` with a prefix condition; `s3:GetObject` and `s3:DeleteObject` on `<prefix>/*`, **excluding `logweir/*`** |
| The record grant | The destination's `evidenceWrite` (or `archiveWrite` when absent), never `archiveRead` | Create-only puts under `logweir/`, no delete |

- Both Secrets must carry their `logweir-binding`: the delete grant's is the
  policy's `status.credentialBinding` (its UID, the destination's route and
  `spec.scope.prefix`). Otherwise the worker refuses before building a handle:
  `retention-refusal=CredentialBindingMismatch`,
  `Enforced=False/CredentialBindingMismatch`.
- Any other refusal (exit 3, nothing deleted) is `Enforced=False/RunFailed`,
  and the message names it, for example `(exit 3, CapUnreadable
  (LOGWEIR_RETENTION_MAX_OBJECTS))`; `EnforcementDegraded`'s message says
  `refused <code>` too. The codes are in
  [reference.md](reference.md#logweir-retention).
- The refusal stays named until the next run starts:
  `status.lastEnforcement.refusalCode` (and `refusalVariable`) records it,
  and the passes between runs leave `Enforced` and `EnforcementDegraded`
  naming it. A pass that has something else to fix first (`mode`, the
  schedule, the catalog view, the ceiling, the approval) shows that on
  `Enforced` instead; the record and `EnforcementDegraded` still name the
  refusal. A refused run is a failed run: it counts toward the three below.
- A record grant that a Job cannot use (malformed, no static keys — a
  `WorkloadIdentity` grant has no path here — or the same Secret as
  `credentialSecretRef`) gives `Enforced=False/EvidenceGrantUnusable` naming
  the field, with no Job, lease or plan. Fixing the grant resumes enforcement
  within about a minute. The check compares Secret names only: that the two
  grants are really distinct principals is your obligation.
- A run with no record credential exits 3. One whose record writes fail stops
  at the first point whose intent tombstone cannot be written (exit 1).
- **The controller cannot delete.** It holds no `delete` verb, no verb on
  `secrets`, and does not link the delete code: `crates/logweir-reaper` is linked
  only by `logweir-retention`, which `scripts/check-no-archive-write.sh` check 3
  proves.
- The enforcement Job runs the runner image (the chart's `runnerImage`) with the
  command `logweir-retention`; there is no separate retention image. It requests
  the `logweir-retention` ServiceAccount, which the chart renders when
  `retention.enabled` is true, in the release namespace. Without it the pod is
  not admitted and nothing is deleted.
- **The margin is the grant.** The binary is in every runner pod, so what stops
  an ordinary run from deleting is that `archiveWrite` carries no
  `s3:DeleteObject`. Do not grant it.
- The shipped `logweir-runner-egress` NetworkPolicy also selects retention pods,
  so they inherit egress to the broker ports. Narrowing it means editing its
  `podSelector` (`logweir.dev/component NotIn [retention]`).

**What a run writes, in order, per point:** the create-only intent tombstone
(unsigned in this build) at
`logweir/retention/<policyUid>/<runId>/<pointId>.intent.json`, the manifest,
the segment objects, then the completion tombstone. The run record lands at
`logweir/retention/<policyUid>/<runId>.json`, named by
`status.lastEnforcement.recordKey`. A point interrupted halfway reads `Missing`
in the catalog, and the next plan finishes it.

**Reading a run.** The run is recorded on the object (`status.lastEnforcement`
`runId`, `startedAt`, `planSha256`) before its Job exists; a record that does not
land creates no Job (`Enforced=False/RunNotRecorded`). After the run,
`status.lastEnforcement` carries `exitCode`, `deleted[]`, `failed[]` with closed
per-point codes and `objectsDeleted`, and, for a refused run, `refusalCode`.
The Job is collected ten minutes after harvest, so **use the record, not a Job
census**, to decide whether a run happened.

```bash
kubectl --context docker-desktop -n <namespace> get retentionpolicy primary \
  -o jsonpath='{.status.consecutiveRunFailures}{"\n"}{.status.lastEnforcement.finishedAt}{"\n"}'
```

Three consecutive failed runs set `EnforcementDegraded=True/ConsecutiveRunFailures`
and stop scheduling until the spec changes (`metadata.generation` moves); one
success resets `status.consecutiveRunFailures`. Neither time nor a restart
releases it. On a build before 2026-09-19, a `lastEnforcement` whose `runId` is
current but whose `finishedAt` is older than its `startedAt` means the counter
was stuck.

| `Enforced=False` reason | Meaning |
|---|---|
| `NothingToDo` | Nothing is due |
| `NothingFitsCeiling` | Points are due but every one is in a set larger than `maxDeletionsPerRun`. Raise it to at least the size of the smallest such set |
| `ViewIncomplete` | `viewIncomplete` is `true` or not stated |
| `ViewExpired` | The catalog view is past, or has no, `status.viewExpiresAt` |
| `AwaitingApproval` | No plan has been approved yet |
| `PlanSuperseded`, `PlanExpired` | The approved digest is not the current plan's, or is older than `planMaxAgeSeconds` |
| `ActiveRestore` | A nonterminal `Restore` reads this destination |

The full list of retention reasons is in [reference.md](reference.md#retentionpolicy).
`status.enforcement` says what is actually happening: `RecommendationOnly`,
`LogweirWorker` or `ExternalLifecycleDeclared`. `status.guarantees` reads
`LogweirEnforced`, `ProviderEnforcedUnverified` or `NotEnforced` for each of
`ageExpiry`, `minUsablePoints`, `activeRestoreProtection`, `sharedSegments` and
`legalHold`. `sharedSegments` stays `NotEnforced` (the view has no segment keys;
the set half is enforced), and `legalHold` stays `ProviderEnforcedUnverified`.

On v1, an archive of more than 5000 points is never enforced, and nor is a
`mode: Full` catalog whose walk does not finish in one sync: use `mode: Index`,
or a `maxObjectsPerRun` that finishes in one sync (`spec.sync` is immutable:
re-create the catalog).

### Versioned and Object Lock buckets

On a versioned bucket a `DELETE` by key writes a delete marker and removes
nothing, and a hold is never consulted. The worker refuses that combination:

1. Before a point's deletes it PUTs the intent tombstone; a version id in the
   answer means versioning is Enabled. Nothing of the point is deleted; it is
   `Kept` with `VersionedBucket`.
2. Before every delete it HEADs the key; a current version with a version id is
   not deleted (`VersionedBucket`). This needs `s3:GetObject` on `<prefix>/*`;
   without it every key is `Kept` with `VersionProbeRefused`.
3. After the deletes it PUTs `logweir/retention/<policyUid>/<runId>/<pointId>.check.json`.
   A version id, or a refused write, makes the point `Orphaned` with
   `VersionedBucket` (or `VersionCheckRefused:…`), not `Deleted`.

The run exits 1. A policy degraded only by `VersionedBucket` or
`VersionProbeRefused` starts one re-probe run 24 h after its last run, so it
resumes by itself once the bucket or grant is fixed. A provider that refuses a
plain `DELETE` gives `Locked` in `failed[]`, and the next evaluation protects
that point as `LegalHold`.

`Deleted` means the current object at each key was removed. **Do not enforce on
a bucket whose versioning was ever enabled and later suspended**: a null version
over an older one is recorded `Deleted` while the older survives. Use
`mode: ExternalLifecycle` or a noncurrent-version lifecycle rule. Do not change a
bucket's versioning while a run is in flight.

### `ExternalLifecycle`

`mode: ExternalLifecycle` declares that a bucket lifecycle rule does the work.
Logweir evaluates nothing and reads no provider configuration. `ageExpiry` and
`legalHold` become `ProviderEnforcedUnverified`; the other three become
`NotEnforced`. When `expirationDays` is shorter than `keepDays`,
`ExternalLifecycleConflict=True` says so, and the bucket wins.

A retention failure never blocks a backup: an unreadable view writes
`Evaluated=False/ViewUnreadable` and touches nothing else.

## Approvals

An `Approval` object that exists is not an approval. An `Approval` whose status
the controller set to `Verified=True` is. Creating the object is a `POST` any
namespace tenant can make; what authorises is a signature by a trusted key over
bytes that bind this plan, this subject and its kind.

### Choosing a mode

Each workspace has one approval mode, set by the installation and frozen into
every run's execution inputs.

| Mode | Internal | Who approves a `Restore` |
|---|---|---|
| **confirm** | `Ordinary` (document v2) | The requester, one click in the console. No key handled by anyone. |
| **two-person** | `Governed` (v2) with `approverSignature: Console` | A second person signed in to the shared console, one click. No key handled by anyone. |
| **strict** | `Governed` (v2) or `legacy-governed-v1` (v1) | An approver's personal `GovernedApproval` key |

The chart renders one document from `approvalPolicy.*` into an immutable,
content-addressed `ConfigMap` `<release>-approval-policy-<digest>`, mounted into
the controller (`LOGWEIR_APPROVAL_POLICY_FILE`) and the console
(`approvalPolicyFile`). Both log the same `approval_policy_digest` at start.

```yaml
approvalPolicy:
  allowOrdinaryConfirmation: true   # needed for any confirm policy; default false
  default: confirm                  # optional: confirm or strict, for unbound workspaces
  policies:
    - name: team-ordinary
      mode: confirm                 # rendered as Ordinary
      maxAgeSeconds: 900            # 60..604800; default 900 (confirm), 86400 (Governed)
    - name: prod-pair
      mode: two-person              # rendered as Governed + approverSignature: Console
      maxAgeSeconds: 3600
    - name: prod-strict
      mode: strict                  # rendered as Governed
      requireDistinctPrincipal: true  # must be true for Governed
  workspaces:                       # each key must be in the chart's `workspaces`
    dev: team-ordinary
    prd: prod-pair
```

- The controller and the console **refuse to start** on a document that does
  not validate: an unknown field, a confirm policy without
  `allowOrdinaryConfirmation: true`, a Governed policy with
  `requireDistinctPrincipal: false`, a binding to an undeclared policy, or the
  reserved names `legacy-governed-v1` and `default-confirm-v1`.
- **An unbound workspace** resolves to `approvalPolicy.default` (`defaultMode`
  in the document; `confirm` or `strict`, never `two-person`); else, on a fresh
  install, `confirm`; else `legacy-governed-v1`. Under `confirm` it resolves to the policy
  `default-confirm-v1` (`Ordinary`, 900 s). An explicit binding always wins.
- **Two-person** needs `api.console.mode: shared`; the chart refuses it in any
  other mode.
- **A policy change is a rollout.** Every signed document names the policy's
  snapshot digest, so a changed policy is a different policy. Changing the
  document renames the `ConfigMap` and rolls both Deployments. Requests signed
  under the old digest (including by an old console pod during the rollout) are
  refused `ApprovalPolicyMismatch` and must be submitted again; a run already
  admitted continues.

**The fresh-install default.** Only the identity hook's first run, the one that
generates the installation identity and the console key
(`identity.bootstrapFeatures.consoleKey`), makes unbound workspaces `confirm`. It
creates the default `TrustPolicy` (only when the cluster has no `TrustPolicy` and
no `TrustRoster/default`) and writes the annotation
`logweir.dev/approval-default: confirm;policy=<name>;uid=<uid>;signing=<keyId>;console=<keyId>`
on `logweir-signing-trust`. The controller (every 15 s) and the console honour it
only when that policy exists with that UID, the provenance
`logweir.dev/created-by: identity-bootstrap`, `default: true` and exactly the
claimed signer and console key. Anything else is unmarked, logged as a WARN, and
every unbound workspace stays `legacy-governed-v1`. An upgrade never reaches this: the
identity already exists.

- That first run needs `create` on `TrustPolicy`. The chart renders the grant
  `<release>-identity-trust` only as a post-install hook of a first install with
  the managed console key, and **refuses it under Helm before 3.19.0**
  (`identity.installationTrust needs Helm 3.19.0 or newer`): use a newer Helm, or
  set `identity.installationTrust.enabled=false` and trust the console key
  yourself. If an install was interrupted, delete it:
  `kubectl delete clusterrolebinding,clusterrole <release>-identity-trust`.
- The console's `ConsoleConfirmation` key (Ed25519) is generated once into the
  retained Secret `logweir-console-confirmation`, its public half published in
  `logweir-console-trust`. An existing Secret of that name is adopted and
  trusted by nobody automatically.

**To opt an older install's unbound workspaces into `confirm`:** (1) a trust
administrator adds the console key from `logweir-console-trust` to the governing
`TrustPolicy`, usage `ConsoleConfirmation`; (2) the installation administrator
sets `approvalPolicy.allowOrdinaryConfirmation: true` and
`approvalPolicy.default: confirm` (or binds the workspaces) and rolls out
([install.md](install.md) §5f).

**Residuals** ([SECURITY.md](../SECURITY.md)). In any console mode, whoever
controls the console pod, its key Secret or the identity provider can approve
alone. The `localAdmin` console confirms as `urn:logweir:local-admin#admin`, so
whoever may port-forward to `deploy/<release>-api` can confirm a restore alone;
two-person is never served there. The controller's ServiceAccount holds
cluster-wide `patch` on `trustpolicies` (for the compromise finalizer), so
whoever can run a pod as `weirkeeper` can append a key to any existing policy; a
`ValidatingAdmissionPolicy` limiting that account to `metadata.finalizers` closes
it. While a first install's identity hook runs, whoever can run a pod as
`<release>-identity-bootstrap` could create a `TrustPolicy`; the installer holds
cluster-admin then anyway.

### Trust: which keys govern a namespace

Trust for one namespace resolves in this order:

1. a `TrustPolicy` whose `spec.namespaces` names it exactly;
2. the one policy with `spec.default: true`;
3. `legacy-roster-v1`, synthesised in memory from `TrustRoster/default`;
4. neither: every `Approval` is refused `RosterNotFound`.

**A namespace two policies claim resolves to nothing**: every approval and
verification there is refused `TrustPolicyConflict`, and both policies report it
in `status.conflicts`. Two `default: true` policies report it under the sentinel
namespace `*`. A namespace never names its own trust, for the reason the
roster's name is fixed: a roster whose name the subject supplies is a roster
the subject can choose.

- A `TrustPolicy` key declares exactly one usage: `EvidenceSigning`,
  `GovernedApproval` or `ConsoleConfirmation` (CEL rule G8). Keys are
  append-only with identical public material; `notAfter` only shortens; `state`
  moves `Active → Retired → Revoked`; revocation instants are write-once.
- `kubectl get trustpolicy` shows `DEFAULT`, `KEYS`, `LOADED` and `BOUND`. Per
  key, the status reports `effectiveState`
  (`Active`/`NotYetValid`/`Expired`/`Retired`/`Revoked`/`Unparseable`),
  `usableForNewSignatures` and `usableForVerification`
  (`Full`/`Historical`/`None`), beside an `evaluatedAt` heartbeat refreshed at
  most every five minutes. The console shows `unknown` when the status is
  absent, lags the generation or is more than fifteen minutes old. An
  unparseable key is that key alone, `Unparseable`.
- `TrustRoster/default` is deprecated, still served and reconciled. The
  controller reads that name and no other. Its status shows `LOADED` and
  `EXPIRED`; one unparseable PEM makes it `Loaded=False` and refuses every
  approval. It reads `Superseded=True/SupersededByTrustPolicy` only when a
  `default: true` policy exists; otherwise `Superseded=False/RosterStillConsulted`,
  and it must still be maintained. Do not delete it: it is the rollback path.
  `logweir trust migrate-roster` writes a policy from it and refuses a key on
  both of its lists. See [keys.md](keys.md) for rotation and migration.
- **A `KeyCompromise` revocation applies to every namespace and outlives its
  policy.** Any `TrustPolicy` recording a key `Revoked` with
  `revocationReason: KeyCompromise`, even one being deleted, revokes that key in
  every resolution, from the earliest `revocationEffectiveFrom`. The finalizer
  `logweir.dev/compromise-revocation` keeps such a policy `Terminating` until
  another policy records the same revocation or nothing lists the key; its
  `CompromiseGuard` condition reads `DeletionBlocked`, `CompromiseRecorded`,
  `CompromiseInherited` or `NoCompromiseRecorded`. CEL rule G9 keeps the reason
  from being edited. See [keys.md](keys.md), *Replacing a `TrustPolicy` safely*.

**Keys each mode needs in the namespace's `TrustPolicy`.** A fresh install's
policy already carries the signer and the console key. Otherwise add the
console's public key, usage `ConsoleConfirmation` (`GET
/api/v1/workspaces/{ws}/approval-policy` prints its key id), and, for strict,
each approver's key, usage `GovernedApproval`, with `principal.id:
<issuer>#<subject>` (their OIDC identity). A workspace bound to a policy in a namespace
still on `legacy-roster-v1` refuses every v2 document `KeyIdNotInRoster`.

### What the controller checks

The controller verifies by the namespace's current binding: an unbound
(`legacy-governed-v1`) namespace accepts only a v1 document; a bound one only v2.

- **v1** (`logweir drill approve` writes it; `"subject_kind": "Restore"` is in the
  signed bytes): payload type first, before any key is tried; every key parses;
  each `keyId` is the SHA-256 of its DER SPKI; a signature's key is trusted; it
  verifies under the matched key; the key is in its window; the document's
  `plan_hash` equals the sha256 of the referent's `spec.planBytes`, recomputed;
  `subject_kind` equals the referent's kind; and the object's own
  `spec.planHash` equals the same hash.
- **v2** (`application/vnd.logweir.restore-authorization+json;version=2.0.0`,
  signed by the console with its `ConsoleConfirmation` key): the exact subject
  including UID, the recomputed plan hash, the policy name, digest and mode equal
  to the binding, and a window no longer than `maxAgeSeconds`, issued at most
  60 s ahead and not expired. Governed also needs a second signature by a usable
  `GovernedApproval` key whose `principal.id` differs from the requester's
  `<issuer>#<subject>` (else `SelfApprovalRefused`; a `principal.id` not of that
  form is refused the same way). Two-person needs the console's approver fields
  (format `2.2.0`). A `ticket` (at most 128 printable characters) is required
  under Governed (`AuthorizationDocumentInvalid` otherwise).
- An `Approval` naming a `RehearsalSchedule` is refused
  `StandingAuthorizationRefused` before any check (withdrawn in v1, release-notes
  item 73).
- A key outside the trust is `KeyIdNotInRoster`, never `SignatureInvalid`.
  Admission is a new use of a key, so a retired, expired, revoked or
  not-yet-valid key is refused under its own reason. `subjectRef.kind: Backup`
  is refused `ReferentHasNoPlanBytes`. `ReferentNotFound` can be a race: the
  `Restore` holds thirty seconds and tries again.

Every `Verified` reason, and the order of the v1 checks, is in
[reference.md](reference.md#approval).

**`approvalBytes` and `sidecarBytes` are the UTF-8 document text, verbatim**,
never base64. Paste exactly what the CLI wrote; the hash is over those bytes.

**What lands on the status.** On success: `verified: true`, `matchedKeyId` (the
key that matched, never `signatures[0]`), `approver`, `ticket`,
`selfAttestedRisk` (the approver key id is also a signing key id; labelled, never
refused), `approverKeyWindow {keyId, notBefore, notAfter}` and `Verified=True`. On
a refusal: `verified: false`, a `Verified` reason and message, and those five
fields sent as `null`. Absent `approverKeyWindow` means unknown, never valid. A
refused `Approval` stays in the cluster as the audit trail. The controller
patches `/status` only, and re-examines on a timer because expiry is a function of
the clock.

```bash
kubectl --context docker-desktop get approval a1 \
  -o jsonpath='{.status.conditions[?(@.type=="Verified")].reason}'
```

**After admission the `Approval` is a record, not a gate.** Once the `Restore`
it names is `Admitted=True` and its bundle names this `Approval`'s UID, the
controller adds `Consumed=True` (reason `RestoreAdmitted`). A `Switchover`'s
`Approval` is consumed the same way (reason `SwitchoverAdmitted`) once the
Switchover carries `Admitted=True`, which its controller writes once, before the
Job; that condition's time is the admission instant. A Job, `status.jobRef` or a
ConfigMap alone is never admission. An `Approval` an older build rewrote
`AuthorizationExpired` after its switchover ran is re-verified from its signed
bytes and recorded again only when that Switchover's status proves the run (a
terminal phase with the run's exit code, and its Job recorded) and its bundle is
that build's, carrying this `Approval`'s bytes; the bundle's creation is then the
instant. The verdict then
stays as recorded whatever the clock, a key's `notAfter`, a retirement or a
policy edit does. Only a compromise reaches it: `verified` becomes `false`, and
`Verified` reads `RecordedBeforeRevocation` when the admission preceded the
revocation, `KeyRevoked` otherwise. Never green.

**The four places v2 is enforced.** The `Approval` controller (above); `Restore`
admission, immediately before any `ConfigMap` or Job (`ApprovalPolicyMismatch`
and `AuthorizationExpired` end the `Restore`); the mounted bundle, which adds
`approval-policy.json` and `confirmation.pub.pem` and is pinned by
`LOGWEIR_EXECUTION_POLICY_SNAPSHOT_SHA256` and `…_CONFIRMATION_KEY_SHA256`
(`ApprovalBundleMaterializationFailed` holds); and the runner
(`--policy-snapshot`, `--confirmation-key`), which re-verifies everything but
expiry and exits 3, `no data operation was started`. A `Restore` and an
`Approval` written straight to the API server are refused the same way and create
no `ConfigMap` and no Job.

### Strict: approving out of band

Under strict the console stores its signed request as
`Approval/<approvalRef>-confirmation`, which authorises nothing. The approver
runs `logweir drill countersign` over the same bytes on their own machine and
submits the result (`POST /api/v1/workspaces/{ws}/restores/{name}/approval`,
Approver role); only then does the referenced `Approval` exist. The console
refuses an approval submitted by the requester (403, whatever roles the actor
holds).

### Two-person: approving in the console

<a id="two-person-approval-in-the-console-prod-162"></a>

The approver opens the Restore's approval page (`GET
.../restores/{name}/approval-request`). The console verifies its own signature
over the stored request and shows the whole scope: source archive and set, point,
target cluster, every topic and its target name (original names marked, with the
requester's statement about declarative owners), and the verification. The click
(`POST .../console-approval`, Approver role) adds `approver` and `approvedAt`,
signs with the same console key (format `2.2.0`) and stores the `Approval`.

- **A second person** is the identity provider's issuer and subject: the same
  issuer (case and a trailing `/` ignored) and another subject (case ignored).
  Never `urn:logweir:local-admin` or a `system:` subject. Two sessions of one
  user are one person; an Administrator is not an Approver unless bound as one.
- `issuedAt <= approvedAt < expiresAt` inside the signed bytes; the controller
  also refuses an `approvedAt` more than 60 s ahead of its clock.
- A two-person request names at most 1024 topics; a larger plan is refused at
  create (`scope_incomplete`). Split it, or bind the namespace `strict`.
- The requester approving is refused by the console (403), the controller
  (`SelfApprovalRefused`) and the runner (exit 3). Another Restore, UID, plan or
  policy, an expired request, a second approver, or a personal-key
  countersignature is refused 409 by the console and again downstream.
- The scorecard carries `approval.console` (who asked, who approved, both
  instants).

## Serving the console

The console, `logweir-api` ([install.md](install.md) §5e), serves the page and a
bounded product API ([api.md](api.md)) on one origin. Every request is
authorised for the session's own identity and workspace grants. The legacy
`kubectl proxy` page and the `logweir-ui` image are withdrawn in v1
(release-notes item 75); the chart refuses `ui.*` by name. The console's
`shared` mode is the one component that may have an Ingress.

The console is at `/ui/`; every page's address is `#/<workspace>/<page>`
([console/README.md](../console/README.md), *Routes*). The navigation shows
only what the session's role may read in the workspace, and the workspace
picker appears only when the session holds roles in more than one.

| Page | What it does |
|---|---|
| Overview (`#/<ns>`) | Policies against their objective, the newest point's age, the last 24 hours' runs and what needs attention, with Restore and Back up now |
| Backups, Schedules, Protection | Runs, their exit, records and verification, and "Restore this point"; schedules with the guided create, the future-policy edit, next-run previews, suspend, "Back up now" and the retention panel; protection health, read-only |
| Restores | Restores, each followed live over a server-sent-event stream (it cancels nothing); the five-step wizard (recovery point, topics and time, target, readiness check, review and create); *Retry to a fresh target* |
| Switchovers | Review a verified restore's consumer positions, confirm, and follow the `Switchover`; its rollback steps are shown, never started |
| Approvals | Confirm, approve a two-person request, or record an out-of-band approval |
| Recovery catalog, Trust | Connected archives and their points, and connecting an existing archive; trust policies and keys (Administrator only) |
| Connections, Destinations | Saved connections, their checks and topic discoveries; destinations, their access tests, rotation and usage. A credential is typed once; the console creates a bound Secret and never shows it again |

What the console will and will not say:

- **A readiness result is the check Job's recorded aggregate, nothing else.** An
  empty `checks` array is not a pass; a `skipped` blocking check is never a pass;
  an unknown phase reads `unknown`. Execution-time guards stay the authority.
- **A topic inventory never reads "complete".** `attestedComplete` is shown with
  its author, its instant and "not verified by Logweir".
- **With no controller for a kind**, statuses stay empty and the console says
  "not judged yet" or `pending`, never ready or failed.
- **The policy panel replaces, it does not patch.** `PUT .../schedules/{name}`
  takes the whole future policy under an `expectedGeneration` precondition, and a
  field left out is removed. A blank input means "do not set this field". A save
  from a stale screen is refused `412`.
- **The browser evaluates no cron.** `GET /api/v1/cadence-previews` compiles a
  preset against the controller's own time-zone database. The page reads
  staleness from `nextRuns[0].at` in the past.
- **A manual run is one run per intent.** "Back up now" holds one
  idempotency key per click (`logweir-console.manual.` plus 32 random hex
  characters): a double click or a retry returns the same run
  (`replayed: true`), and "Back up again" sends a new key.
- **Protection health and schedule health are two columns**, never collapsed.
- **The catalog keeps availability and verification apart.** Whether a point may
  be restored is the API's `selectable`, read and never recomputed. **There is no
  one-click trust**: an untrusted signer shows its key id, the fingerprint
  command, and a `TrustPolicy` document the page renders and does not apply.
- **`unknown` is not `valid`.** A key's state is judged against the server's
  clock (`GET /api/v1/trust-policies` publishes `evaluation {state, reason,
  serverTime, freshWithinSeconds, ageSeconds}`). Reading trust policies needs an
  Administrator binding; namespace lists are filtered to what the actor
  administers (`namespacesFiltered`).
- **The retention panel shows the RetentionPolicy that names the schedule's
  destination** (`spec.destinationRef.name`, the controller's own match), with
  `status.enforcement` beside `spec.mode`: a `Report` policy reports and deletes
  nothing, an `Enforce` one is shown as deleting. A policy that is not
  recommendation-only and names another destination is listed under it: the
  page does not compare locations, and two destinations can share a bucket and
  prefix. "Logweir never deletes from your archive" is shown only when the
  policies were read and none names the destination (nor does a policy that is
  not recommendation-only name another).
  `legalHold` reads "declared by your provider; Logweir cannot verify it".
- The API publishes no Job, pod or `ConfigMap` names and no frozen
  `locationDigest` on a catalog point; open vocabularies are rendered verbatim.

The console's lint refuses markup from data, browser storage and any request
outside its one client, and `console/scripts/check-dist.mjs` refuses a build
that carries the mock or names a file outside `./assets/`. The page ships inside
the console image (`Dockerfile.console`); `just smoke-console` compares its
served files with this tree's `console/dist`.

### Recording an out-of-band approval (strict, v1)

In a `legacy-governed-v1` namespace the approver signs on their own machine.
Nothing in the product holds an approver key.

1. **Mint both names from the plan bytes**, because both `.spec`s are sealed:
   `restore-<first 8 hex of sha256(planBytes)>` and `approval-<the same 8 hex>`.
   Create the `Restore` first; it holds `ApprovalNotVerified`.
2. **Get the exact bytes.** Use the wizard's download button, or
   `kubectl --context docker-desktop get restore <name> -o jsonpath='{.spec.planBytes}' > <name>.yaml`.
   Do not copy from the page: browsers strip trailing whitespace.
3. **Sign:**

   ```bash
   logweir drill approve --spec <file> --key <privkey> --approver <id> --ticket <id>   --subject-kind Restore --out <file>
   ```

   It prints `plan_hash  sha256:<64 lowercase hex>`, which must equal the hash
   the wizard showed. The sidecar lands beside `--out` with `.sig`.
4. **Record it** on the approvals page, which posts the two files verbatim. It
   refuses a `.pem` or `.key` file or a private-key header ("this page never
   accepts a private key"), and reads every spec field off the `Restore` itself.
5. **The controller decides** (see [Approvals](#what-the-controller-checks)).

**Check a key out of band** by asking its holder for the public half:

```bash
openssl pkey -pubin -outform DER -in <key>.pub.pem | openssl dgst -sha256
```

The digest is the `keyId` the trust carries and the `matchedKeyId` the
controller records. A plan cannot be edited: the wizard's "edit" makes a new
`Restore` with a new plan hash, which the old approval does not cover.

`TrustRoster/default` is cluster-scoped and sealed; prefer a `TrustPolicy`. Its
shape is `spec.approverKeys[]` and `spec.signingKeys[]` (each `keyId`, `spkiPem`
public key, `subject`, `notAfter`) and `allowedClusterIds`. Replace it with
`kubectl create` after deleting the old one ([install.md](install.md)); every
approval is refused while it is absent. An empty `signingKeys[]` makes every
verification `NotAttempted`.

## Topic discovery

A `TopicDiscovery` is one bounded observation of the topics a saved connection
can see. It is a request, not a cache: `spec.request` is immutable, so
refreshing means creating another object, and the previous result stays
readable. It runs as a check Job in the object's namespace, with the connection's
credential and no Kubernetes token. The result is advisory.

| `status.phase` | Meaning |
|---|---|
| absent / `Pending` | Not looked at yet. |
| `Queued` | Over an installation concurrency ceiling (`ConcurrencyLimited`); retried every ten seconds. |
| `Running` | The check Job exists; `reason` says what the pod waits for. |
| `Succeeded` | A verified relay was decoded and its chunks committed. |
| `Failed` | Terminal. A check that ran keeps its own code (`BrokerUnreachable`, `AuthenticationFailed`, `TlsHandshakeFailed`, `MetadataTimeout`, `ClusterAuthorizationFailed`, …) with message and remedy in `status.message`. Otherwise the controller's: `ConnectionNotFound`, `ConnectionInvalid`, `DeadlineExceeded`, `ResultUnreadable`, `CheckPlanConflict`, `ResultStorageConflict`, `Stalled`, or a pod-waiting code such as `CredentialSecretNotFound`. |
| `Cancelled` | `spec.cancelRequested` reached a running object; no chunks were written. |

- `ConnectionNotFound` and `ConnectionInvalid` are terminal: create the
  `KafkaCluster`, then a new `TopicDiscovery`. `ResultUnreadable` means the relay
  did not decode or verify, or carried neither an inventory nor a failing check.
  The check Job itself shows `Complete` even when the discovery is `Failed`.
- **`unknown` is the healthy answer.** Kafka silently omits topics the principal
  may not `DESCRIBE`, so `status.result.visibility.state` is `unknown` for a clean
  listing, `limited` when an authorization failure was observed, and
  `attestedComplete` only when an administrator attestation in
  `weirkeeper-policy` matches this namespace, `KafkaCluster`, the broker's
  cluster id and the principal, is unexpired, and the inventory was not
  truncated. Logweir records the attestation's id and does not verify it
  [UNVERIFIED — an attestation matching a live broker has not been run on
  docker-desktop; the matching rules are unit-tested only].
  `visibility.basis` records near misses such as `attestationPrincipalMismatch`
  and `attestationClusterIdMismatch`.
- Empty is `Succeeded` with `result.counts.returned: 0`. Stale is past
  `status.freshUntil` (`observedAt` plus `discovery.freshSeconds`, 900 s by
  default). `status.binding` records the connection the observation was taken
  against. `observedAt` is the runner container's `finishedAt`.
- The names live in immutable `ConfigMap` chunks owned by the discovery (at most
  2,500 entries and 768 KiB each, at most 64 chunks); `status.result.chunks`
  indexes them and `status.result.topicsSha256` is the controller's digest of the
  whole inventory. A result cut to `maxTopics` reads `truncated: true`,
  `truncationReason: MaxTopics`. Reading chunks with `kubectl` needs `get` on
  `configmaps`, which no Logweir role grants; browse in the console.
- Internal topics (names starting `__`) are excluded and counted in
  `counts.internalExcluded`; `spec.request.includeInternal: true` returns them.
- Cancelling collapses the Job's `activeDeadlineSeconds` to 1. A finished Job
  gets `ttlSecondsAfterFinished: 600` after the status write. Deleting the
  discovery removes its plan and chunks by cascade. Terminal discoveries are
  collected automatically after `discovery.retentionSeconds` (24 hours) or
  outside the newest `discovery.keepPerConnection` (five) per connection; see
  [the installation policy](#weirkeeper-policy).

## Consumer positions

<a id="consumer-position-evidence-specconsumergroups"></a>

A `Backup` or `BackupSchedule` may name consumer groups whose committed
positions each run records as signed evidence:

```yaml
spec:
  topics: [orders, payments]
  consumerGroups: [billing, invoicing]   # exact ids; at most 100
```

Each run reads the groups just before its engine starts and records exactly one
outcome per group in the receipt's `consumer_positions` (format 1.7.0):
`captured`; `excluded` (`GroupTypeNotCaptured` for a share, streams or other
group; `GroupNotFound`); or `failed` (`NotVisibleToPrincipal`,
`GroupVanishedDuringCapture`, `PositionsUnstable`, `GenerationChangedDuringCapture`).
A captured group carries its position counts; every position is in
`<run_id>.consumer-positions.json` beside the receipt, which the receipt binds
by digest ([the format](formats/backup-receipt.md#consumer_positions--consumer-position-evidence-format-170)).
A partition with no committed offset is counted, never offset 0.

- **Read-only on the source.** Group listings, one DescribeConsumerGroups, one
  RequireStable OffsetFetch per captured group (bounded at 15 s; a pending
  transactional commit fails `PositionsUnstable`) and the partitions'
  watermarks. The run's principal needs Describe on each group, and Describe on
  the cluster for a complete listing. Nothing is committed and no group joined.
- **Not atomic with the records.** Positions are read while applications run.
  The receipt says when they were observed and which groups were active. A topic
  whose marks regressed during the run fails the groups holding a position on it
  (`GenerationChangedDuringCapture`); the receipt's `generations` block shows a
  recreated topic.
- **Kafka 3.7.x** types no group, so every group is `excluded:
  GroupTypeNotCaptured`. Use 3.9 or 4.x.
- **Where it shows.** Both receipt readers print one `consumer_positions` line
  per group and, given `--consumer-positions`, verify and print each position.
  The catalog view and the API (`PointView.consumerPositions`) show per group
  its outcome and counts, and the snapshot's `observedBeforeRecoveryPointMs`.
- **Refusals.** A repeated, blank or control-character id, one over 255 bytes,
  more than 100, or a selection whose receipt summary could exceed 80 KiB is
  refused before any Job, `ExecutionSpecInvalid` naming
  `ConsumerGroupSelectedTwice`, `ConsumerGroupIdInvalid` or
  `ConsumerGroupSelectionTooLarge`; a schedule carrying one is `Ready=False`.
- **Set when a schedule is created, or with `kubectl`.** The schedule create
  (`POST .../schedules`, the console's *Create a schedule*) takes
  `consumerGroups` and refuses a selection by the rules above, by field, before
  anything is stored; an empty list is none. The schedule's and each run's
  views show it, as the console's schedule and run pages do. An edit through
  the API or the console leaves the stored selection alone; `kubectl` changes
  it. An ad-hoc run from the API selects none.
- **Nothing here resets a group.** A restore maps the positions; only a
  [`Switchover`](#switching-consumer-groups-over) applies them. To read
  positions with the source gone, see
  [the receipt format](formats/backup-receipt.md#recovering-positions-with-the-source-offline).
- A schedule that names groups changes its `runPolicySha256`. An older
  controller ignores `consumerGroups` on a run it has not frozen yet (it records
  no positions) and refuses a run whose frozen inputs carry it
  (`PlanConfigMapConflict`): let such runs finish, or remove the field, before
  rolling back.

## Switching consumer groups over

A restore writes the data under new offsets; a consumer that resumes from its
old position would skip or re-read records. Logweir translates the positions a
backup captured and applies them, reviewed, to **stopped** groups on the
restore's target. Nothing commits a position automatically after a restore.

1. **Back up with groups** (`spec.consumerGroups`, above).
2. **Restore with `coverage: complete`**, bound to that point. When the run
   passes and covered every partition, phase 7 maps every captured position
   onto the target and writes `logweir/drills/<run_id>.positions-mapping.json`
   beside the scorecard, bound by digest in
   `integrity.verification.positions_mapping` (scorecard 1.12.0, or 2.4.0 for
   a partition subset). Each entry is `exact`, `approximate` (the restore's own
   selection excluded records the group had not read; `skipped` counts them) or
   `unavailable` with a reason (`ArchiveGap`, `PartitionNotRestored`,
   `TransactionalArchive`, `BeforeLogStart`, `NotCaptured: …`, …). A sampled
   or failing restore writes no mapping.
3. **Review** (optional, advisory). A `Preflight` with `operation: Switchover`
   (`POST …/preflights` `{"operation": "switchover", "switchover":
   {"restoreName": R, "restoreUid": U, "groups": [{"source": "app"}]}}`) reads
   what the switchover would, and changes nothing: `switchover.restore` (the
   `Restore` exists with that UID, is not scratch, `Succeeded` with a `Valid`
   verdict, writes evidence to a saved destination, and the namespace has
   evidence keys), `switchover.evidence` (the signed scorecard and the mapping
   it binds verify, as the run's step 3), `switchover.target` (the restore's
   cluster id and topic IDs, as step 5) and `switchover.groups` (each target
   group's type, state and members admit a commit, and its committed
   positions are none or already the mapped ones). The details
   (`GET …/preflights/{id}/details`) carry one line per group and restored
   topic, every partition with its mapped offset, class and committed
   position. A `ready` review authorises nothing; the run repeats every check.
   An inline-archive restore is not reviewed (`ArchiveUrlUnreadable`); create
   the `Switchover`, which checks it.
4. **Plan.** `logweir switchover plan --scorecard S --positions-mapping M
   --restore-name R --restore-uid U [--group src[=target]]… --out plan.yaml`
   plans every mapped entry (unavailable ones are listed, never planned) with
   `expected: none`. An operator may replace `expected` with the positions a
   target group already holds (an earlier attempt's); the approver sees it and
   the run holds the group to it.
5. **Approve and create** a `Switchover` (operators create, approvers approve):

   ```yaml
   apiVersion: logweir.dev/v1alpha1
   kind: Switchover
   metadata: {name: orders-cutover}
   spec:
     planBytes: |          # the plan file, verbatim
       ...
     approvalRef: {name: orders-cutover}
     restoreRef: {name: incident-4471, uid: 6f1c…}
     deadlineSeconds: 900
   ```

   The `Approval` names `subjectRef: {kind: Switchover, name: orders-cutover}`;
   `logweir drill approve --subject-kind Switchover --spec plan.yaml` mints a v1
   document, and a namespace bound to an approval policy takes its normal mode
   (confirm, two-person or strict). An approval for the `Restore` cannot
   authorise it (`SubjectKindMismatch`).
6. **Admission.** The controller refuses a plan that is not its
   `restoreRef`'s, a `Restore` that did not succeed with a `Valid` verdict
   (`RestoreNotSucceeded`), a scratch restore (`RestoreIsScratch`) and a second
   switchover of the same restore while one runs (`SwitchoverInProgress`), then
   creates the immutable bundle `<name>-switchover`, writes `Admitted=True`
   (the admission, once), and creates one Job (`logweir switchover run`) with
   the restore's target connection and its evidence destination's two grants:
   `evidenceRead` to read the evidence, `evidenceWrite` to write the record
   ([the grants](#the-grants-and-the-object-storage-actions-each-one-needs)).
   A bundle that already exists is used only when it is byte for byte this
   admission's, with this Switchover as its one controller owner; otherwise the
   Switchover ends `Refused`, `ApprovalBundleConflict`, and no Job is created.
   A Job named after the Switchover before it is admitted is not adopted
   (`Pending`, `SwitchoverJobNotAdmitted`, until it is gone); once it is
   admitted, a Job under its name is the run only when its one controller owner
   reference is this Switchover's UID, and any other ends it `Refused`,
   `JobNameConflict`, with no `jobRef` (the Restore's check). A run whose Job
   is deleted before it finishes ends `Failed`, `SwitchoverJobLost`, and is
   never admitted again: create a new Switchover and approval.
7. **The run** verifies the approval, the scorecard's signature and plan hash,
   a passing complete verification (`VerificationNotComplete`, naming the
   field), the mapping's digest, every plan entry against the mapping
   (`PlanDisagreesWithMapping`), the target's cluster id
   (`TargetClusterChanged`) and each restored topic's ID against the one
   recorded at creation (`TargetGenerationChanged`, `TargetIdentityUnknown`).
   Then, per group, independently: a group with members is `GroupActive`; a
   share or streams group `TargetGroupTypeUnsupported`; one the principal
   cannot see `TargetNotVisible`; an offset outside the partition now
   `BelowTargetLogStart`/`AboveTargetEnd` (`TargetMarksUnreadable` when a
   partition's marks could not be read); the committed positions are read
   (the priors) and compared — `applied` when they are what the plan expects,
   `alreadyApplied` when they are the plan's, `TargetPositionsChanged`
   otherwise — and the commit is Logweir's own non-member commit, which the
   broker refuses while the group has a member. Each group is read back.
8. **The result.** `status.phase` is `Succeeded`, `PartiallyApplied`, `Failed`
   or `Refused`, and `status.message` ends with the runner's own sentence for
   a whole-run refusal or failure. A store that refuses a read of the evidence
   is `Failed` with reason `EvidenceUnreadable` (`could not read <key> with
   grant <grant>: AccessDenied`), never `MappingDigestMismatch`, which means
   the bytes are not the bound ones. `status.groups[]` one outcome per group;
   `status.evidence.recordKey` the signed record
   `logweir/switchovers/<run_id>.record.json` (+ `.sig`; verify it with
   `logweir drill verify --payload-type switchover-record`, signature only).

**Retry and rollback.** The same plan in a new `Switchover` (and a new
approval) is safe: applied groups read `alreadyApplied`, refused ones are tried
again, moved ones are `TargetPositionsChanged`. `logweir switchover
rollback-plan --record R` builds `offsets := prior, expected := applied`; a
group whose consumers ran since is refused, naming how many records they read,
and a prior that was absent cannot be restored through a commit — it is listed
with the `kafka-consumer-groups.sh --delete-offsets` command to run.

**A group left `failed: CommitFailed` with some partitions applied** (the
record's `applied` per partition says which) can be neither re-run (its
positions are no longer all what the plan expects: `TargetPositionsChanged`)
nor rolled back (`rollback-plan` reverses `applied` groups only). Both refuse,
so nothing is overwritten. The way out, with the group stopped, is the
broker's own tool: remove the positions the record shows applied
(`kafka-consumer-groups.sh --bootstrap-server <b> --group <g> --topic <t>:<p>
--delete-offsets`, one per applied partition), check with `--describe` that
the group holds no position on the restored topic, and create a new
`Switchover` with the same plan. (Setting the rest by hand with
`--reset-offsets --to-offset <planned> --execute` also works, and no signed
record then shows that commit.)

**Permissions.** The runner's target principal needs Describe on the cluster
(a complete group listing), Describe and Read on each target group, and
Describe on the restored topics. The controller needs `get, list, watch` on
`switchovers` and `patch` on `switchovers/status` (the chart grants them).

**Upgrade and rollback.** An older controller ignores `Switchover` objects
(nothing is applied); a Helm rollback leaves the CRD and its objects inert. An
older verifier ignores `positions_mapping` and refuses the switchover record's
payload type.

## Protection health

An enabled schedule says the cron fires. A `ProtectionPolicy` says whether a
recoverable point exists. Its spec is mutable and has no CEL seal: it is
evaluation policy, never an execution input. `status.observedGeneration` says
which revision a verdict came from.

**A point is available** when the run is `Succeeded` with `exitCode: 0`; its
evidence is `Valid` or `ValidHistorical` (unless
`objectives.requireVerifiedEvidence` is off); it covers the policy's source,
destination and topics; and, with `protects.catalogRef` and
`objectives.requireCatalogAvailability`, the catalog view is current and says
`Available` and selectable. `Untrusted` and `Invalid` evidence never count, at
any setting. `recoveryPointAt` is the newest available point's capture start
(`Backup.status.capture.startedAt`); `status.lastAvailablePoint.newestRecordAt`
is its newest record.

| `status.health` | Meaning |
|---|---|
| `Healthy` | An available point inside `maxRecoveryPointAgeSeconds`, failures below the threshold, no suspended or not-ready schedule, no missed slot |
| `AtRisk` | Inside the objective, but failures at the threshold, a suspended or not-ready schedule, or a missed slot newer than the last fire |
| `Stale` | The newest available point is older than the objective |
| `Unprotected` | No available point at all |
| `Unknown` | The evaluation could not happen: the catalog view expired or did not read, or the source or destination is gone |

- `Protected` is `True` only for `Healthy`, `Unknown` for `Unknown`, `False`
  otherwise. `status.availabilityBasis` is `KubernetesStatus`, `Catalog` or
  `CatalogStale`.
- Failures count slots, not attempts: a retry chain is one failed slot, and
  `maxConsecutiveFailedRuns: 2` means two failed nights. A manual run of a
  schedule counts as its history.
- `status.alerts` is a ledger: one open entry per `(policy, kind)` under
  `logweir-protection-<policyUID>-<kind>`. `Staleness` covers `Unprotected`. An
  entry resolves only when health is back to `Healthy` or `AtRisk`.
  `RecoveryCompleted` keys on the `Restore` UID and resolves at once.
- **Alert delivery is withdrawn in v1 (release-notes item 74).** Nothing is
  posted anywhere. A policy that still carries `spec.notifications` keeps
  parsing, and `NotificationsDelivered` is `False` with
  `NotificationsWithdrawn`. Remove the field.
- **A point whose receipt the controller could not read** (a `SecretKeys` or
  `WorkloadIdentity` `evidenceRead`, verdict `NotAttempted`) is placed from its
  catalog row: joined on the archive set id, with its capture time read off the
  row, and `requireVerifiedEvidence` satisfied by the row's own verification
  axis. Only `NotAttempted` (or `Valid` on `trust.basis: Unverified`) defers this
  way. With no catalog or no row, `Protected=Unknown`, reason
  `PointFactsUnread`, and an open `Staleness` entry stays open.
- An entry whose axes are empty is `CatalogUnreadable`, so `Unknown`. A deleted
  page, or a page line the controller cannot parse, reads the same, never a
  pass.
- Bounds: 16 ledger entries (8 recoveries), 16 schedules, 64 topics on
  `lastAvailablePoint` (`topicsTruncated: true` beyond), and the newest 50 runs
  over at most 5 API pages of 200. The API server lists `Backup`s by name, so
  past 1,000 in the namespace the newest runs may be the ones not read: the
  verdict is then `Unknown`, reason `BackupHistoryTooLarge`, never a verdict
  over the runs it saw. Delete old terminal `Backup` objects (the archive keeps
  their points) and the policy evaluates again.
- The console's Protection page shows this read-only.

## The installation policy and roles

### Roles

The chart ships four roles. The two human ones are unbound; people use the
console, whose role bindings are per workspace.

| Role | For |
|---|---|
| `weirkeeper` (Role) and `weirkeeper-cluster-scope` (ClusterRole) | The controller: its namespaced rules in the release namespace only, and the two cluster-scoped trust kinds (`trustrosters`, `trustpolicies`) |
| `logweir-viewer` (Role) | Read on every namespaced kind, in every workspace; no verb on `configmaps` or `secrets`. The one role to hand out for `kubectl` |
| `logweir-trust-admin` (ClusterRole) | Read and write on the cluster-scoped `trustpolicies`, and the only write on them. Needs a `ClusterRoleBinding`. No `delete` |

There is no `kubectl` write role ([Workspaces](#workspaces)): `logweir-operator`,
`logweir-approver` and `logweir-retention-admin` were withdrawn with OD-23,
because a write in the namespace is a write in every workspace. Writing a
`RetentionPolicy`, whose `spec.mode` moves an install from reporting to
deleting, is therefore an installation administrator's act with `kubectl`; the
console cannot write one.

The controller reads all fourteen kinds, patches their status, creates
`Backup`s, `Restore`s, Jobs and `ConfigMap`s, reads pods, `pods/log` and
`events`, and holds one `patch` on `backups` (the history detach) and one on
`trustpolicies` (the compromise finalizer). On `secrets` it holds `get` alone,
for the workspace gate's metadata read of each Secret an object names (its
`logweir.dev/workspace` label, never its data). It holds **no verb on
`pods/exec` or `pods/attach`, no `update` on anything, and `delete` on exactly
two kinds**, `topicdiscoveries` and `preflights`. Every status write is a merge
`PATCH` preconditioned on `metadata.resourceVersion`. The chart's
[roles](../charts/logweir/templates/controller-rbac.yaml) are the authority;
`manifest_lint.rs` checks every call site has a grant and every grant a caller.
The console's own principal (`<release>-api`) is tabled in
[install.md](install.md); it holds `create` on `secrets` and no read verb.

**Fencing the console's `create secrets` (Kubernetes 1.30+).** The chart's
`admissionPolicy.enabled=true` renders a `ValidatingAdmissionPolicy` that lets
the console principal create only Secrets of type
`logweir.dev/object-store-credential` or `logweir.dev/kafka-sasl-password`
labelled `app.kubernetes.io/managed-by: logweir` (`failurePolicy: Fail`, action
`Deny`). It is off by default because the floor is 1.29, where the kind does
not exist. `admissionPolicy.consoleServiceAccountName` must be the console's
account. [UNVERIFIED — no API server has seen either document.]

`logweir-runner-egress` selects every Job pod in its namespace
(`batch.kubernetes.io/job-name: Exists`) and allows DNS, the broker ports and
object-store ports 443/9000; the chart renders it in the release namespace,
where every Job runs. [UNVERIFIED — enforcement needs a kind cluster with
Calico and a runner probe that times out to a disallowed address while reaching
Kafka.] Docker Desktop does not enforce NetworkPolicy.

### `weirkeeper-policy`

The one administrator-owned document: a `ConfigMap` `weirkeeper-policy` in the
release namespace, key `policy.json`, which the chart renders from its values.
The controller finds it through `LOGWEIR_INSTALLATION_NAMESPACE` or
`LOGWEIR_POLICY_CONFIGMAP=<namespace>/<name>` and re-reads it every 30 s. No
document means the defaults, and `configuration.policy` reads ready.

```json
{"version": 1,
 "checks": {"maxActivePerWorkspace": 4, "maxActiveTotal": 20,
            "maxActiveDiscoveriesPerConnection": 1,
            "maxEvidenceFetchActivePerWorkspace": 4},
 "discovery": {"freshSeconds": 900, "retentionSeconds": 86400, "keepPerConnection": 5,
               "defaultMaxTopics": 20000, "hardMaxTopics": 50000,
               "visibilityAttestations": []},
 "preflight": {"defaultTimeoutSeconds": 120, "retentionSeconds": 3600},
 "engine": {"allowUnverifiedCustomCa": false},
 "evidence": {"controllerIdentityLocations": []},
 "legacyArchiveAddressing": {"endpoint": "", "region": "", "allowHttp": false,
                             "virtualHostedStyle": false},
 "runs": {"maxManualBackupsActivePerWorkspace": 4,
          "maxManualRestoresActivePerWorkspace": 2}}
```

| Block | Decides |
|---|---|
| `checks` | Check Jobs at once, per workspace and in total; evidence fetches have their own pool. Over a ceiling a request is `Queued`, `ConcurrencyLimited` |
| `discovery.freshSeconds` | After this an inventory reads stale |
| `discovery.retentionSeconds`, `keepPerConnection` | When terminal discoveries are collected |
| `discovery.hardMaxTopics` | The ceiling a request's `maxTopics` is lowered to |
| `discovery.visibilityAttestations` | The only route to `attestedComplete` |
| `preflight.retentionSeconds` | When terminal preflights are collected |
| `discovery.defaultMaxTopics`, `preflight.defaultTimeoutSeconds` | Withdrawn: nothing reads them. Still accepted (any whole number to 4,294,967,295) so an older controller can read the document |
| `engine.allowUnverifiedCustomCa` | Whether a destination with a private CA may run backups and restores |
| `evidence.controllerIdentityLocations` | `[{endpoint, region, bucket}]` where the controller's own identity may read evidence; anything else is `ControllerIdentityNotAllowlisted` |
| `runs` | Manual-run ceilings per workspace (defaults 4 and 2). The chart renders the block only when a value differs |
| `legacyArchiveAddressing` | The inline-archive addressing, published read-only for the legacy restore check. Its `allowHttp` and `virtualHostedStyle` are read by nothing, by decision (FX-15): the check takes transport and addressing from the plan, as the restore runner does, and dropping them would change every install's policy digest |

An attestation has nine required, non-blank fields and applies only on an exact
match of namespace (the release namespace), `KafkaCluster`, the broker's cluster id and the principal,
before `expiresAt`, to an untruncated listing:

```json
{"id": "att-orders-prod", "namespace": "logweir-system", "kafkaCluster": "source",
 "clusterId": "M29I2S7FQPyHBEX12Vx7XA", "principal": "User:backup",
 "attestedBy": "platform-admin@example.invalid",
 "attestedAt": "2026-09-15T00:00:00Z", "expiresAt": "2026-12-15T00:00:00Z",
 "statement": "User:backup has DESCRIBE on literal Topic:* with no DENY; reviewed ACL export 2026-09-14"}
```

**A document the controller refuses fails closed:** no attestations, an empty
evidence allowlist, an advisory `configuration.policy notReady PolicyUnreadable`
row, and one `WARN` line, `the installation policy ConfigMap was REFUSED`
(`kubectl -n logweir-system logs deploy/weirkeeper | grep REFUSED`). The chart's
`values.schema.json` and `templates/_validate.tpl` check the same rules at
install, so a chart install cannot produce a refused document. Every check
records the policy's digest in `status.binding.policyDigest`.

**Collection of the two check kinds.** Terminal `TopicDiscovery` and `Preflight`
objects are deleted on an hourly pass: terminal only, with a UID precondition,
at most twenty per pass, and by age alone when the listing was truncated. A
running check is never collected. Keep-last-five is per
connection (`status.binding.connectionUid`, which only the controller writes), so
creating six discoveries can retire that connection's older ones and nothing
else. There is no per-object override: copy a verdict out to keep it.

## Running the CLI as a CronJob

The [CronJob example](../examples/cronjob-drill.yaml) schedules `logweir drill
run` without the controller. Its container is called `logweir`.

- **`backoffLimit: 0` and `restartPolicy: Never`.** A retry of an exit 2 repeats
  the restore, and `OnFailure` can lose the pod that carries the code. Read the
  code from the pod (`containerStatuses[?(@.name=="logweir")]`) before the Job
  is collected.
- **Account and mounts.** The runner makes no Kubernetes API call: use the
  `logweir-runner` ServiceAccount with `automountServiceAccountToken: false`
  ([install.md](install.md)). It runs as uid/gid 65532; projected signing
  Secrets need `fsGroup: 65532` and `defaultMode: 0440` (without `fsGroup` the
  file is root-owned and unreadable whatever the mode). Credentials stay Secrets;
  `ConfigMap`s are readable at 0644. The approval bundle mounts at `/approval`
  (`approval.json`, `approval.sig`, `approver.pub.pem`, `allowed-clusters.json`);
  keeping the allowlist in a Secret stops a subject with only `patch configmaps`
  widening a restore's targets. `--approver-key-ids` (repeatable) restricts the
  accepted approver keys. `emptyDir` suits `/work`; it is lost with the pod, so a
  crashed restore is not resumable.
- **Environment.**

  | Variable | Why |
  |---|---|
  | `LOGWEIR_ENGINE_BIN` | Set by the image to `/usr/local/bin/kafka-backup` |
  | `LOGWEIR_ENGINE_VERSION`, `LOGWEIR_ENGINE_DIGEST` | Not needed in the runner image, which declares its engine in `/etc/logweir/engine-identity`; mandatory outside it (an empty value is exit 1). The run checks the engine's `--version` either way |
  | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, or IRSA / Pod Identity | `object_store`'s own chain; `~/.aws/credentials`, `AWS_PROFILE` and SSO are not supported |
  | `TMPDIR` | Where the rendered `restore.yaml` lands; point it at a writable volume |
  | `RUST_LOG` | The example sets `info` |

- **Metrics.** `--metrics-file` writes a Prometheus textfile; there is no HTTP
  endpoint ([metrics.md](metrics.md)). It must outlive the pod and be visible to
  node_exporter: the example uses a `hostPath` with `type: Directory`, prepared
  on every eligible node with
  `sudo install -d -m 0775 -g 65532 /var/lib/node_exporter/textfile`
  (`DirectoryOrCreate` makes a root-owned 0755 directory uid 65532 cannot write).
  Pod Security `baseline` and `restricted` forbid `hostPath`: remove the volume,
  its mount and `--metrics-file` together. Use node_exporter's file mtime to see
  a run that stopped ([metrics.md](metrics.md#is-the-drill-still-running-at-all)).

## Troubleshooting by reason and exit code

### Read a run's exit code

Kubernetes shows every non-zero exit as `Error`, and Job status does not carry
the code. The controller lifts it off the `runner` container into
`status.exitCode` of the `Backup` or `Restore`, with `status.exitReason` and a
condition, before it lets the Job be collected.

| Code | Meaning |
|---|---|
| 0 | Pass. |
| 1 | Operational failure; no artifact. Retryable. |
| 2 | A measured result that did not pass; a scorecard was signed. |
| 3 | A guard refused the run. |
| 4 | Signing or lock proof failed; nothing was uploaded. |

To read the pod directly while it exists (the CronJob example names its
container `logweir`; controller Jobs name it `runner`):

```bash
kubectl --context docker-desktop get pod -l job-name=<job> \
  -o jsonpath='{.items[0].status.containerStatuses[?(@.name=="runner")].state.terminated.exitCode}'
```

Runner Jobs use `backoffLimit: 0`, `restartPolicy: Never` and
`podFailurePolicy: FailJob` for disruption and exits 2, 3 and 4. A retry of a
legitimate exit 2 would repeat the restore. Every `exitReason` and terminal
reason is in [reference.md](reference.md#backup-exit-code-to-status).

**No exit code at all.** A run whose pod never produced a terminated `runner`
gets a terminal status and no invented code: `DisruptedMidDrill`
(`DisruptionTarget=True`), `PodUnschedulable`, `PodCreationForbidden` (the Job's
`FailedCreate` event names a quota, `LimitRange`, webhook or missing
ServiceAccount), `VolumeMountFailed`, `CredentialReferenceMissing`,
`RunnerImageUnavailable`, else `NoExitCode`. An empty `EXIT` column with
`PHASE=Failed` is one of these.

**A pod is read only if its controller owner is the run's own Job, by UID.** The
`job-name` label narrows the listing and never decides. Two pods claiming one Job
is terminal `PodOwnershipContested` (not retryable): someone who could read the
Job's UID planted one. Skipped pods are logged `ForeignPodIgnored`. Do not grant
pod `create` in the install's namespace: Kubernetes' `edit` role carries
both `pods: create` and `jobs: get`.

### Why a guard refused: the message

<a id="what-a-refused-run-says-about-why-fx-34"></a>

At exit 3 the terminal condition's message ends with the runner's own reason:

```
kubectl -n team-a get restore r1 -o jsonpath='{.status.conditions[?(@.type=="Failed")].message}'
the runner exited 3 (guard-refused); the code was read from status.containerStatuses[name=runner].state.terminated.exitCode; the runner's own reason, cleaned and bounded: GuardRefused: source.storage.endpoint is a plain http:// endpoint but source.storage.allow_http is false. The pinned engine (kafka-backup 0.22.0 and later) derives plaintext transport from an http:// endpoint whatever allow_http says, so it would dial the archive in the clear although the spec asked for no plaintext. Set allow_http: true to state plaintext explicitly, or use an https:// endpoint.
```

`status.progress.message` carries the same text. `status.exitReason` stays the
state off the `refusal-reason=` line (or `GuardRefusedUnknownReason`).

- The reason is shown only from a `refusal-detail=` line the runner sealed
  with this Job's line token: a fresh 160-bit value the controller passes as
  `--runner-line-token <hex>`, which no plan can contain. Every line the
  controller reads off a runner (the evidence keys, the states, the probe's
  two lines, the progress lines) is held to the same token
  ([sealed lines](reference.md#sealed-lines-fx-43)). The token is never shown
  on any status, event, API answer or log line of the controller. The code
  must be on the kind's closed list ([reference.md](reference.md#refusal-detail)).
- The sentence is cleaned: printable ASCII and `§ – — … →` kept, URLs lose query
  and userinfo, credential shapes become `[redacted]`, cut to 760 bytes. It is
  partly written by whoever wrote the plan; read it as a description of that
  object.
- The controller reads the `runner` container's last 256 lines, at most 4 MiB,
  once, at every exit code. When nothing is shown, the message says why: no
  line with the token, a line that did not validate, `the pod is gone`, a
  refused read (`HTTP 403`), or a log over 4 MiB.

#### The runner image must be at least as new as the controller

The controller passes `--runner-line-token` to every runner Job (`Restore`,
`Backup`, the `KafkaCluster` probe, the check Jobs and the `RetentionPolicy`
Job), and every runner image published before FX-43 (the released `v0.2.0`
included) stops while parsing its arguments, before any work.

One `helm upgrade` of the packaged chart moves `controllerImage` and
`runnerImage` together. The mixed pair comes from two pinned tags with one
moved, from the floating `:latest` defaults pulled at different moments (a
mirror that copies the controller first, a node holding an old `logweir:latest`
under `IfNotPresent`), or from a `runnerImage` pinned apart.

**What it looks like:** every run ends `Failed`, `exitCode: 1`,
`exitReason: RunnerOlderThanController`, and the message names the flag and
the chart value; a `BackupSchedule` does not retry it. A `KafkaCluster` says
`Reachable=Unknown`, reason `RunnerOlderThanController`, with `reachable`
cleared. A check (a `Preflight` row, a `TopicDiscovery`, a `RecoveryCatalog`
sync) fails `CheckContractMismatch` with `RunnerOlderThanController` in its
message. A `RetentionPolicy` run is refused before deleting anything:
`Enforced=False`, `lastEnforcement.refusalCode: RunnerOlderThanController`. The runner pod's log starts with

```
error: unexpected argument '--runner-line-token' found
```

**What to do:** set `runnerImage` to the image from the same build as
`controllerImage`, in one `helm upgrade`, and create the run again. **Rolling
back: both together, or the controller first.** An older controller passes
`--line-token` or no token, and this runner then prints what that controller
reads. Runs created before an upgrade are read as the controller that created
them read them.

### A run that is stuck or failed with no exit code

`status.progress` says what a running run is doing:

| Field | Says |
|---|---|
| `stage` | `Admission`, `Queued`, `Preparing`, `Running`, `Verifying` or `Finished` |
| `reason`, `message` | The current `RunnerReady` reason, and an explanation |
| `runner` | The owned pod: name, phase, scheduled, container state, and the kubelet's waiting reason verbatim |
| `runnerPhase` | The runner's own phase, from its `progress-phase=<n>:<name>` lines |
| `diagnostics[]` | At most eight, newest first. `count` counts minutes, not occurrences |

`RunnerReady` is `False` with `WaitingForPod`, `PodUnschedulable`,
`VolumeMountFailed`, `CredentialReferenceMissing`, `RunnerImageUnavailable` or
`PodCreationForbidden`, and `True/RunnerStarted` once the container ran. The
diagnostic code is more specific: `CredentialSecretNotFound` (create the
Secret), `CredentialSecretKeyMissing` (add the key), `SigningKeyMissing`,
`RunnerImagePullFailed`. Diagnostics come from Events, listed by
`involvedObject.uid`; Events are best effort, so a missing one yields the weaker
`WaitingForPod`, never an invented cause.

**Fail-fast.** When a non-transient diagnostic has held for
`LOGWEIR_FAIL_FAST_SECONDS` (chart `controller.failFastSeconds`, default 300,
floor 60) and the runner never started, the controller collapses the Job's
deadline and the run ends with that diagnostic as its reason. Nothing was
consumed; create a new run. `PodUnschedulable` and `RunnerImagePullFailed` are
never failed fast. Set `0` to switch fail-fast off, for example where an
external-secrets controller materialises a Secret minutes after the Job.

**Job cleanup.** Terminal status first, then `ttlSecondsAfterFinished`
(`LOGWEIR_JOB_TTL_SECONDS`, chart `controller.jobTtlSeconds`, default 604800,
floor 3600). A later pass repairs a finished, owned Job left without a TTL.

### Evidence keys and records

At exit 0 the runner prints `receipt-sha256=sha256:<hex>` and its final stdout
lines `receipt-key=<key>` then `sidecar-key=<key>`. The controller reads them by
key name from the final sixteen non-empty log lines (`KEY_SCAN_TAIL_LINES = 16`)
through `pods/log`, and writes `status.evidence.receiptKey` and `sidecarKey`.
`EvidenceRecorded=True/EvidenceKeysRecorded`, or
`False/EvidenceKeysUnreadable`; absent at exits 1, 3 and 4. A missing key is
never guessed from the backup id.

- `pods/log` is a subresource; `get` on `pods` does not cover it. The controller
  reads no Secret's data (only a named Secret's labels; its `get` on `secrets`
  could, as RBAC has no metadata-only grant), holds no verb on
  `pods/exec` or `pods/attach`, and writes every
  status with a merge `PATCH` preconditioned on `metadata.resourceVersion` (a
  `409` means another writer won; the next pass reads it).
- `status.records` and `status.capture` are written only beside a `Valid`
  verdict, and are left in place if trust is later withdrawn. A record count is
  only as trustworthy as the verification badge beside it.

### Connections

- A pod given `localhost:9092` reaches itself: Kafka redirects clients to the
  advertised address after bootstrap. Advertise an address pods can reach.
- An object-store endpoint that does not resolve looks like an empty bucket.
  From inside docker-desktop a laptop MinIO is `http://host.docker.internal:9000`
  (`us-east-1`, plaintext); that is an author-only setup, and no shipped default
  names it.
- `KafkaCluster` reachability: see [Saved connections](#saved-connections). A
  `Restore` admits a target only on `reachable: true`, so a stale or crashed probe
  refuses it `ClusterNotReachable` until the next probe answers.

### Logs

`drill run` and the runner write JSON logs to stdout at `info`. Logweir events
carry `fields.run_id` or `span.run_id`, the same id the scorecard and the metrics
file carry, and every terminal path logs `drill finished` with
`fields.exit_code` and `fields.meaning`. A non-blank `RUST_LOG` overrides the
level. Save logs without piping the run's own exit status away:

```bash
kubectl --context docker-desktop logs job/<job> > drill.log
jq -r 'select(.level=="ERROR") | .fields.run_id' drill.log
```

### Images

The three images (`logweir`, `weirkeeper`, `logweir-console`) are built for
`linux/amd64` and `linux/arm64`; a runner Job needs no particular node
architecture. The engine rollback (`ENGINE_SOURCE=oso`, [install.md](install.md))
is amd64 only. With `imagePullPolicy: Never` the exact reference must be loaded
on the node: `ErrImageNeverPull` means a missing reference or an architecture
mismatch, and image pruning can remove it.

## Upgrade

**0.4.x to 0.5.0 has no in-place upgrade** (OD-23: one namespace per install,
workspaces inside it). Export trust as in [*Recover onto a clean installation
with the kit*](install.md#recover-onto-a-clean-installation-with-the-kit), keep
the bucket, `helm uninstall` the old release (one install per cluster), delete
the `TrustPolicy/logweir-installation` and `ClusterRole/logweir-identity-singleton`
it leaves (exported with the trust; the fresh install makes its own), apply
the 0.5.0 chart's CRDs server-side
(`kubectl apply --server-side --force-conflicts -f charts/logweir/crds/`, then
wait for them to be established), install 0.5.0 into one namespace with
`workspaces` and `--skip-crds` (Helm 4 would apply `crds/` again and fail on
the fields `kubectl` now owns), import trust, and then in each
workspace add connections, destinations and schedules and connect a catalog to
see the old points. Delete the old namespaces when done. Every archive stays
readable and verifiable: nothing in the bucket names a namespace. The CRDs go
first because `helm uninstall` leaves the old ones and `helm install` does not
replace a CRD that exists: without the apply, 0.5.0 runs on 0.4.x's schemas and
the API server prunes the fields it added (`KafkaCluster.spec.schemaRegistry`,
`Restore.status.interruption`).

Within a release line, the order is always: **CRDs, then the controller and runner images together,
then the console.** Helm installs `crds/` only on first install, so apply them
by hand and wait for all fourteen to be established
([install.md](install.md#upgrade-crds-before-upgrading-the-controller) has the
loop). A controller started on older CRDs has its new fields pruned by the API
server; CRDs ahead of an older controller are inert. Each release's own steps
are in [release-notes.md](release-notes.md); these are the ones that recur.

**Before the upgrade.**

- **Suspend credentialed schedules, then bind each credential Secret** after the
  roll ([Credential binding](#credential-binding)). Unbound Secrets are refused.
- **Find selections over 1,000 topics**; they are refused by name at each run:

  ```sh
  kubectl get backupschedules,backups -A -o json | jq -r \
    '.items[] | select((.spec.topics | length) > 1000)
     | "\(.kind) \(.metadata.namespace)/\(.metadata.name): \(.spec.topics | length) topics"'
  kubectl get backups -A -o json | jq -r \
    '.items[] | select((.status.selection.resolvedTopicCount // 0) > 1000)
     | "\(.metadata.namespace)/\(.metadata.name) resolved \(.status.selection.resolvedTopicCount) topics"'
  ```

- **Grant the retention delete credential `s3:GetObject` on
  `<bucket>/<prefix>/*`** before upgrading the controller or runner, or every
  enforcement run keeps every point (`VersionProbeRefused`). On a versioned or
  Object Lock bucket `Enforce` now deletes nothing, and enforcement records from
  earlier builds there that say `Deleted` are false. Plans over a set two
  receipts name change: re-approve them.
- **`KafkaCluster` shapes that stop being accepted** (fixed by delete and
  re-create, because `spec` is immutable): a bootstrap entry that is empty or
  holds a comma or whitespace, an illegal `auth.secretRef` name or
  `passwordKey`, `plaintext` with `tls: true`, and SCRAM without a username or
  Secret.
- **List `RehearsalSchedule` objects**; the kind is withdrawn and its CRD stays
  until you delete it (release-notes item 73).
- **Approval-policy changes** go CRDs → controller and runner → console with its
  confirmation key → `TrustPolicy` keys → the binding. Requests signed under an
  old policy digest are refused `ApprovalPolicyMismatch` and submitted again.

**During the roll.** Restores and backups already admitted keep their Jobs and
finish. A point-bound `Restore` whose bundle the older controller made ends
`ApprovalBundleConflict`: delete and create it again. A `Preflight` in flight may
read `unknown`; create a new one. `helm upgrade --reuse-values` keeps a pinned
`runnerImage` unless you pass `--set runnerImage=…`: the runner must be at least
as new as the controller ([see why](#the-runner-image-must-be-at-least-as-new-as-the-controller)).

**Check that a field arrived before the roll.** A server-side apply without
`--force-conflicts` is refused field by field while the `Established` wait still
passes, on the old schema. Read a field the new controller writes from the CRD
itself, and stop if it is not there:

```bash
kubectl --context "$LOGWEIR_CONTEXT" get crd/approvals.logweir.dev \
  -o jsonpath='{.spec.versions[?(@.name=="v1alpha1")].schema.openAPIV3Schema.properties.status.properties.verifiedSubjectRef.type}'
# object
```

A controller started on an older schema has its new fields pruned: a `Restore`
can then wait forever for an `Approval`'s `status.verifiedSubjectRef`, and every
`Backup` reports `ExecutionInputsUnverified` for want of `status.execution`.

**After the upgrade.** Wait for `HistoryRetained=True` on every schedule before
deleting one without `--cascade=orphan`. Set a catalog's `spec.syncRequest` to
see trust changes at once. Restart the controller after creating or rotating
`logweir-evidence-ro`.

### Rolling back

Roll the controller and runner back together, or the controller first; never
the runner alone. Leave the CRDs in place: they are additive. Before rolling
back:

- **Drain restores.** Scale `weirkeeper` to zero, let or cancel every pending
  and running `Restore`, and check that none sits between its plan `ConfigMap`
  and its Job; an older controller could otherwise build a Job from a
  half-materialised newer `Restore`. A Job that already exists keeps running
  under either controller. Keep the namespace-wide `logweir-approval-bundle` of
  an older build until no remaining Job's pod template references it.
- **Let in-flight `Backup`s finish.** An older runner without the execution
  claim re-runs the engine over a re-created Job's set, and an older controller
  cannot read a `v2` frozen plan (`PlanConfigMapConflict`), nor one frozen with
  `consumerGroups` or with the Strimzi `KafkaTopic`s a `KafkaCluster`'s
  `spec.strimzi` listed.
- **Bound credential Secrets keep working.** An older controller and runner
  ignore the `logweir-binding` pair.
- **Rolling the CRDs back** (not needed: they are additive) prunes
  `spec.target.topicNaming.originalName` and `status.targetTopicsAppeared` from
  stored `Restore`s; their plans are unchanged, and an older runner refuses an
  original-name plan at phase 0.
- **Set every `RetentionPolicy` to `mode: Report`**, wait for `status.lease` to
  clear and enforcement Jobs to finish. An older worker records delete markers
  as deletions on a versioned bucket and refuses a plan with `co_point_ids`.
- **Delete `SourceConnection` and `Switchover` preflights.** An older
  controller cannot decode them, and then reconciles no `Preflight` in any
  namespace (repeat the query below with `"Switchover"`):

  ```bash
  kubectl --context docker-desktop get preflights -A \
    -o jsonpath='{range .items[?(@.spec.request.operation=="SourceConnection")]}{.metadata.namespace}{" "}{.metadata.name}{"\n"}{end}'
  kubectl --context docker-desktop delete preflight -n <ns> <name>
  ```

- **Remove `Approval`s naming a `Switchover`** before rolling the controller or
  the console below the release that added the kind (PROD-04.2). An older build
  decodes `Approval`s as a closed set of kinds, and ONE `Switchover` approval
  fails its whole list (``unknown variant `Switchover` ``, a warning about every
  15 s): no `Approval` is verified, and every new `Restore` stays `Pending`,
  `ApprovalNotVerified`, until they are gone. Record them, then delete them:

  ```bash
  kubectl --context "$LOGWEIR_CONTEXT" get approvals -A -o json \
    | jq '[.items[] | select(.spec.subjectRef.kind == "Switchover")]' > switchover-approvals.json
  kubectl --context "$LOGWEIR_CONTEXT" get approvals -A -o json \
    | jq -r '.items[] | select(.spec.subjectRef.kind == "Switchover") | "-n \(.metadata.namespace) \(.metadata.name)"' \
    | xargs -r -L1 kubectl --context "$LOGWEIR_CONTEXT" delete approval
  ```

  This loses the approvals of switchovers not yet admitted: after rolling
  forward again, such a `Switchover` needs a new approval. A finished
  switchover keeps its signed record (approval mode and principals), and the
  `Switchover` objects stay, inert, under an older controller.
- **Remove `Approval`s naming a `RehearsalSchedule`** before rolling below the
  build that added the value; expect no output from
  `kubectl --context "$LOGWEIR_CONTEXT" get approvals -A -o jsonpath='{range .items[?(@.spec.subjectRef.kind=="RehearsalSchedule")]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}'`.
  Never delete the `Approval` CRD: it deletes every `Approval`.
- **Remove `approverSignature` and `approvalPolicy.default`** (two-person and the
  confirm default) before rolling the console or controller back: older binaries
  refuse to start on them. Requests not yet admitted are then refused
  `ApprovalPolicyMismatch`; admitted runs continue.
- **Suspend schedules** whose overlap matters, that set `timeZone`, `retry`,
  `catchUpPolicy` or the deadline fields, or that select dynamically. An older
  controller does not count detached runs for `Forbid` and starts every queued
  manual run at once.
- **An install that set `runs.*`** rolls the controller back with the chart
  (`helm rollback`), never alone: an older controller refuses a policy document
  with `runs` and fails closed.
- Roll the console and the controller forward together before anyone confirms
  an original-name restore (authorization document 2.1.0).
- To clear check objects an older controller no longer collects:
  `kubectl delete topicdiscoveries,preflights --all -n <namespace>`.
